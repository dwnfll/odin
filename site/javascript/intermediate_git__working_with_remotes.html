イントロダクション

ここまで、カリキュラムのさまざまなプロジェクトに取り組む中で、自分のGitHubリポジトリにプッシュしたりプルしたりするたびに、リモートリポジトリを扱ってきました。このセクションでは、まだ出会ったことがないかもしれない、あるいは使う必要がなかったかもしれない、もう少し高度なトピックを扱います。

レッスン概要

このセクションでは、このレッスンで学ぶトピックの概要を説明します。

  • リモートを使って履歴を変更する方法。
  • 履歴を変更する操作の危険性。
  • 履歴を変更する操作のベストプラクティス。

Gitでフォースプッシュする

あなたがもう一人でプロジェクトに取り組んでいるのではなく、誰かと一緒に取り組んでいるとしましょう。あなたは、変更を加えたブランチをリモートリポジトリにプッシュしたいと思っています。通常、Gitは、あなたがすでにこのリモートからの最新のコミットでローカルブランチを更新している場合にのみ、変更をプッシュさせてくれます。

もしローカルブランチを更新しておらず、リモートリポジトリ上でコンフリクトを引き起こすコミットをgit pushしようとすると、エラーメッセージが表示されます。これは実は素晴らしいことです!これは、一緒に作業している人たちが作ったコミットを上書きしてしまう(悲惨な結果になりかねません)のを防ぐための安全機構です。エラーが出るのは、あなたの履歴が古くなっているからです。

少し調べてみると、git push --forceというコマンドが見つかるかもしれません。このコマンドは、リモートリポジトリを自分自身のローカルの履歴で上書きします。では、他の人と一緒に作業しているときにこれを使うとどうなるでしょうか?まずは、自分一人で作業しているときに何が起こるかを見てみましょう。以下のコマンドをターミナルに入力し、インタラクティブなリベースツールが表示されたら、Create fourth fileのコミットを削除してください:

git push origin main
git rebase -i --root
git push --force
git log

おや、これは興味深いですね。ローカルシステム上に4つ目のファイルが見当たりません。GitHubリポジトリを確認して、そこにあるかどうか見てみましょう。

ああ、まさに今それを壊してしまいました!このシナリオにおける危険性は、一緒に作業している人たちの作業を壊してしまう可能性があるということです!git push --forceは非常に危険なコマンドであり、他の人と共同作業をしているときには注意して使う必要があります。その代わりに、fetchとmergeを使ってローカルの履歴を更新し、それから改めてpushを試みることで、履歴が古いというエラーを解決できます。

別のシナリオを考えてみましょう:

touch test4.md
git add test4.md && git commit -m "Create fifth file"
git push origin main
git log

コミットメッセージを見て、しまった、間違えてしまったことに気づきました。git resetでこのコミットを取り消して、そのままフォースプッシュしたくなるかもしれません。でも待ってください!フォースプッシュは非常に危険なコマンドだということを思い出してください。それを使おうと考えるときは、常にそれが適切かどうか、代わりにより安全なコマンドを使えないかを確認してください。他の人と共同作業をしていて、今行ったばかりのコミットを取り消したい場合は、代わりにgit revertを使うことができます。これならフォースプッシュを行う必要がありません!特に共同作業の文脈についてのより詳しい情報は、「Git Revert vs Git Reset」を見てください。

git revert HEAD
git push origin main

リベースを行っているときに、HEAD、つまり現在見ているコミットを扱っていたことを覚えていますか?これが行うのは、HEADへの変更を取り消す(revert)ことです!それから、私たちが取り組んでいるブランチ(この例ではmainですが、通常はおそらくフィーチャーブランチ上で作業しているでしょう)に、新しいコミットをプッシュすることになります。

さて、git push --forceのさまざまな危険性について学んだところで、なぜこれが存在するのか、そしていつ使うべきなのか、疑問に思っているかもしれません。開発者がgit push --forceを使う非常によくあるシナリオは、プルリクエストを更新するときです。共同作業についてはまた別のレッスンでさらに詳しく扱いますが、このセクションから持ち帰ってほしいのは、--forceオプションは、それが適切だと確信できるときにのみ使うべきだということです。機密情報が誤ってリポジトリにアップロードされてしまい、そのすべての出現箇所を取り除きたい場合など、あまり一般的ではないシナリオもあります。

git push --force-with-leaseについては特に触れる価値があります。一部の企業ではこれがデフォルトのオプションになっています。その理由は、これがフェイルセーフだからです!このコマンドは、プッシュしようとしているブランチが更新されているかどうかを確認し、更新されていればエラーを返します。これにより、前述の通り、作業内容をfetchしてローカルリポジトリを更新する機会が得られます。

危険性とベストプラクティス

ここまで扱ってきた危険性を振り返ってみましょう。ええ、わかっています、怖い話ですよね。でも、気をつけていないと、同僚に嫌われてしまうかもしれません!このレッスンを振り返ってみると、共通するテーマが見えてくるはずです。commit --amend、rebase、reset、push --forceは、いずれも他の人と共同作業をしているときに特に危険です。これらのコマンドは、同僚が作り上げた作業を壊してしまう可能性があります。ですので、それを心に留めておいてください。履歴を書き換えようとするときは、必ず使おうとしている特定のコマンドの危険性を確認し、ここまで扱ってきたコマンドについて、以下のベストプラクティスに従ってください:

  1. チームプロジェクトに取り組んでいる場合は、履歴を書き換えることが安全かどうかを確認し、他の人があなたがそれを行っていることを把握しているようにしてください。
  2. 理想的には、これらのコマンドは、自分一人だけで作業しているブランチに対してのみ使うようにしてください。
  3. 何かを強制するために-fフラグを使うことには、恐れを感じるべきです。それを使うには、本当に十分な理由が必要です。
  4. コミットするたびにプッシュするのはやめましょう。公開済みの履歴を変更することは、可能な限り避けるべきです。
  5. ここまで扱ってきた具体的なコマンドについて:
    1. git commit --amendについては、リモートリポジトリにプッシュ済みのコミットを決してamendしないでください。
    2. git rebaseについては、他の人が作業のベースにしているかもしれないリポジトリを決してリベースしないでください。
    3. git resetについては、リモートリポジトリにプッシュ済みのコミットを決してリセットしないでください。
    4. git push --forceについては、適切な場合にのみ使い、注意して使い、できれば代わりにgit push --force-with-leaseをデフォルトで使うようにしてください。
