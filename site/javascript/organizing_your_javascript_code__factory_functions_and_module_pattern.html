スコープをすくい取る

「スコーピング(scoping)」という言葉は基本的に、「ある変数はどこで私が利用できるのか?」と問うものです - それは変数の現在のコンテキストを示します。ある変数がどんな関数の中でも宣言されておらず、どんな{ 波括弧 }の外にも存在する場合、それらはグローバルスコープにあると言われ、どこからでも利用可能であることを意味します。もしそれらが関数や{ 波括弧 }の中にあれば、それらはローカルスコープにあることが知られています。

ECMAScript 6より前は、JavaScriptには変数を宣言するためのキーワードがvar一つだけでした。これらの変数は再定義や更新ができ、関数スコープ内で定義されていると言われます。つまり、それらは宣言された関数の中でのみ利用可能だということです。

ECMAScript 6では、letとconstというキーワードが導入されました。var変数が関数スコープだったのに対し、これらはブロックスコープである変数を定義できるようにしてくれます - 基本的に、その変数が定義された最も近い{ 波括弧 }のセットの中でのみ利用可能になるように、スコープを絞ります。これらの波括弧は、forループ、if-else条件、あるいは他の似たような構造のものであってもよく、これらはブロックと呼ばれます。これらすべてをまとめる例を見てみましょう。

// This is a global variable
let globalAge = 23;

// This is a function - and hey, a curly brace indicating a block
function printAge(age) {
  // This is a function scoped variable
  var varAge = 34;

  // This is yet another curly brace, and thus a block
  if (age > 0) {
    // This is a block-scoped variable that exists
    // within its nearest enclosing block: the if's block
    const constAge = age * 2;
    console.log(constAge);
  }

  // ERROR! We tried to access a block scoped variable
  // outside its scope
  console.log(constAge);
}

printAge(globalAge);

// ERROR! We tried to access a function scoped variable
// outside the function it's defined in
console.log(varAge);

その例についてじっくり考える時間を取ってください。結局のところ、それほど驚くべき概念ではありませんが、そこにはたくさんの用語が詰まっています - それらすべてが、次の巨大なテーマ、クロージャを理解するのに役立ちます。

クロージャは怖くない

何らかの入力に基づいて、ある値を繰り返し取得したり作成したりする必要がある場合、パラメータを持つ関数を使うことがあるのをご存知でしょう?例えば、引数を受け取り、それらの引数を使った結果として配列や文字列や数値を返す関数を書くことができます。関数も同じです。ある関数を使って別の関数を作成することができます。

これに取り組む最良の方法は、例から始めることでしょう - 以下のコードの断片を見てみてください。

function makeAddingFunction(firstNumber) {
  // firstNumber is scoped anywhere within makeAddingFunction,
  // including returnedFunction
  // any variables declared here will also be accessible within returnedFunction

  // we don't need to name the returned function
  // this is just to reference more easily in explanation
  return function returnedFunction(secondNumber) {
    // secondNumber is scoped only within returnedFunction
    return firstNumber + secondNumber;
  }
}

それから、makeAddingFunctionを呼び出すことで、私たちの関数を作成できます:

const add5 = makeAddingFunction(5);
console.log(add5(2)); // 7

const add8 = makeAddingFunction(8);
console.log(add8(2)); // 10

const add79100105110 = makeAddingFunction(79100105110);
console.log(add79100105110(111687378)); // 79211792488

毎回新しい関数を書く代わりに、私たちのために関数を作成してくれる関数を使うだけです - これは、異なる日付を使って何度も呼び出すtoFormattedDateString(date)関数を書くのと同じように、ロジックと結果の文字列を毎回ハードコーディングする代わりに行うことです。

returnedFunctionは、firstNumberパラメータの周りにクロージャを形成します。クロージャとは、ある関数と、その関数が宣言された周囲の状態の組み合わせを指します。この周囲の状態は、そのレキシカル環境とも呼ばれ、クロージャが作られた時点でスコープ内にあったすべてのローカル変数で構成されます。ここで、add5はmakeAddingFunction(5)の呼び出しによって返された関数への参照です。makeAddingFunction(5)の実行が終了した後も、返された関数がまだそれを必要としているため、5はメモリ上でクリーンアップされません。返された関数は、そのレキシカル環境(この場合はfirstNumberパラメータを含む)にアクセスできます。

これは関数の極めて重要な振る舞いです。これにより、データを関数に関連付け、囲んでいる関数の外側のどこからでもそのデータを操作できるようになります。これをファクトリー関数で利用できますが、それについてはもうすぐ扱います。

では、コンストラクタの何が問題なのか?

コンストラクタに関しては、歴史的に一部の人があまり乗り気になれなかったいくつかのことがあります。それらが悪いとか避けるべきだという意味ではなく、単に、オブジェクトを作成する際、代替手段と比較してコンストラクタが機能する仕方について不満を持っていた人がいた、というだけです。

その一例は、newキーワードなしでコンストラクタを呼び出すといった、間違った使い方を防ぐ自動的な保護策が提供されていないということです(自分自身で保護策を適用する必要があります)。それらは構文的には通常の関数と同じであるため、newなしで呼び出しても依然として「動作」してしまいます。場合によっては、これは意図的に利用されることもあります。例えばDate()コンストラクタは、newと共に呼び出されたかどうかによって異なるものを返します。しかし、これは常に望ましいわけではありません。保護策を追加し忘れると、newなしでオブジェクトを構築しようとしてしまい、その時点でエラーになる代わりに、間違った振る舞いで「動作」してしまうかもしれません(これは、プログラムの他の場所から来る非常に紛らわしいエラーを引き起こすかもしれません)。

もう一つの歴史的な不満は、instanceofが実際にどう機能するかから来ています。他のいくつかのプログラミング言語では、このキーワードはあるオブジェクトがどのコードで作られたかを知るための信頼できる方法です。JavaScriptでは、これはオブジェクトのプロトタイプチェーン全体におけるコンストラクタのプロトタイプの存在をチェックするものであり、あるオブジェクトが実際にそのコンストラクタで作られたかどうかを確認する役には全く立ちません。プロトタイプは、オブジェクトが作成された後でさえ再割り当てされ得ます。

そのため、一部の人々(全員ではありません)は、特定の状況でコンストラクタを使うことを好まず、代わりにこれらの問題のいくつかに対処する似たようなパターンを好みました。今では、コンストラクタの欠点をそれほど多く持たずにオブジェクト/プロトタイプの操作を行うさらに多くの方法があります(class構文については後で学びます)が、これは依然として、実際の現場でよく見かけることになるものであり、それ自体の長所と短所を持っています。

「ファクトリー関数」の登場です。

ファクトリー関数 🏭

これらの凝った響きの関数は、コンストラクタがどう機能するかととても似た働きをしますが、一つ重要な違いがあります - それらはクロージャの力を活用します。オブジェクトを作成するためにnewキーワードを使う代わりに、ファクトリー関数は、関数を呼び出したときに新しいオブジェクトをセットアップして返します。実際のところ、それらはオブジェクトを返す普通の関数に過ぎず、それほど凝ったことは何も起きていません。それらが「ファクトリー関数」のような凝った名前を持つのは、より特定のコンテキスト(オブジェクトを生産する工場のような)である特定の方法で使われるからに過ぎません。

それらはプロトタイプを直接利用しないため、パフォーマンス上のペナルティが発生しますが、一般的なルールとして、何千ものオブジェクトを作成しているのでない限り、このペナルティは大きなものではありません(あなたが作るすべての単一の配列が、毎回すべての単一の配列・オブジェクトメソッドの独自のコピーを持って現れることを想像してみてください…それらがどれほど基本的なもので、一つのプログラムでどれほど多く使うことになりそうかを考えると、それは正気の沙汰ではないでしょう)。

コンストラクタ関数と比較するための基本的な例を見てみましょう。

function User(name) {
  this.name = name;
  this.discordName = "@" + name;
}

おや、これはコンストラクタですね…では、これをファクトリーにリファクタリングできます!

function createUser(name) {
  const discordName = "@" + name;
  return { name, discordName };
}

これはコンストラクタと非常によく似ていますが、これは単なる通常の関数であるため、newキーワードで呼び出す必要はないという点が異なります。

オブジェクトのショートハンド記法

ファクトリー関数の例で返されるオブジェクトの書き方に、混乱する人もいるかもしれません。2015年、オブジェクトを作成するためのショートカットがJavaScriptに追加されました。名前、年齢、色を持つオブジェクトを作成したいとしましょう。これは次のように書くことになります:

const name = "Bob";
const age = 28;
const color = "red";

const thatObject = { name: name, age: age, color: color };

しかし今では、割り当てようとしているプロパティと同じ名前を持つ変数がある場合、それを一度だけ書けばよいのです!

const nowFancyObject = { name, age, color };

これに加えての利点は、これで値をきれいにconsole.logできるようになったということです!以前、name、age、colorの変数を一緒にログ出力したい場合、次のようなことをしていたでしょう:

console.log(name, age, color);

これはBob 28 redのようなものをログ出力します。悪くはありませんが、何が何なのか最も明確というわけではありません。代わりに、今度はそれをいくつかの波括弧で囲んでみてください。これによりそれはオブジェクトになります:

// shorthand for console.log({ name: name, age: age, color: color })
console.log({ name, age, color });

これで{ name: "Bob", age: 28, color: "red" }とログ出力され、これはずっと明確で、しかも手動でラベルを追加する必要もありませんでした!

分割代入

さらにもう一つの表現方法により、オブジェクト(または配列)から値を「取り出す」「抽出する」ことができます。これは分割代入(destructuring)として知られています。オブジェクトがある場合、そのオブジェクトのプロパティを同じ名前の変数に、あるいは配列の場合は任意の名前を付けた変数に抽出できます。以下の例を見てみてください:

const obj = { a: 1, b: 2 };

// equivalent of doing
// const a = obj.a;
// const b = obj.b;
const { a, b } = obj;

そして配列でも:

const array = [1, 2, 3, 4, 5];

// equivalent of doing
// const zerothEle = array[0];
// const firstEle = array[1];
const [zerothEle, firstEle] = array;

分割代入についてのMDNのドキュメントには素晴らしい例がいくつかあり、この概念について良い読み物になるはずです。

プライベート変数とプライベート関数

さて、これらすべてのどこにクロージャが関わってくるのだろうと思っているかもしれません。ファクトリーはオブジェクトを返しているように見えます。ここで、私たちのUserファクトリーを拡張して、さらにいくつかの変数を追加し、「プライベート」なものを導入することができます。今度はこれを見てみてください:

function createUser(name) {
  const discordName = "@" + name;

  let reputation = 0;
  const getReputation = () => reputation;
  const giveReputation = () => { reputation++; };

  return { name, discordName, getReputation, giveReputation };
}

const josh = createUser("josh");
josh.giveReputation();
josh.giveReputation();

// logs { discordName: "@josh", reputation: 2 }
console.log({
  discordName: josh.discordName,
  reputation: josh.getReputation()
});

新しいユーザーのために新しい指標、レピュテーション(reputation)を導入しました。ファクトリー関数で返しているオブジェクトには、reputation変数自体も、その値のコピーも含まれていないことに注目してください。その代わり、返されるオブジェクトには2つの関数が含まれています - 一つはreputation変数の値を読み取るもので、もう一つはその値を1増やすものです。reputation変数は、私たちが「プライベート」変数と呼ぶものです。なぜなら、オブジェクトのインスタンスでその変数に直接アクセスすることはできず、私たちが定義したクロージャを通してのみアクセスできるからです。

落とし穴: 「オブジェクト内で変数をreturnする」

以下は、多くの人が最初に予想するようには振る舞いません:

return { name, discordName, reputation };

これは「reputation変数をreturnする」ことにはなりません。長い形式の構文では、これは次と同じです:

return { name: name, discordName: discordName, reputation: reputation };

私たちはただ、別のオブジェクトプロパティを作成している(オブジェクトのショートハンド記法のおかげで、たまたま自動的にreputationと呼ばれることになる)だけであり、それにreputation変数の値を割り当てているだけです。これは、ある変数の値で別の変数を普通に割り当てるのとまったく同じです。もう一方の変数は元の変数を「追跡」しません。これは次と同じ振る舞いです:

let a = 1;
let b = a;
console.log(a, b); // 1 1

a = 5; // only reassigns a
console.log(a, b); // 5 1

b = 23; // only reassigns b
console.log(a, b); // 5 23

プライベート変数にアクセスする唯一の方法は、クロージャを通してです。

ファクトリー関数に関して言えば、プライベートな変数や関数は、クロージャを使って、ファクトリー関数自体の中により小さな専用の変数や関数を作成します - これらは、オブジェクト自体の中でreturnする必要のないものです。こうすることで、返されるオブジェクトを不要な変数で汚すことなく、よりすっきりしたコードを作ることができます。多くの場合、ファクトリー内のすべての単一の関数をオブジェクトと一緒にreturnする必要はありませんし、内部の変数を公開する必要もありません。クロージャの性質のおかげで、それらをプライベートに使うことができます。

この場合、私たちはreputation変数自体のコントロールを必要としませんでした。レピュテーションを誤って-18000に設定してしまうといった、うっかりミスを避けるために、getReputationとgiveReputationという形で必要な詳細だけを公開します。

コンストラクタとクロージャ

技術的には、プロトタイプの上ではなくコンストラクタの内側で「プライベートプロパティ」にアクセスするメソッドを定義することで、コンストラクタでもクロージャを使うことができるということに注意してください。しかしそれでは、それらは継承不可能になってしまい、コンストラクタの目的が損なわれてしまいます。

ファクトリーによるコンポジション

コンストラクタのレッスンでは、プロトタイプと継承の概念、そして私たちのオブジェクトに別のオブジェクトのプロパティへのアクセスを与える方法について深く見てきました。ファクトリー関数を使うと、同じプロトタイプの仕組みを通してではありませんが、似たような継承のような振る舞いを模倣できます。もう一つの仮定のシナリオを考えてみましょう。私たちは、それ自体のプロパティに加えて、Userからのいくつかの(あるいはすべての)プロパティへのアクセスを持つPlayerファクトリーを必要としています - それを行う方法がいくつかあります:

function createPlayer(name, level) {
  const { getReputation, giveReputation } = createUser(name);

  const getLevel = () => level;
  const increaseLevel = () => { level++; };
  return {
    name,
    getReputation,
    giveReputation,
    getLevel,
    increaseLevel,
  };
}

これでできました!Userを作成し、そこから必要なものを抽出し、望むものを再びreturnし、残りは何らかのプライベートな変数や関数として隠すことができます!複数のオブジェクトから何かを取りたい場合は、Object.assignメソッドを使うこともできます:

function createPlayer(name, level) {
  const user = createUser(name);

  const getLevel = () => level;
  const increaseLevel = () => { level++; };
  return Object.assign({}, user, { getLevel, increaseLevel });
}

これは依然として、createPlayerで作成するオブジェクトごとに、「継承された」メソッドのまったく新しいインスタンスを作成します(プロトタイプ継承を使う場合のようにメモリ内で同じメソッドを共有するのとは異なります)が、先ほど述べたように、絶対的に大量のオブジェクトを作成しているのでない限り、実際にはこれが大きな問題になることはまずありません。

これはコンポジションと呼ばれます。これにより継承と似たようなことができますが、もう少し柔軟性が得られます。なぜなら、必ずしも別のオブジェクトからすべてを望むわけではないかもしれないからです(もしそう望むなら、すべてを取ることもできます)。私たちは、複数のソースから新しいオブジェクトを「コンポーズ(合成)」します。ある問題には継承が向いていることもありますが、それが脆くなることもあり、コンポジションの柔軟性が非常に適していることもあります。技術的にはコンストラクタでもコンポジションを行うことはできますが、それらは継承のアプローチにずっとよく向いています。コンポジションはしばしば、ファクトリー関数の方がずっと自然に行えます。

モジュールパターン

IIFE

多くの場合、複数のオブジェクトを生産するためにファクトリーが必要なわけではなく、代わりにそれを使ってコードのセクションをまとめてラップし、他の場所で必要としない変数や関数をプライベートとして隠すために使っています。これは、ファクトリー関数を括弧で囲み、それをすぐに呼び出す(実行する)ことで簡単に達成できます。この即座の関数呼び出しは、一般的にImmediately Invoked Function Expression(まさにその名の通りです)、略してIIFEと呼ばれます。IIFEは文字通り、即座に呼び出される関数式です:

// This is a function expression
() => console.log("foo");

// The function expression is now an IIFE!
// Although this one is not particularly useful of course
(() => console.log("foo"))();

IIFEを使ってモジュールパターンを実装する

ES6モジュール

ECMAScript 6(2015年にリリース)は、「モジュール」と呼ばれる新しいJavaScriptの機能を導入しました。これは、異なるJavaScriptファイル間でコードをインポート・エクスポートするための構文のセットです。今のところは、実際の現場で今でも見かけることになる、IIFEを使ったモジュールパターンについて、より一般的に話していきます。後のレッスンで、似たような目的でES6モジュールを使うことについて扱います。

IIFEのより役立つ使い方は、「プライベートな」コードをIIFEの中にラップするというパターンです: モジュールパターンです。これはしばしば、ファクトリー関数を使って行われます:

const calculator = (() => {
  let lastResult;

  const add = (a, b) => {
    lastResult = a + b;
    return lastResult;
  };
  const subtract = (a, b) => {
    lastResult = a - b;
    return lastResult;
  };
  const multiply = (a, b) => {
    lastResult = a * b;
    return lastResult;
  };
  const divide = (a, b) => {
    lastResult = a / b;
    return lastResult;
  };
  const getLastResult = () => lastResult;

  return { add, subtract, multiply, divide, getLastResult };
})();

console.log(calculator.add(3, 5)); // 8
console.log(calculator.subtract(6, 2)); // 4
console.log(calculator.getLastResult()); // 4
console.log(calculator.multiply(14, 5534)); // 77476

ここでは、4つの基本的な算術メソッドと、最も最近の計算結果を読み取るメソッドを持つ電卓があります。私たちは電卓オブジェクトを一つだけ欲しいのですが、それでもファクトリー関数を使っています!なぜオブジェクトリテラルを直接使わないのでしょうか?

好むと好まざるとにかかわらず、すべてのオブジェクトプロパティはパブリックです。もし単に電卓オブジェクトリテラルを作っていたら、パブリックな.lastResultプロパティを持つことになり、それを直接再割り当てできてしまう可能性が生まれます(例えばcalculator.lastResult = 111100105110)。私たちはlastResultをプライベートに保ち、その値を読み取り専用でパブリックに公開したいのです。再割り当ては、私たちの決めた条件で内部的にのみ起こるべきです。lastResult変数を、それを実際に必要としていない何からも本当に隠す唯一の方法は、それを外部のスコープから離れた関数の中に置き、それから同じスコープ内でオブジェクトを作成してそれをreturnすることです。ファクトリー関数を…一度だけ呼び出す必要があるものとして!

ここで、私たちはカプセル化という言葉に出会います: データ、コード、あるいは何かを一つの単位にまとめ、その単位自体の内部にあるものへの選択的なアクセスを提供することです。一般的に聞こえるかもしれませんが、これはまさに、私たちがコードをモジュールにラップ(カプセル化)するときに起こることです。私たちはプログラム本体にすべてを公開するわけではなく、他のものが「モジュール」の中の何かとやり取りするために必要なものだけを公開します。

なぜIIFEなのか?

しかし、それならなぜファクトリー関数を書いて一度だけ呼び出すのではダメなのでしょうか?なぜわざわざIIFEを使う必要があるのでしょうか?実は、IIFEなしでは、後で呼び出せるように関数に名前を付ける必要があります。今、それは名前を持つことになり、そのスコープ内で名前を一つ占有すると同時に、そのスコープ内で再利用可能であることも意味します。それは望ましくないかもしれません - 私たちは意図的にそれを一度だけ呼び出したいかもしれません。ファクトリーをIIFEでラップすることで、私たちは同じコードフローを達成しますが、もはや関数に名前を付ける必要がなく、これは後で参照できないことも意味します。私たちは電卓を作成するコードを、事実上モジュールであるものにパッケージ化し、それから後でコード内で使う必要のあるもの、つまりcalculatorオブジェクトだけを公開します。
