Using Git in the Real World

We've just scratched the surface, so here's what to be aware of as you start developing more and more using Git.

イントロダクション

Gitの基本はとてもシンプルですが、混乱するようなエラー状況の間違った側に自分がいると気づいたとき、底なしの穴のように感じられることがあります。何かを間違えたり、間違った解決策を試したりするとデータを失ってしまうのではないかと思ってしまうため、それが余計にもどかしく感じられます。実際には、Gitでデータを「失う」ことは非常に難しいのですが、経験豊富な開発者が探ってみないと気づかないような場所に、確かに隠れてしまうことはあります。

Gitについて言えるのは、よほど驚異的な記憶力を持っていない限り、読むだけで習得することはできない、ということです。実践的な練習が必要なのです!例えば、直したい問題を見つけ、マージエラーに遭遇し、それからGoogleで調べて、その問題を直す助けになる新しいGitのテクニックを学んでいく、といった具合です。

あなたを助けるために、困ったときにはまたこのレッスンに戻ってきて参照してください。まずはコミットメッセージについておさらいし、それから、このプロジェクト自体で実際に使われているGitHubワークフローの実例を扱います。

共同作業のためのコミットメッセージ

ワークフローに深く入っていく前に、少し時間を取って、良いコミットメッセージについておさらいしておきましょう。おさらいのためにCommit Messagesのレッスンを確認できます。ここで特に注目しておきたいのが、Conventional Commitsです。これは共同プロジェクトでますます人気が高まっている、コミットの標準規格です。これにより、あなたのコミットメッセージが、読む人全員にその目的を明確に伝えられるようになります。今後は、(まだ実践していないなら)これらを実践してみるとよいかもしれませんし、少なくとも他のリポジトリを読むときのために知っておくとよいでしょう。

課題

私たちのカリキュラムリポジトリに貢献したいとしましょう。

リポジトリへの書き込みアクセス権がない場合、どうやって貢献すればよいのでしょうか?以下は、このウェブサイトの貢献者が実際に使っている、本番環境で使えるワークフローです。ここでは、あなたが私たちのリポジトリのオープンなissueにコメントし、それがあなたに割り当てられたと仮定します。もしissueが割り当てられていなくても、適当な更新を加えながら同じように進めることはできますが、あなたの変更は正当なものではないため、プルリクエストを送るセクションのステップ3の手前で止めてください。

この話の主な登場人物は、upstream(元のGitHubリポジトリ)、origin(そのリポジトリのあなたのフォーク)、そして「local」リポジトリ(originのあなたのローカルクローン)です。幸せな三角関係だと考えてください……ただし、上のワークフロー図に示されているように、「local」はupstreamからプルすることしかできず、プッシュはできません。

初期セットアップ

  1. プロジェクトのTOPのcontributingガイドを読んでください。
  2. ブラウザでcurriculumリポジトリを開いてください。リポジトリページの右上にある「Fork」ボタンを使って、リポジトリ全体(1つのファイルだけではなく)のコピーを、あなた自身のGitHubアカウントに作成してください。
  3. git clone git@github.com:your_user_name_here/curriculum.gitのようなコマンドを使って、フォークしたリポジトリをローカルマシンにクローンしてください(そのURLは、GitHub上のそのリポジトリのページの右側のサイドバーにある小さなウィジェットから取得できます)。
  4. リポジトリをクローンしたことで、あなたにはすでにoriginを指すリモートがあります。これは、あなたのGitHub上のフォークです。これを使って、変更をGitHubに再びプッシュすることになります。また、GitHub上の元のリポジトリ(これをupstreamと呼びます)から直接プルできるようにもしたいので、もう一つのリモートとしてセットアップします。これを行うには、プロジェクトフォルダcurriculumの中で、以下のgitコマンドを使ってください:
git remote add upstream git@github.com:TheOdinProject/curriculum.git

継続的なワークフロー

メインブランチは1つ、mainです。mainは本番環境で使える準備が整ったコードのためのものです。main(あなたのフォークではなく、元のリポジトリの方)にデプロイされたコードは、ステージングでテストされてから本番環境に出荷されます。あなたはフィーチャーブランチで作業し、mainブランチに対してプルリクエストを送ることになります。

  1. 構築したい機能のための新しいフィーチャーブランチを作成し、Revisiting Rock Paper Scissorsのレッスンのブランチのセクションで学んだのと同じやり方に従って、コミットを追加してください。
  2. 機能が完成する頃には、おそらくその間に誰かがupstreamリポジトリに変更を加えているでしょう。つまり、あなたのmainブランチはおそらく古くなっているということです。git fetch upstreamを使って、最新のコピーをフェッチしてください。
  3. 次に、git mergeを使って、upstreamの変更をあなたのローカルのmainにマージしてください。具体的には、まずgit checkout mainで自分がmainブランチにいることを確認し、それからgit merge upstream/mainで、先ほどフェッチしたupstreamの変更をマージします。
  4. これでmainブランチがupstreamと同期して最新になったので、今度はそれをフィーチャーブランチにマージする必要があります。はい、それで合っていますが、最初は奇妙に感じるかもしれません。フィーチャーブランチをmainブランチにマージしたいのではないのか、と思うかもしれません。ええ、その通りです、でもまだです。あなたのフィーチャーブランチは汚れています。忍び寄ってくるかもしれないコンフリクトがあるかどうか、まだわかりません。より「上位の」ブランチをマージするとき(例えば、フィーチャーをマージしてmainにする場合)は、できる限りクリーンでコンフリクトのないマージにしたいものです。そこでまず、「上位の」ブランチを汚れたブランチにマージして、それらのコンフリクトを解決します。git checkout your_feature_nameを実行してフィーチャーブランチに戻り、それからgit merge mainでmainをそこにマージしてください。
  5. マージコンフリクトが発生することがあります……Working with Remotesのレッスンで学んだスキルを使って、それらを解決してください!

fetchとmergeを使って明示的に行う

git fetch upstreamの後にgit merge upstream/some_branchを行うのは、git pull upstream some_branchを実行するのとまったく同じことである点に注意してください。ここではステップを明示的に見ていけるように、あえて分割しています。

プルリクエストを送る

  1. これでフィーチャーブランチはすっかりきれいになり、mainにクリーンにマージできることがわかったので、大変な部分はすべて終わりました。あとは、GitHub上の私たちのupstreamリポジトリに対して、プルリクエスト(しばしばPRと略されます)を作成するだけです!

  2. 次に、フィーチャーブランチをあなたのorigin(upstreamリポジトリのあなたのフォーク)に送り返したいと思います。あなたにはupstreamへのアクセス権がないため、直接送ることはできません。そのため、プルリクエストを作成する必要があります。git push origin your_feature_nameを使って、フィーチャーブランチをGitHub上のあなたのフォークに送ってください。

    不要なPRを開かないでください

    取り組むべきissueを割り当てられていない場合は、ここで止まってください。テスト用・練習用のPRを開かないでください。そのようなPRはすべて、スパムとして扱われ、レビューされることなくメンテナーによってクローズされます。

    メンテナーによってissueへの取り組みを割り当てられている場合は、遠慮なく次のステップに進んでください。

  1. 割り当てられたissueを完了した場合、最後のステップは、フィーチャーブランチを元のupstreamリポジトリのmainブランチにマージするための、プルリクエストを送ることです。これはGitHubのインターフェースを使って行えます。
  2. 存分に喜んでください、あなたはOSSのコントリビューターです!
