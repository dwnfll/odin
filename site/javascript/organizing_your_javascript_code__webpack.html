Webpack

イントロダクション

前のレッスンでは、ES6モジュール(ESM)とnpmを紹介しました。ESMの導入により、個々のスクリプトファイルと依存関係を管理することに関する問題の一部は大きく緩和されました。しかし、特にサードパーティのファイルがさらに多くインポートされるにつれて、大量のモジュールファイルを個別にダウンロードすることはパフォーマンスを低下させる可能性があります。

幸いなことに、より最近のウェブ技術はこれらの側面を大きく改善してきましたが、バンドラーは今でも、私たちのコードをさまざまな方法で処理・最適化するための大きな力を提供してくれます。しかし、この力には、バンドラーを設定する必要があるという小さなコストが伴います。今のところ、私たちのニーズは少なくシンプルなので、基本的なことを一つずつ見ていくことができます。

バンドラーについての認識と基本的な経験は価値があります。近年、私たちのために多くの基本的な設定を処理してくれる新しいビルドツールが登場していますが、実際の現場では、これらの目新しいツールを使う機会が常にあるとは限りません。より手動の設定を必要とするツールを使っているコードベースで作業することになるのは、非常にありそうなことです。あなたのために多くのことを処理してくれるツールを使うときでさえ、それらのツールが実際にあなたのために何をしているのかを理解しておくことは役立ちます。

先に進む前に、最新のLTSバージョンのNode.jsを実行していることを確認してください。必要であれば、Node.jsのインストールのレッスンに従って、NVMを使って最新のLTSバージョンをインストールできます。

レッスン概要

このセクションでは、このレッスンで学ぶトピックの概要を説明します。

  • バンドラーの目的とその仕組みを説明します。
  • JavaScriptモジュールをバンドルするようWebpackを設定します。
  • HtmlWebpackPluginの使用を含め、バンドリング中にJavaScript以外のファイルを扱うようWebpackを設定します。
  • Webpackの開発サーバーをセットアップします。

バンドリング

ES6モジュールのレッスンでは、エントリーポイントとは何か、依存関係グラフとは何か、そしてエントリーポイントファイルをモジュールスクリプトとしてHTMLに追加する方法を学びました。バンドリングでも、エントリーポイントと依存関係グラフの同じ概念が当てはまります。私たちはバンドラーにエントリーポイントを提供します。それから、そのファイルから依存関係グラフを構築し、関連するすべてのファイルを組み合わせ、必要なコードがすべて含まれた単一のファイルを出力します。

これを行っている間に、コードのミニファイ化、画像の最適化、あるいは「ツリーシェイキング」といった、他のさまざまなことも行わせることができます。これらの追加の最適化のほとんどはこのコースの範囲を超えていますが、代わりにJavaScriptの基本的なバンドリングと、HTML、CSS、画像の扱いに焦点を当てていきます。

Webpack

Webpackは、最も人気があるとは言わないまでも、最も人気のあるJavaScriptバンドラーの一つであり、長い間そうであり続けています。バンドリングを始めてみましょう!

まず、練習用アプリのために新しいディレクトリを作り、それから(Webpackのような)使用するパッケージについての情報をnpmが記録するためのpackage.jsonファイルをその中に作成する必要があります。ターミナルで以下を実行してください:

mkdir webpack-practice &&
cd webpack-practice &&
npm init -y --init-type=module

これにより、あなたが今作って入ったwebpack-practiceディレクトリの中にpackage.jsonファイルが作成されるはずです。さあ、これでWebpackをインストールできます:

npm install --save-dev webpack webpack-cli

npm auditの脆弱性

npmでパッケージをインストールした後、出力にいくつかの脆弱性とnpm audit fixの実行について何か書かれているかもしれません。これらは技術的には脆弱性ではありますが、非常に特定のニッチなものである可能性が高く、TOPに関する限り、カリキュラムであなたが行うどんなことにも実際に危険を及ぼす可能性は非常に低いので、それらを見かけても無視して構いません。

これらは、より大きな利害が絡む本番アプリを作っている場合に、それらの脆弱性自体を調べて実質的な害を及ぼし得るかどうかを確認する必要がある、という場合に、より関連性があります。

--save-devフラグ(ショートカットとして-Dも使えます)を含めたことに注意してください。これは、npmに、私たちの2つのパッケージを開発時の依存関係として記録するよう伝えます。私たちは開発中にのみWebpackを使うことになります。Webpackを実際に動かすコードは、ブラウザが実行するコードの一部にはなりません。

また、これらのインストールが完了すると、npmが私たちのためにnode_modulesディレクトリとpackage-lock.jsonファイルを作成したことにも気づくでしょう。node_modulesはWebpackの実際のコード(その他たくさんのもの)が置かれる場所で、package-lock.jsonは、npmがより具体的なパッケージ情報を追跡するために使う、単なる別のファイルです。

srcとdist

Webpackを扱うとき(そしてしばしば他のどんなバンドラーやビルドツールを扱うときも)、非常に重要な2つのディレクトリがあります: src(「source」の略)とdist(「distribution」の略)です。技術的にはこれらのディレクトリを好きなように呼ぶこともできますが、これらの名前は慣習です。

srcは、私たちのウェブサイトのソースコードすべてを保管する場所であり、基本的に私たちのすべての作業が行われる場所です(例外は、プロジェクトのルートにある設定ファイルを変更することです)。私たちがコードをバンドルするためにWebpackを実行すると、バンドルされたファイルはdistディレクトリに出力されます。この考え方は、もし誰かがプロジェクトをフォークあるいはクローンしたとしても、distディレクトリは必要ない、というものです。なぜなら、彼らはただWebpackを実行してsrcから自分自身のdistにビルドできるからです。同様に、私たちのウェブサイトをデプロイするには、distのコードだけがあればよく、他には何も必要ありません。それを覚えておいてください!srcの中で作業し、distにビルドし、それからそこからデプロイするのです!

JavaScriptをバンドルする

インポートのファイル拡張子

通常、ESMでは、他のファイルからインポートする際にファイル拡張子を指定する必要があります(例えば"./greeting.js")。Webpackや他の多くのバンドラーでは、.jsのような一部のファイル拡張子はオプションです。なぜなら、Webpackはデフォルトで、拡張子のないファイルパスに対して自動的に.jsファイルをチェックするからです(例えば"./greeting")。

これはESMではなくWebpackの機能です。

このレッスンでは、インポートの例は、明示的にするために、適切な場合は常にファイル拡張子を含めます。

さて、プロジェクトディレクトリにWebpackをインストールしたので、その中に2つのJavaScriptファイルを含むsrcディレクトリを作成しましょう: index.jsとgreeting.jsです。

mkdir src && touch src/index.js src/greeting.js

2つのJavaScriptファイルの中に、次のものを入れます:

// index.js
import { greeting } from "./greeting.js";

console.log(greeting);
// greeting.js
export const greeting = "Hello, Odinite!";

素晴らしい、これでgreeting.jsからインポートし、それに依存するindex.jsができました。これをバンドルするには、Webpackの設定ファイルも必要になります。これには、エントリーポイント、出力先、そしてプラグインやローダー(これについてはすぐ後で扱います)のようなものなど、バンドリングに必要なすべての詳細が含まれます。

プロジェクトのルート(つまりsrcの外)に戻り、次の内容を含むwebpack.config.jsファイルを作成してください:

// webpack.config.js
import path from "node:path";

export default {
  mode: "development",
  entry: "./src/index.js",
  output: {
    filename: "main.js",
    path: path.resolve(import.meta.dirname, "dist"),
    clean: true,
  },
};

エクスポートされたオブジェクトには、いくつかの重要なセクションが含まれていることに気づくでしょう:

  • mode: 今のところ、これは開発モードのままにしておきます。その方が私たちにとってより役立つからです。これとproductionモードについては、後のレッスンで再訪します。
  • entry: 設定ファイルから、私たちのエントリーポイントであるファイルへのファイルパスで、この場合はsrc/index.jsです。
  • output: 出力バンドルについての情報を含むオブジェクトです。
    • filename: 出力バンドルの名前です - 好きなものにできます。
    • path: 出力ディレクトリへのパスで、この場合はdistです。Webpackを実行したときにこのディレクトリがまだ存在しない場合、自動的に作成してくれます。path.resolveの部分がなぜあるのかについては、あまり気にしすぎないでください - これは単に、Webpackが出力ディレクトリを指定することを推奨している方法です。
    • clean: このオプションを含めてtrueに設定すると、バンドルするためにWebpackを実行するたびに、ファイルをバンドルする前にまず出力ディレクトリを空にします。これにより、distをきれいに保つことができ、最も最近のバンドリングによって生成されたファイルだけが含まれるようになります。

これらすべてのファイルが揃ったら、Webpackを実行して何が起こるか見てみましょう!

npx webpack

Webpackが私たちのために、main.jsファイルを含むdistディレクトリを作成したのが見えるはずです!このファイルの中には…たくさんのものが…あります。心配いりません、これらのもののほとんどは、後で使う開発ツールのためだけのものです。もしこのファイルをnode dist/main.jsで実行してみると、ターミナルにHello, Odinite!がログ出力されるのが見えるはずです。

おめでとうございます!あなたはたった今、Webpackで最初のバンドルを作りました!

HTMLを扱う

実際にいくつかのHTMLを含めてみましょう。結局のところ、私たちが興味を持っているのはウェブサイトを作ることですから!HTMLはJavaScriptではないため、Webpackはそれをそのままバンドルすることはできませんが、私たちにぴったりの、HtmlWebpackPluginと呼ばれる便利なツールがあります。

以下のコマンドを実行して、HtmlWebpackPluginを(こちらも開発時の依存関係として)インストールしてください:

npm install --save-dev html-webpack-plugin

また、srcの中にtemplate.htmlを作成し(このファイルは好きな名前にできます)、いつものHTMLボイラープレートで埋めるべきです。このファイルにscriptタグを入れる必要はありません!HtmlWebpackPluginが自動的に、出力バンドルをscriptタグとして追加してくれます。自分自身のものも含めることで二重にしたくはありませんよね!webpack.config.jsの中に、いくつか小さな部分を追加できます。

// webpack.config.js
import path from "node:path";
import HtmlWebpackPlugin from "html-webpack-plugin";

export default {
  mode: "development",
  entry: "./src/index.js",
  output: {
    filename: "main.js",
    path: path.resolve(import.meta.dirname, "dist"),
    clean: true,
  },
  plugins: [
    new HtmlWebpackPlugin({
      template: "./src/template.html",
    }),
  ],
};

ここで行っているのは、私たちのWebpackの設定がHtmlWebpackPluginにアクセスできるようにし、それから設定オブジェクトにプラグインとして追加することだけです。HtmlWebpackPluginのコンストラクタ呼び出しの中に、オプションを渡します。今のところ、私たちが関心があるのはtemplateオプションだけです。

もしsrc/template.htmlファイルへのパスをテンプレートとして提供すると、再びnpx webpackを実行したときに、distディレクトリにmain.jsファイルだけでなくindex.htmlファイルも含まれていることに気づくでしょう(それらを一つのファイルにまとめることはできません)。また、HtmlWebpackPluginが自動的にindex.htmlファイルに遅延読み込みのscriptタグを追加してくれたことにも気づくでしょう - なんて愛らしいのでしょう!このファイルをブラウザで開いてブラウザのコンソールを確認すると、私たちの素敵な"Hello, Odinite!"という文字列がログ出力されているのが見えるはずです。

これで、HTMLファイルを扱い、適切なscriptタグを注入するようにWebpackをうまく設定できました。HTMLに何か変更を加えるたびに、Webpackを再実行するだけで、新しいdistのコードを生成できます。

CSSをどう扱うか見てみましょう。

CSSを読み込む

CSSのために新しいパッケージが一つだけ必要なわけではなく、2つ必要です。まったく、なんて欲張りな…インストールしましょう。

npm install --save-dev style-loader css-loader

css-loaderは、JavaScriptファイルでインポートするあらゆるCSSファイルを読み取り、その結果を文字列として保存します。style-loaderはそれから、その文字列を受け取り、それらのスタイルをページに適用する実際のJavaScriptコードを追加します。ですので、両方が必要です。

webpack.config.jsに戻って、Webpackに何をすべきか分からせるために、これらのローダーを追加する必要があります。これらはプラグインではないため、別のセクションに入ります:

// webpack.config.js
import path from "node:path";
import HtmlWebpackPlugin from "html-webpack-plugin";

export default {
  mode: "development",
  entry: "./src/index.js",
  output: {
    filename: "main.js",
    path: path.resolve(import.meta.dirname, "dist"),
    clean: true,
  },
  plugins: [
    new HtmlWebpackPlugin({
      template: "./src/template.html",
    }),
  ],
  module: {
    rules: [
      {
        test: /\.css$/i,
        use: ["style-loader", "css-loader"],
      },
    ],
  },
};

これがすることは、.cssで終わるインポートされたファイルに出会ったら、リストされたローダーを使ってそのCSSファイルを処理すべきだとWebpackに伝えることだけです。

CSSではローダーの順序が重要!

配列の末尾にcss-loaderを置いていることに注目してください。この順序を設定しなければならず、逆にしてはいけません。

Webpackは末尾からローダーを実行していくので、まずcss-loaderでCSSファイルを文字列に読み込み、それからstyle-loaderを使ってその文字列内のCSSをページに適用するJavaScriptを注入してほしいのです。逆の順序では同じようには機能しません。

これで、Webpackはインポートされたcssファイルをどう扱えばよいか分かるようになったので、いくつかCSSを追加してみましょう!次の内容でsrc/styles.cssを作成してください:

/* styles.css */
body {
  background-color: rebeccapurple;
}

これで、自分のJavaScriptファイルの一つにCSSファイルをインポートできます。src/index.jsが理にかなっています。インポートされたCSSファイル自体からは何も必要ありません。CSSとstyleのローダーがそのすべてを私たちの代わりに処理してくれるので、副作用のためのインポートを使うだけで構いません。

// src/index.js
import "./styles.css";
import { greeting } from "./greeting.js";

console.log(greeting);

もう一度、npx webpackを使ってWebpackでバンドルし、それからdist/index.htmlを開いて、美しい紫の画面を楽しんでください!

linkタグはどうなったのか?

以前していたように、HTMLテンプレートでCSSファイルをリンクしていないことに気づいたでしょう。次のセクションのローダーの一つを使ってこれを行うこともできますが、実際の現場では、プロジェクトはしばしば多くの可動部分と多くのモジュールを含みます。結局のところ、それらが必要とされるモジュールでインポートする、複数のより小さなCSSファイルを扱う方が簡単になっていきます。それらのファイルを、グローバルにではなくそれらのモジュールだけにスコープする方法さえあります!

私たちは、CSSをJavaScriptにインポートできるようにするための最小限のものだけを紹介していますが、多くのビルドツールやより洗練されたバンドラーの設定は、ここで示したものよりもインポートされたCSSに対してずっと多くのことを行います。

画像を読み込む

主要なWebpackの設定はほぼ終わりです!ウェブサイトに含めたいローカルの画像ファイルがある場合、それらもJavaScriptファイルではないため、少し追加の設定が必要になります。

ローカルの画像ファイルを扱う可能性のある方法は3つあります:

  1. url()の中でCSSで使われる画像ファイル

    幸運なことに!css-loaderがすでにこれを私たちの代わりに処理してくれるので、CSS内の画像パスについては追加ですることは何もありません!

  2. HTMLテンプレートで参照する画像ファイル、例えば<img>のsrcとして

    html-loaderと呼ばれるものをインストールし、それを使うようWebpackに伝える必要があります。これは、HTMLテンプレート内の画像ファイルパスを検出し、正しい画像ファイルを私たちの代わりに読み込んでくれます。これがないと、./odin.pngのようなsrcは、Webpackを実行してdistにビルドすると、もう正しいファイルを参照しなくなる、単なるテキストの断片になってしまいます。インストールしましょう:

    npm install --save-dev html-loader

    それから、webpack.config.js内のmodule.rules配列に次のオブジェクトを追加してください:

    // webpack.config.js
{
  test: /\.html$/i,
  use: ["html-loader"],
}

  3. JavaScriptで使う画像で、ファイルをインポートする必要があるもの

    もしローカルの画像ファイルをJavaScriptで使う必要がある場合(例えばimg要素を作成・編集してsrc属性を設定するためにDOMを操作するときなど)、画像をJavaScriptモジュールにインポートする必要があります。画像はJavaScriptではないため、asset/resourceルールを追加することで、これらのファイルがアセットであることをWebpackに伝える必要があります。ここでは何もインストールする必要はありません。webpack.config.js内のmodule.rules配列に、次のオブジェクトを追加するだけです:

    // webpack.config.js
{
  test: /\.(png|svg|jpg|jpeg|gif)$/i,
  type: "asset/resource",
}

    testプロパティの正規表現は、必要のないファイル拡張子を取り除いたり、必要な拡張子を追加したりして、いつでも編集できます。上記に示されているものは、Webpackのアセット管理ガイドそのままのもので、最も一般的な画像ファイルの拡張子のほとんどを認識してくれます。

    それから、その画像を使いたいどのJavaScriptモジュールでも、デフォルトインポートするだけで構いません。

    // src/index.js
import odinImage from "./odin.png";

const image = document.createElement("img");
image.src = odinImage;

document.body.appendChild(image);

    distにバンドルするときでもodinImage変数が正しいファイルパスを含むように、これをインポートする必要があります。もし単にimage.src = "./odin.png";と書いていたら、その「ファイルパス」は単なるプレーンな文字列になってしまいます。distにバンドルするとき、Webpackは私たちのJavaScript内のこの文字列がファイルを参照しているとは魔法のように認識してくれないため、バンドルにそれを含めません。それをインポートし、正しいasset/resourceルールを設定すると、Webpackはそのインポートを認識し、バンドル時に画像ファイルを含め、さらにインポートされた変数が最終的に正しいファイルパスを含むようにしてくれます。

これらすべてを終えて、html-loaderと画像のasset/resourceルールの両方を追加すると、私たちのwebpack.config.jsは次のようなものになるでしょう:

// webpack.config.js
import path from "node:path";
import HtmlWebpackPlugin from "html-webpack-plugin";

export default {
  mode: "development",
  entry: "./src/index.js",
  output: {
    filename: "main.js",
    path: path.resolve(import.meta.dirname, "dist"),
    clean: true,
  },
  plugins: [
    new HtmlWebpackPlugin({
      template: "./src/template.html",
    }),
  ],
  module: {
    rules: [
      {
        test: /\.css$/i,
        use: ["style-loader", "css-loader"],
      },
      {
        test: /\.html$/i,
        use: ["html-loader"],
      },
      {
        test: /\.(png|svg|jpg|jpeg|gif)$/i,
        type: "asset/resource",
      },
    ],
  },
};

画像がバンドリング時に含まれると、dist内の出力画像ファイルは異なるファイル名を持つことに気づくかもしれません(おそらく数字と文字のごちゃまぜのようなものになるでしょう)。デフォルトでは、Webpackはバンドルされた画像ファイルに、その内容をハッシュ化することで新しい名前を付けます。これがどう機能するかを知る必要はありませんし、なぜそうなるのか、あるいはそれをどう変更するかについて深掘りする必要もありません。これが期待される振る舞いだということだけ知っておいてください(これはブラウザのキャッシュやファイル名の一致に関する問題を防ぐためのものです)。

必要なものだけを設定すればよい

私たちが言及したことすべてが必要というわけではないかもしれません。もしあなたのプロジェクトがHTMLテンプレートにローカルファイルパスのソースを持つ画像を持っていないなら、html-loaderをセットアップする必要はありません。JavaScriptでローカルの画像を一切使っていないなら、画像のasset/resourceルールをセットアップする必要はありません。

同様に、将来的には、カスタムフォントやプリプロセッサのような、特別なローダーやプラグインを必要とするものを扱うことになるかもしれません。その時が来たら、Googleを使うか、Webpackのドキュメントを参照して、何が必要かの手順を確認することができます。

Webpackの開発サーバー

このレッスンの間、変更のたびにnpx webpackを実行して再バンドルしなければならないことに少しイライラしましたか?幸いなことに、これにはいくつかの解決策があり、私たちが最も便利だと考えるオプション、webpack-dev-serverに焦点を当てていきます。次のようにインストールしてください:

npm install --save-dev webpack-dev-server

以前、変更を保存するたびにウェブページを自動的にリフレッシュしてくれる、Live Preview VSCode拡張機能のようなものを使ったことがあるかもしれません。webpack-dev-serverはそれと非常によく似ており、つまり、変更を加えるたびにnpx webpackを実行し続ける必要がなくなるということです。

これは、あなたのコードを裏側でバンドルすることによって機能します(npx webpackを実行したかのようですが、ファイルをdistに保存することはありません)。そして、バンドルで使われるファイルを保存するたびにこれを行います。エラーメッセージが、単一のバンドルされた.jsファイル内のごちゃごちゃした内容ではなく、私たちの開発コードのファイルと行を参照するように、source mapと呼ばれるものを使うこともできます!

インストールしたら、私たちのwebpack.config.jsの中で、設定オブジェクトのどこかにさらにいくつかのプロパティを追加するだけで済みます(これらのプロパティの順序は重要ではありません):

// webpack.config.js
import path from "node:path";
import HtmlWebpackPlugin from "html-webpack-plugin";

export default {
  mode: "development",
  entry: "./src/index.js",
  output: {
    filename: "main.js",
    path: path.resolve(import.meta.dirname, "dist"),
    clean: true,
  },
  devtool: "eval-source-map",
  devServer: {
    watchFiles: ["./src/template.html"],
  },
  plugins: [
    new HtmlWebpackPlugin({
      template: "./src/template.html",
    }),
  ],
  module: {
    rules: [
      {
        test: /\.css$/i,
        use: ["style-loader", "css-loader"],
      },
      {
        test: /\.html$/i,
        use: ["html-loader"],
      },
      {
        test: /\.(png|svg|jpg|jpeg|gif)$/i,
        type: "asset/resource",
      },
    ],
  },
};

まず、devtoolオプションとしてeval-source-mapを設定することで、source mapを追加します。これを行わないと、得られるエラーメッセージが、私たちの開発コードの正しいファイルや行番号と必ずしも一致しなくなります。開発者ツールの「Sources」タブでも、元の手を加えていないコードを見つけることができなくなり、Chromeのデバッガーが使いにくくなります。このsource mapを追加することで、これらの両方の問題が解決されます。

次に、デフォルトでは、webpack-dev-serverは、私たちのJavaScriptバンドルにインポートしているファイルへの変更を検出したときにのみ自動的に再起動するため、私たちのHTMLテンプレートは無視されてしまいます!必要なのは、それを開発サーバーの監視対象ファイルの配列に追加することだけです - 簡単でシンプルですね!

セットアップが終わったら、次のコマンドを使って開発サーバーを起動できます:

npx webpack serve

私たちのサイトは、デフォルトでhttp://localhost:8080/から利用可能になります。

設定変更時には開発サーバーを再起動する

webpack-dev-serverは、起動時にのみあなたのwebpack設定を読み取ることに注意してください。開発サーバーが実行されている間にwebpackの設定ファイルを変更しても、その設定の変更は反映されません。ターミナルでCtrl + Cを使ってそれを終了させ、それからnpx webpack serveを再実行して新しい設定を適用してください。

まとめ
