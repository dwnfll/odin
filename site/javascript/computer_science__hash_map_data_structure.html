HashMap Data Structure

日本語訳

← javascript

Learn how a hash map works, to save and retrieve data

イントロダクション

プログラミング言語全般で最もよく使われるデータ構造の一つが、ハッシュテーブル、別名ハッシュマップです。ハッシュマップは従来の配列と似ていますが、値に対して意味のない連番を振る代わりに、"キー"をインデックスとして使う点が異なります。このようにデータを整理することで、その構造の中のキーに対して高速な検索が可能になります。JavaScriptのオブジェクトリテラル({})、Set、Mapを使ったことがあるなら、あなたはすでにハッシュテーブルをベースにした構造を使ったことがあることになります。しかし、それらは内部でどのように動作しているのでしょうか?どうやってキーと値のペアを保存し、後で取り出すことができるのでしょうか?

このレッスンでは、それがどのように機能するのかを学び、次のプロジェクトでは自分自身のハッシュマップを実装することになります!まずは、ハッシュマップについての簡単な説明から始めましょう: ハッシュマップはキーと値のペアを受け取り、ハッシュコードを生成し、そのペアをバケットに保存します。ハッシュコード?バケット?何のこと?と思うかもしれませんが、心配いりません。これらの概念について、詳しく学んでいきます。さあ、始めましょう!

  • ハッシュマップと、その内部での動作の仕組み。

ハッシュコードとは何ですか?

まずは、値をハッシュ化するとはどういうことかを学ぶところから始めましょう。ハッシュ化とは、入力を受け取り、それに対応する出力を生成することです。ハッシュ関数は純粋関数(pure function)であるべきです。同じ入力をハッシュ化すれば、常に同じハッシュコードが返されるべきであり、ランダムに生成される要素があってはいけません。例えば、名前を受け取り、その名前の最初の文字を返すハッシュ関数を見てみましょう:

function hash(name) {
  return name.charAt(0);
}

これで、最初の基本的なハッシュ関数ができました。

ハッシュ化と暗号化(encryption)には重要な違いがあります: それは可逆性です。 ハッシュ化は一方向のプロセスです。上の例を使うと、名前からハッシュコードを作ることはできますが、ハッシュコードから名前に戻すことはできません。名前が"Carlos"だとすると、これを"C"にハッシュ化できます。しかし、"C"から元の形に戻すことは不可能です。それが"Carlos"なのかどうかはわかりません。もしかしたら"Carla"かもしれませんし、"Carrot"かもしれません。それはわからないのです。

ハッシュ化の利点

ハッシュ化はセキュリティにおいて非常に有用です。パスワードが与えられたとき、そのパスワードの平文の代わりに、パスワードのハッシュを保存できます。もし誰かがあなたのハッシュを盗んだとしても、ハッシュをパスワードに戻すことができないため、元のパスワードを知ることはできません。

使用例

これらのハッシュを使って、何ができるのでしょうか?学校で、フォルダがより小さなフォルダに整理されていて、それぞれのフォルダが同じ頭文字を持つ人たちの情報を保持しているのを見たことがあるかもしれません:

C:
  carlos.txt
  carla.txt
B:
  bryan.txt
  bob.txt
  beatrice.txt
  bella.txt
  benjamin.txt
  bianca.txt

もし私たちの学校に"Carlos"という名前の新しい生徒が入ってきたら、ハッシュ関数を実行して、どのフォルダに入れるべきかを調べることができます。hash("Carlos") -> "C"となるので、"Carlos"をCというラベルの付いたディレクトリに入れます。

ここで問題に気づいたかもしれません: もし私たちの学校に、名前の頭文字がCである人がたくさんいたらどうなるでしょうか?そうすると、Cというラベルの付いたディレクトリに名前が入りすぎてしまう一方で、他のディレクトリは空になってしまうかもしれません。この重複をなくし、生徒たちをよりうまく分けるためには、ハッシュ関数を見直す必要があります。

function hash(name, surname) {
  return name.charAt(0) + surname.charAt(0);
}

名前の最初の文字だけを取るのではなく、名(first name)と姓(last name)の最初の文字を取るようにします。"Carlos Smith"のハッシュコードは"CS"になります。これにより、生徒たちがより多くのディレクトリに分散され、重複するハッシュコードが生成されにくくなります。

しかし、これでも問題は解決しません。生徒の名前の頭文字の組み合わせがよくあるものだったらどうなるでしょうか?それでもディレクトリのサイズには偏りが生じてしまいます。探している人をもっと簡単に見つけられるようにする必要があるので、ハッシュコードをもう一度見直しましょう。

function stringToNumber(string) {
  let hashCode = 0;
  for (let i = 0; i < string.length; i++) {
    hashCode += string.charCodeAt(i);
  }

  return hashCode;
}

function hash(name, surname) {
  return stringToNumber(name) + stringToNumber(surname);
}

このテクニックでは、最初の文字だけを考慮するのではありません。代わりに、名前全体を数値に変換します。

名前全体をそのままハッシュコードとして保存すればいいのではないか、と思うかもしれません。それは事実です。そうすれば名前ごとに一意になりますが、ハッシュマップの文脈では、ハッシュコードは数値である必要があります。この数値が、キーと値のペアを保存するバケットへのインデックスとして機能することになります。バケットについては次のセクションで詳しく説明します。

バケット

バケットとは、要素を保存するために必要なストレージのことです。配列の各インデックスがそれぞれバケットを持っている、と考えることができます。特定のキーに対して、どのバケットに保存するかをハッシュ関数によって決定します。ハッシュ関数は、この特定のキーと値のペアを保存する配列のインデックスとして機能する数値を返します。ある人のフルネームを、キーを"Fred"、値を"Smith"として保存したいとしましょう:

  1. "Fred"をハッシュ関数に渡し、ハッシュコード385を得ます。
  2. インデックス385のバケットを見つけます。
  3. そのバケットにキーと値のペアを保存します。この場合、キーは"Fred"、値は"Smith"になります。

もし、インデックス385のバケットに、すでに同じキー"Fred"を持つ項目が入っていたらどうなるでしょうか?キーを比較して同じ項目かどうかを確認し、そうであれば値を新しい値で上書きします。これが、Setの中に一意な値しか持てない理由です。Setはハッシュマップに似ていますが、決定的な違い(key difference、キーにかけた言葉遊びです)は、Setのノードはキーだけを持ち、値を持たないという点です。

これはかなり単純化した説明です。内部の仕組みについては、このレッスンの後半でさらに詳しく説明します。

では、キーを使って値を取得したい場合はどうでしょうか:

  1. 値を取得するには、キーをハッシュ化し、そのバケットのインデックスを計算します。
  2. バケットが空でなければ、そのバケットに移動します。
  3. 次に、そのノードのキーが、取得に使ったキーと同じかどうかを比較します。
  4. 同じであれば、そのノードの値を返すことができます。そうでなければ、nullを返します。

もしかしたら、すでにバケットのインデックスがわかっているのに、なぜキーを比較する必要があるのか、と疑問に思うかもしれません。思い出してください、ハッシュコードは単なる場所にすぎません。異なるキーが同じハッシュコードを生成することがあります。バケットの中にある両方のキーを比較することで、キーが同じであることを確実に確認する必要があるのです。

以上です。これを作ることで、has、set、getを備えたハッシュマップができあがります。

挿入順序は保持されない

ハッシュマップは、反復処理(イテレート)を行うときに挿入順序を保証しません。ハッシュコードからインデックスへの変換は、最初のインデックスから最後のインデックスへと直線的に進んでいくわけではありません。むしろ、項目が挿入された順序とは関係なく、より予測不可能なものになります。つまり、キーと値の配列を取得して反復処理を行う場合、それらは挿入した順序どおりにはなっていない、ということです。

JavaScript自身のMapのように、挿入順序を考慮してハッシュマップを実装しているライブラリもあります。しかし、この後のプロジェクトでは、順序を保証しないハッシュマップを実装します。 例: Mao、Zach、Xariという値をこの順番で挿入した場合、イテレータを呼び出すと["Zach", "Mao", "Xari"]が返ってくるかもしれません。

ハッシュマップを頻繁に反復処理することが目的であれば、このデータ構造はその作業には適していません。シンプルな配列を使うほうが良いでしょう。

衝突

対処しなければならないもう一つの問題があります: 衝突(collision)です。衝突は、2つの異なるキーがまったく同じハッシュコードを生成したときに発生します。同じハッシュコードを持つため、それらは同じバケットに入ることになります。

例を挙げましょう: 名前"Sara"と名前"raSa"をハッシュ化すると、同じハッシュコードが生成されます。これは、両方の名前に含まれる文字が同じで、並び順が違うだけだからです。 アルゴリズムを使って、名前の中で文字がどこに現れるかに応じた一意なハッシュコードを得られるように、stringToNumber関数を見直すことができます。

function stringToNumber(string) {
  let hashCode = 0;

  const primeNumber = 31;
  for (let i = 0; i < string.length; i++) {
    hashCode = primeNumber * hashCode + string.charCodeAt(i);
  }

  return hashCode;
}

この新しい関数を使うと、名前"Sara"と"raSa"は異なるハッシュコードを持つようになります。これは、両方の名前が同じ文字を含んでいても、一部の文字が異なる位置に現れるためです。新しい繰り返しのたびに古いハッシュ値を掛け合わせ、その後に文字コードを足すようにしたことで、ハッシュコードが変化するようになったのです。

衝突を最小限に抑える

素数が使われていることに注目してください。好きな数を選ぶこともできましたが、素数のほうが望ましいのです。素数を掛けることで、ハッシュコードがバケットの長さで割り切れてしまう可能性が低くなり、衝突の発生を最小限に抑えるのに役立ちます。

"Sara"/"raSa"の衝突を避けるためにハッシュ関数を見直しましたが、それでも衝突が起こる可能性は常にあります。バケットの数は有限であるため、衝突を完全になくす方法はありません。できる限り衝突を減らすことを目指しましょう。

衝突への対処

ここまでのところ、私たちのハッシュマップは一次元のデータ構造です。もし、バケットの中の各Nodeが複数の値を保存できるとしたらどうでしょうか?ここで登場するのが連結リスト(Linked List)です。これからは、各バケットが連結リストになります。バケットに挿入する際、そのバケットが空であれば、連結リストの先頭ノードとして挿入します。バケットにすでに先頭ノードが存在する場合は、その連結リストをたどっていき、末尾に追加します。

ここまでで、できるだけ多くの衝突をなくすような、優れたハッシュ関数を書かなければならない理由が、おそらく理解できたのではないでしょうか。ほとんどの言語にはハッシュ関数が組み込まれているため、実際には自分でハッシュ関数を書くことはほとんどないでしょうが、ハッシュ関数がどのように機能するかを理解しておくことは重要です。

ハッシュマップの成長

バケットの数について話しましょう。私たちは無限のメモリを持っているわけではないので、バケットを無限に持つことはできません。どこかから始める必要がありますが、最初から大きくしすぎるのも、値を一つしか持たないハッシュマップにとってはメモリの無駄遣いになってしまいます。そこでこの問題に対処するために、バケット用の小さな配列から始めるべきです。ここではサイズ16の配列を使います。

配列の初期サイズを設定する

ほとんどのプログラミング言語では、デフォルトのサイズとして16から始めます。これは16が2の累乗であり、インデックスに対してビット演算を必要とするパフォーマンス向上のテクニックの一部に役立つからです。

衝突は避けたいものだということを思い出してください。理想的な世界では、各バケットにはノードが0個か1個しかない状態になります。そこで、ノードが同じバケットに積み重ならず、より広く分散する可能性を高めるために、バケット配列を大きくします。配列を大きくするには、サイズが2倍の新しい配列を作成し、既存のすべてのノードのキーを再度ハッシュ化しながら、この新しい配列のバケットにコピーしていきます。

バケット配列を大きくすべきタイミングはどうやってわかるのか?

これに対処するために、私たちのハッシュマップクラスは、capacity(容量)とload factor(負荷係数)という2つの新しいフィールドを管理する必要があります。

  • capacityは、現在保持しているバケットの総数です。

  • load factorは、ハッシュマップの作成時に設定する数値です。これは、バケット配列を大きくすべき適切なタイミングを決定する係数です。さまざまな言語のハッシュマップの実装では、0.75から1の間の負荷係数が使われています。

この2つの数値の積によって一つの数値が得られ、ハッシュマップ内のエントリ数がその数値を上回ったときに、大きくすべきタイミングだとわかります。例えば、バケットが16個あり、負荷係数が0.8だとすると、エントリ数が16 * 0.8 = 12.8を超えたとき、つまり13個目のエントリが追加されたときに、バケット配列を大きくする必要があります。この値を低く設定しすぎると、空のバケットが多くなりすぎてメモリを消費しすぎることになり、逆に高く設定しすぎると、配列のサイズを変更する前に多くの衝突が発生してしまいます。

計算量

ハッシュマップは、挿入・取得・削除の操作において非常に効率的です。これは、これらの操作に配列のインデックスを使っているためです。ハッシュマップは、以下のメソッドについて、平均的なケースでO(1)の計算量を持ちます:

  • 挿入
  • 取得
  • 削除

これは、優れたハッシュマップが書かれていることを前提としています。これらの操作の最悪のケースはO(n)になり、これはすべてのデータが、まったく同じ一つのバケットにハッシュ化されてしまった場合に起こります。この計算量そのものは連結リストによって生じるものであり、O(n)になるのは、同じバケットにさらに別のノードを挿入するために連結リストをたどる必要があるからで、これはまさに衝突が原因で起こります。

ハッシュマップの成長は、常にO(n)の計算量を持ちます。
