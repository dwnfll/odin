Revisiting Webpack

イントロダクション

Restaurant Pageに取り組んだ、よくできました!すべてのローダーとプラグインを使ってWebpackをセットアップして使うことは、面倒に感じたかもしれませんし、今でもそのすべてのポイントが何なのか疑問に思っているかもしれません。先に進んでいくにつれて、これらの多くはあなたにとってより自然なものになっていきますし、これらの基本的な概念が、まだ来ぬ問題に対処するのに役立つことを願っています!

Webpackを少しいじってみたところで、セットアップの体験と開発のワークフローを改善するのに役立ういくつかのことを見ていきましょう。これらのいくつかは、Webpackだけに限定されるものではなく、進んでいく中で他のツールでも使い続けられるものです。

レッスン概要

このセクションでは、このレッスンで学ぶトピックの概要を説明します。

  • npmスクリプトの書き方と実行方法。
  • Webpackのモードとは何で、必要に応じてモード間の切り替えを自動化する方法。
  • テンプレートリポジトリの作成方法と使い方。

npmスクリプト

npx webpackとnpx webpack serveは特に長いコマンドではありませんが、Restaurant Pageプロジェクトのデプロイ手順でgit subtree push --prefix dist origin gh-pagesに出会ったはずです。それを使う必要があるたびに毎回それを入力したいとは、きっと思わないでしょう。

幸いなことに、package.jsonファイルに、スクリプトのオブジェクトを含む"scripts"プロパティを追加することで、npmスクリプトを書くことができます。スクリプトは"name": "command"という形式で書くことができ、ターミナルでnpm run <name>を実行することで実行されます。例えば:

{
  // ... other package.json stuff
  "scripts": {
    "build": "webpack",
    "dev": "webpack serve",
    "deploy": "git subtree push --prefix dist origin gh-pages"
  },
  // ... other package.json stuff
}

ここには3つのnpmスクリプトがあります。この場合、npm run buildを実行するのはnpx webpackを実行するのと同じ(これは前のWebpackのレッスンのWebpackガイドで見たかもしれません)であり、npm run devはnpx webpack serveと同じで、npm run deployは私たちの代わりにgit subtree push --prefix dist origin gh-pagesを実行します。時間を節約できるだけでなく、コマンドに理にかなった、ある程度標準化された名前を付けられることも良い点です。npm run buildには、しばしばツールのビルド/バンドル/コンパイルのためのコマンドが含まれています。npm run devは、しばしば開発サーバーを起動するために使われます、などです。名前は常に同じとは限りませんが、npx webpackよりもその目的をよりよく説明してくれます。

webpackとwebpack serveコマンドをスクリプトとして設定する際、先頭のnpxを省いていることに注意してください。npmスクリプトなしでターミナルで直接それらを実行するためだけにnpxが必要だったからです。

Webpackのモード

ここまで、私たちは開発モードでWebpackを使い続けてきました。これは、開発作業をしているときに当然最も適しています。しかし、デプロイのためにプロジェクトをビルドする段階になると、専用のproductionモードが、私たちのためにいくつかの異なる最適化を行ってくれます。試してみましょう!Restaurant Pageプロジェクトに行き、webpack.config.jsでモードを"production"に変更してから、ビルドコマンドを再び実行してみてください。dist内のJavaScriptバンドルを見て、さらに壮大な文字のごちゃまぜを見てみてください!

私たちは、正確にどんな最適化が適用されたのかを知る本当の必要はありませんし、productionモードの他の詳細について知る必要もありませんが、この2つのモードが存在し、特定の目的のために設計されているということを知っておくのは良いことです。

distにバンドルする前や開発サーバーを再び使う前など、モードを切り替えたいたびに設定ファイルを手動で編集する手間を省くために、2つの異なる設定ファイル(例えばwebpack.dev.jsとwebpack.prod.js)を持ち、それからビルド用と開発用のnpmスクリプトに、どの設定ファイルを使うかを指定させることができます(--configオプションを省略すると、Webpackはデフォルトでwebpack.config.jsを探します):

"build": "webpack --config webpack.prod.js",
"dev": "webpack serve --config webpack.dev.js"

課題では、複数のWebpack設定ファイルを、重複を最小限にして扱いやすくしてくれる、webpack-mergeと呼ばれるツールを紹介します。このようにするのは良いことです。一度セットアップすれば、それぞれのスクリプトが適切な設定ファイルとモードを使ってくれるので、あとは忘れてしまって構いません!

テンプレートリポジトリ

すでに気づいたかもしれない一つのことは、Webpackのセットアップには複数のファイルとディレクトリ、そしてかなりの量の設定が関わってくるということです。Webpackで新しいプロジェクトをセットアップするたびに、以前設定したものを見て、再利用したい設定をコピー&ペーストする必要があるかもしれません。また、Githubで新しいリポジトリを作成するとき、上部近くにRepository templateのオプションがあることにも気づいたかもしれません。

これが、テンプレートリポジトリが本当に役立つ場面です。あなたの既存のリポジトリはどれでも、その設定でテンプレートに変換できます(リポジトリの名前を変更できる場所のすぐ下に、そのリポジトリがテンプレートかどうかのチェックボックスがあります)。このボックスにチェックを入れれば、おめでとうございます!それだけで十分です。今度、新しいリポジトリを作成するとき、Repository templateのドロップダウンに、選択できるテンプレートがリストされます。一つを選ぶと、新しいリポジトリは空っぽのものではなく、選んだテンプレートのコピーになります!

テンプレートに何が欲しいか、あるいは何が必要かを確実には分からないかもしれませんが、複数のプロジェクトで多くのセットアップコードを再利用していることに気づいたら、必要なすべてのセットアップコードを持つ新しいリポジトリを作成し、それをテンプレートとしてマークし、それから必要に応じて更新できます。これで、新しいプロジェクトのリポジトリを作成する際にそのテンプレートを選択して時間を節約し、プロジェクト自体の作業により早く飛び込めるようになります!

課題

  1. Webpackの「Production」ガイドを読んで、webpack-mergeの使い方と設定ファイルの分割方法を見ていきましょう。そのガイドで使われている正確なコード例は、彼らが持っているより長いチュートリアルの前の部分から続いていますが、webpack-mergeと設定ファイルの分割についての主な部分は、新しいプロジェクトでも十分に追っていけるはずですし、Restaurant Pageプロジェクトをこのやり方に変換してみることもできます!
    • 「Specify the Mode」のセクションとその例は無視して構いません。
