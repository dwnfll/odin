メモリについて話すとき、私たちが意味しているのは主記憶(primary memory)、つまりあなたのシステムがアルゴリズムを実行するために利用できる作業メモリのことです。このトピックについては、このGeeksforGeeksの主記憶についての記事でさらに読むことができます。

空間計算量とは何を意味するのか?

空間計算量は、入力のサイズに対する、アルゴリズムが使用する総スペースだと考えることができます。前のレッスンを振り返ってみると、私たちは、アルゴリズムが実行される一つの特定のインスタンスでどう動作するかで、そのアルゴリズムの効率性を考えるわけではないということを思い出すでしょう。その代わり、入力のサイズが変化したときに効率性がどう変化するかを知りたいのです。

空間計算量を測定する際は、あなたのアルゴリズムの入力と補助空間によって使われるスペースを考慮します。補助空間とは、アルゴリズムによって使われる余分なスペースです。これらは、アルゴリズムの実行中に作成される一時変数のようなものであり得ます。それらはメモリスペースに永続的な影響を与えることはありませんが、アルゴリズムの実行中は考慮する必要があります。したがって、空間計算量とは、私たちのアルゴリズムが必要とする作業メモリの総量だと考えることができます。

空間計算量を考慮することの重要性

もしあなた自身でアルゴリズムの効率性について何か調べたことがあれば、空間計算量はそれほど重要ではないと思い込んでしまっても無理はありません。このトピックについて読むほとんどの記事は、時間計算量を扱うことにすべて、あるいは大部分の時間を費やしており、もし空間計算量について言及するとしても、ほとんど脚注程度のものです。

また、あなたが書くほとんどのアルゴリズムは、おそらく非常に管理しやすい入力サイズを扱うことになり、そのためスペースが実際に問題になることはあまりない、と言うのも公平でしょう。メモリが使い果たされるという問題に遭遇する前に、プログラムが遅いという問題に必ず遭遇することになるでしょう。

一方で、あなたのハードウェアには通常、固定量のメモリしかありません。ほとんどの状況では、それをその場で簡単に拡張することはできません。問題が時間に関するものである場合、プログラムをより長く実行させ続けることができ、最終的には結果が返ってきます。しかし、スペースについてはこれができません。

全体的に見て、使用にかかる時間の方が使用するスペースよりも重要な問題に出会うことの方が多いでしょうが、空間計算量を測定することについて知っておけば、スペースの制約がある状況に実際に出会ったときに、それに対処する準備ができているということになります。

空間計算量を測定する

良い知らせは、私たちが空間計算量を測定する方法は、時間計算量とまったく同じだということです。前のレッスンですでにBig Oについて学んだので、すでにあなたのコードの効率性を測定する方法を知っています。違いは、時間ではなくメモリをアルゴリズムがどう利用しているかについて考える必要があるということです。

まず知っておくべきことは、時間計算量と同様に、定数を含むすべてのステップを考慮して空間計算量を測定し、それからBig O記法をアルゴリズムに適用する際にその定数を省く、ということです。ですので、入力が変化するにつれて線形計算量でメモリを使い、そうする中で3つの一時変数を作成するアルゴリズムがあるかもしれません。そのため、私たちのアルゴリズムの計算量は、メモリを使う3つの補助変数を持つO(N)だと考えることができます。それらの3つの変数は入力サイズに関係なく同じであるため、アルゴリズムの空間計算量を考える際には、それらを気にしません。ですので、空間計算量はO(N)だと言うことになります。これは、時間計算量のレッスンから馴染みがあるはずです。

念のため、最も一般的なBig O記法は次の通りです:

  • O(1) - 定数計算量
  • O(log N) - 対数計算量
  • O(N) - 線形計算量
  • O(N log N) - N x log Nの計算量
  • O(n²) - 二次計算量
  • O(n³) - 三次計算量
  • O(2ⁿ) - 指数計算量
  • O(N!) - 階乗計算量

いくつかの例を見ていきましょう。ほとんどのものは、あなたが馴染みがあり最もよく使うことになるデータ構造には当てはまらないため、あらゆる可能な計算量を扱うわけではありません。最も一般的なものをカバーしていきます。

O(1) - 定数計算量

この例を考えてみましょう

function multiply(num1, num2) {
  return num1 * num2;
}

ここでは、関数呼び出しに渡す引数が何であっても、単一の値(数値の積)だけが作成されるということが、うまくいけば明確なはずです。それは変わりません。したがって、これが取るスペースは常にO(1)だと考えることができます。

O(N) - 線形計算量

あなたが出会うほとんどのデータ構造は、O(N)の空間計算量を持ちます。それは理にかなっています - データ構造内のアイテム数を増やすと、そのデータ構造がメモリ内で占めるスペースは線形の方法で増加します。

function sumArr(arr) {
  const copyArr = arr.slice();
  let sum = 0;
  copyArr.forEach((number) => {
    sum += number;
  });
  return sum;
}

少し分かりやすくするために、これを通常JavaScriptで書くよりも少し冗長な方法で書きました。ここには配列を受け取るメソッドがあります。その中には、2つの変数があります。一つはsumと呼ばれ、もう一つは渡された配列のコピーを保持するcopyArrです。それから、配列を反復するforEachループがあります。このアルゴリズムが取るスペースの量は、それに渡される配列によります。配列の中に3つの要素があるかもしれませんし、300個あるかもしれません。配列の長さが分からないとき、私たちはそれをNと呼ぶので、sumと呼ばれるN + 1個の変数があることになります。Big Oでは定数を省くと知っているので、Nだけが残り、そのBig O記法はO(N)になります。

なぜ配列のコピーを作ったのでしょうか?それについては後のセクションで議論します。

この計算量は、どんなデータ構造でも再現されます:

function sumObjectValues(obj) {
  const copyObject = { ...obj };
  let sum = 0;
  Object.values(copyObject).forEach((value) => {
    sum += value
  });
  return sum;
}

ここでは、オブジェクトのサイズが増えるにつれて、それが使うスペースも線形の方法で増加します。

補助空間の分析

空間計算量を考える際に混乱を引き起こすよくある領域の一つは、アルゴリズムの文脈でスペースを使うとは何を構成するのかということです。先ほどの例では、配列とオブジェクトの引数を複製するメソッドを書きました。それは明示的にするためにそうしました。しかし、もしそのメソッドを次のように書いていたらどうでしょうか:

function sumArr(arr) {
  let sum = 0;
  arr.forEach((number) => {
    sum += number;
  });
  return sum;
}

データ構造が引数として渡されるとき、特に配列を値ではなく参照で渡す言語では、そのメソッドが空間計算量を計算する際にそのデータ構造が使うスペースを考慮しているのかどうか、少し不明確になることがあります。私たちは依然として、入力のサイズを考慮して、このアルゴリズムはO(N)のスペースを必要とすると言うこともできます。あるいは、入力配列の作成は、この関数を呼び出す前にそれを割り当てた、外部の何らかのルーチンに属すると言うこともできます。これは、他のすべての変数が定数であるため、このアルゴリズムがO(1)のスペースしか取らないということを意味します。この後者のアプローチは「補助空間分析」として知られています。

このアプローチを使うと、私たちはアルゴリズムが取る追加のスペースだけを考慮することになり、つまり入力は考慮に入れられません。これは、追加のスペースを異なる方法で使うアルゴリズムを説明する際に、状況によっては役立ちます。手早い例を見てみましょう:

function squareNumsInPlace(arr) {
  for (let i = 0; i < arr.length; i++) {
    arr[i] = arr[i] * arr[i];
  }

  return arr;
}

function squareNumsNewArr(arr) {
  // note that `Array.prototype.map()` makes a *new* array
  return arr.map((number) => number * number);
}

ここには、数値の配列を受け取り、それぞれの数値が二乗された配列を返す、2つの関数があります。1つ目の関数は入力配列を直接変更しますが、2つ目の関数は、それぞれの数値が二乗された新しい配列を構築します。従来の空間分析を使うと、どちらの関数もO(N)のスペースを取ることになります。しかし、この状況では、それはこれら2つのアルゴリズムがメモリをどう使うかの(非常に明確な)違いについて、あまり多くを教えてくれません。補助空間分析を使って、上の関数はO(1)の追加スペースを使い、下の関数はO(N)を使うと言う方が良いでしょう。

その他の計算量

私たちが述べてきたように、多くのデータ構造はO(N)の空間計算量を共有しているため、それと異なる空間計算量を持つアルゴリズムをたくさん書くことにはならないでしょう。

一部の再帰関数やソートアルゴリズムでは異なる空間計算量が見られますが、通常、それ以外のものを考慮する理由はあまりありません。

前のレッスンで、課題の一つはBig-Oチートシートへのリンクでした。今もう一度見てみると、それが空間・時間計算量のリファレンスとしていかに素晴らしいものであるかを、より深く理解できるかもしれません。下にスクロールしてデータ構造、それからソートアルゴリズムのセクションを見ると、時間と空間の計算量を教えてくれるのが分かります。特にデータ構造について、いかに多くがO(N)であるかに注目してください。多くのソートアルゴリズムは、O(1)の空間計算量しか持たないことに注意してください。これは、学習の過程でさまざまなソートアルゴリズムに出会う際に、心に留めておくべきことです。

これが、空間計算量について他のBig O記法の例に深く踏み込まない理由です。あなたが書くことになるほとんどのコードを代表しないような、込み入った例を考え出さなければならないでしょう。もしあなた自身のコードで良い実世界の例に出会ったら、ぜひ教えてください。他の人が考慮できるよう、ここに追加することを検討するかもしれません。

まとめ

時間であれ空間であれ、あなたのアルゴリズムの計算量を測定することは、難しいことがあります。それには練習と考慮が必要です。あなたが書くほとんどの練習コードでは、それは頭に浮かぶことではないでしょう。特に、コードを動かすことに苦労しているときはなおさらです。

しかし、あなたのコードが動作するようになり、リファクタリングしたいと思うようになったら、そのコードができる限り効率的かどうかを考えるために少し時間を取る価値は間違いなくあります。不要な変数を作成していませんか?あるいは、あなたのアルゴリズムは、それが主に使われる目的にとって、別のデータ構造よりも悪い時間計算量を持つデータ構造を使っていませんか?

これらの考慮事項に加えて、あなたのコードの読みやすさとのバランスも取る必要があります。もしあなたのコードをより効率的にするためにメモ化を導入し始めたら、それは理解するのがずっと難しくなることを意味するでしょうか?そのトレードオフは価値があるでしょうか?最終的には、あなたがそれについて判断を下す必要があります。私たちのアドバイスは、まず読みやすさを考慮し、パフォーマンスに明確な影響がある場合には、より良い効率性のためにリファクタリングすることを検討する、というものです。
