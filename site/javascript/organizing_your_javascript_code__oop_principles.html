OOP Principles

イントロダクション

この時点まで来て、あなたはJavaScriptで最も一般的なオブジェクトの作成・整理のパターンを学び、それを練習する機会を持ったはずです。しかし、それは氷山の一角に過ぎません。ファクトリー関数やモジュールの構文を学ぶことよりも重要なのは、それらを効果的に使う方法を見つけ出すことです。

この一連のレッスンはすべて、「オブジェクト指向プログラミング」パラダイム(OOP)についてのものでした。オブジェクトやクラスを作成する基本は比較的単純明快です。しかし、それぞれのオブジェクトに何を入れるべきか、いつ新しいオブジェクトを作るべきか、いつあるオブジェクトを別のオブジェクトから「継承」させるべきかを決めることは、単純明快ではありません。

幸いなことに、私たちのオブジェクトに関して良い決断を下す助けとなる、いくつかの概念や原則があります。このレッスンは、それらの概念のうち最も重要なものへの入門です。あなたのアプリケーション設計の質問に対する非常に明確な答えは、通常存在しないということを心に留めておいてください。一部のパターンやアイデアは明らかに他のものより優れていますが、特定の関数をどこに置くかを決める際には、しばしば何らかのトレードオフがあります。言い換えると…これらの原則はルールではなく、役立つガイドラインです。

これらのリソースを読んでいく中で、すでに終えたいくつかのプロジェクトに戻って、あなたが書いたものが目にする例とどう比較されるかを考えてみるのが役立つかもしれません。そしてもちろん、先に進んでいくにつれて、新しいプロジェクトを作る際にもこれらのことを心に留めておいてください。

レッスン概要

このセクションでは、このレッスンで学ぶトピックの概要を説明します。

  • 「単一責任の原則」を説明します。

  • なぜ一般的に継承よりコンポジションが好まれるのかを理解します。

単一責任

オブジェクトを作っていく中で、覚えておくべき最も重要なことの一つは、単一責任の原則です。これは、クラス(あるいはオブジェクトやモジュール…お分かりですね)は一つの責任だけを持つべきだと述べています。これは、あるオブジェクトが一つのことしかできないという意味ではありませんが、そのオブジェクトが行うすべてのことは、一つの責任の一部であるべきだという意味です。

本当によくある例をご紹介します。私たちのコードのほとんどは、アプリケーションロジックに加えて、DOMに何かを更新・書き込む関数を持っています。DOM関連のものをアプリケーションロジックから分離するのは、本当に良い考えです。

ここに、ゲームオーバーの条件が満たされたかどうかをチェックすべき関数があります。これには2つの問題があります:

function isGameOver() {

  // game over logic goes here!

  if (gameOver) {
    const gameOverDiv = document.createElement('div');
    gameOverDiv.classList.add('game-over');
    gameOverDiv.textContent = `${this.winner} won the game!`;
    document.body.appendChild(gameOverDiv);
  }
}

一つ目の問題は、この関数(そしてそれが含まれるモジュール)が、DOMを直接操作するものであるべきではないということです。すべてのDOM操作を独自のモジュールに抽出し、次のように使うべきです:

function isGameOver() {

  // game over logic goes here!

  if (gameOver){
    DOMStuff.gameOver(this.winner);
  }
}

残っている二つ目の問題は、isGameOver関数はgameOverの条件が満たされているかどうかをチェックすることだけに責任を持つべきだということです。isGameOverの戻り値に基づいて、DOMStuff.gameOver(this.winner)を呼び出すかどうかを決める責任は、ゲームループを処理する関数が持つべきです。

単一責任の原則についてのもう一つの考え方は、あるメソッド/クラス/コンポーネントは、変更すべき理由を一つだけ持つべきだというものです。そうでなければ、あるオブジェクトが複数の責任を持とうとすると、ある側面を変更することが別の側面に影響してしまうかもしれません。

単一責任の原則は、SOLID原則と呼ばれる、一般的によく見られる5つの設計原則のセットの最初のものです。これらの原則については、以下の課題の記事でさらに読むことになります。

疎結合なオブジェクト

当然ながら、私たちのすべてのオブジェクトは、一緒に働いて最終的なアプリケーションを形作ることを意図しています。しかし、あなたの個々のオブジェクトが可能な限り単独で成り立つように気を配るべきです。密結合なオブジェクトとは、互いに非常に強く依存しているため、一方を削除したり変更したりすると、もう一方を完全に変更しなければならなくなるオブジェクトのことです - これは本当にがっかりすることです。

これは「単一責任」とかなり強く関連していますが、異なる角度から見たものです。例えば、もしゲームを書いていて、ユーザーインターフェースの動作方法を完全に変更したい場合、ゲームロジックを完全に作り直すことなくそれができるべきです。ですので、主にconsole.log()を使ってゲームを書き始め、それから後で、ゲームロジックに触れることなくたくさんのDOM関数を追加できるべきです。
