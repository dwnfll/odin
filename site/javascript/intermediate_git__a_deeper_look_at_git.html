A Deeper Look at Git

日本語訳

← javascript

Beyond just `$ git add` and `$ git commit`...

イントロダクション

Gitは、趣味でやっているだけの人であれ、プロのウェブ開発者を目指している人であれ、身につけておくべき重要なスキルです。Gitは、いわば強化版の「保存」ボタンであり、シームレスな共同作業を可能にしてくれます。学ぶべきコマンドの数自体はそれほど多くありませんが、Gitの本当の難しさは、何が起こっているのかを頭の中でイメージすることにある場合がよくあります。

このレッスンでは、これまで主に使ってきたgit addやgit commit、git pushといったコマンドよりも一歩踏み込むことで、そのイメージを掴む手助けをしていきます。リモート、ポインタ、Gitの履歴を変更することといったトピックを扱います。これにより、Gitの内部で実際に何が起こっているのかについての理解が深まるはずです。

カリキュラムをこれ以上先に進める前に、この内容全体に目を通しておくことが非常に重要です。プロジェクトの作業はますます複雑になってきているため、規律あるGitワークフローを使うことはもはや任意ではありません。このレッスンを終える頃には、Gitの履歴を変更することにずっと慣れ、Git全体についてより深く理解できているはずです。

このセクションでは、このレッスンで学ぶトピックの概要を説明します。

履歴を変更する

さて、あなたはもう良いコミットメッセージを書くことに慣れていて、良いGitワークフローを実現するためにブランチを使いこなしているとしましょう。しかし、完璧な人などいません。美しいコードを書いている最中にも、何かがうまくいかなくなることがあります!早くコミットしすぎてファイルが漏れてしまうこともあるでしょう。コミットメッセージの一つを間違えて、重要な詳細を省いてしまうこともあるでしょう。

では、直近の履歴も、ずっと過去の履歴も、私たちのニーズに合わせて変更するいくつかの方法を見ていきましょう。以下のことを行う方法を扱います:

  • 直近のコミットを変更する
  • 複数のコミットメッセージを変更する
  • コミットの順序を入れ替える
  • 複数のコミットをスカッシュしてまとめる
  • コミットを分割する

準備をする

レッスンを始める前に、コードを安全に試しながら履歴を変更する操作を行えるような、Gitの練習場を作りましょう。GitHubにアクセスし、これまでと同じように新しいリポジトリを作成してください。名前は好きなものを付けてかまいません。そして、このリポジトリをローカルシステムにクローンしてください。それでは、今クローンしたリポジトリにcdで移動し、いくつか新しいファイルを作成しましょう!リポジトリの中に入ったら、以下のコマンド(タイプミスも含めて)をそのまま実行してください。何が起きているのか分からない部分があれば、調べてみてください。

touch test{1..4}.md
git add test1.md && git commit -m 'Create first file'
git add test2.md && git commit -m 'Create send file'
git add test3.md && git commit -m 'Create third file and create fourth file'

コードエディタを設定する

git commit --amendやgit rebase -iのように、テキストエディタを開く必要がある特定のGitコマンドを実行するには、コードエディタを正しく設定しておくことが重要です。デフォルトでは、Gitはコマンドラインインターフェース(CLI)の中でテキストエディタを開くため、変更を加えた後にエディタを保存して閉じることができない場合があります。

コードエディタを正しく設定するには、Git Basicsのレッスンに記載されている手順に従ってください。その手順を扱っている具体的なセクションはこちらです: Gitのコミットメッセージエディタを変更する。

直近のコミットを変更する

さて、私たちが最後に行ったコミットを見てみるとおっと!、git statusとgit logを入力すると、ファイルを一つ追加し忘れていたことがわかります!足りなかったファイルを追加して、git commit --amendを実行しましょう。

git add test4.md
git commit --amend

ここで何が起こったかというと、まず足りなかったファイルを含めるようにステージングエリアを更新し、それから足りなかったファイルを含む新しいコミットで、直近のコミットを置き換えました。もし望むなら、コミットのメッセージを変更することもでき、その場合は過去のコミットのメッセージが上書きされていたはずです。

まだどこにもプッシュしていないコミットに対してのみamendを行うことを忘れないでください!その理由は、git commit --amendは直近のコミットを編集するのではなく、そのコミットをまったく新しいコミットで置き換えるからです。つまり、他の開発者がそのコミットを基にして作業を進めている場合、そのコミットを壊してしまう可能性があるということです。履歴を書き換えるときは、必ず安全な方法で行い、同僚があなたが何をしているかを把握していることを確認してください。

複数のコミットを変更する

では、もっと過去の履歴にある、修正したいコミットがあるとしましょう。ここで登場するのが、美しいコマンドgit rebaseです!rebaseの複雑さについては、このレッスンの後半でさらに深く掘り下げますが、今のところは非常に基本的な使い方から始めていきましょう。

git rebase -iは、修正しようとしている各コミットの後でインタラクティブに停止し、望む変更を何でも加えられるようにしてくれるコマンドです。このコマンドには、編集したい最後のコミットがどれなのかを伝える必要があります。例えば、git rebase -i HEAD~2とすると、直近の2つのコミットを編集できます。実際にどのようなものか見てみましょう。以下を入力してください:

git log
git rebase -i HEAD~2

リベースを行うと、コミットはgit logで見るときとは逆の順序でリストされることに気づくはずです。少し時間を取って、このインタラクティブなツールが提供するすべてのオプションを見てみてください。それでは、ツールの一番上にあるコミットメッセージを見てみましょう。これらのコミットのうち一つを編集したい場合は、該当するコミットのpickという単語をeditに変更します。コミットを削除したい場合は、リストからそのコミットを取り除きます。順序を変更したい場合は、リスト内での位置を変更します。実際に編集がどのようなものか見てみましょう!

edit eacf39d Create send file
pick 92ad0af Create third file and create fourth file

これにより、Create send fileコミットのタイプミスをCreate second fileに編集できるようになります。あなたのインタラクティブなリベースツールでも同様の変更を行ってください。ただし、上記のコードをそのままコピー&ペーストしても動作しないので注意してください。エディタを保存して終了すると、以下の指示でコミットを編集できるようになります:

git commit --amend

上記のコマンドにより、コミットをamendできます。変更内容に満足したら、以下でリベースを完了できます:

git rebase --continue

それでは、git commit --amendと入力してコミットを編集し、タイトルのタイプミスを直してから、git rebase --continueと入力してリベースを終わらせましょう。これで完了です!git logと入力して、自分の成果と、変更された履歴を確認してみてください。簡単そうに見えますが、誤って使うと非常に危険なツールなので、注意してください。最も重要なのは、もし共有リポジトリでコミットをリベースしなければならない場合は、同僚が把握している非常に正当な理由があることを必ず確認してください。

コミットをスカッシュする

コミットに対してsquashを使うことは、複数のコミットを1つにまとめることで、Gitの履歴をよりすっきりと保つための、とても便利な方法です。このsquashのやり方を知っておくことは重要です。というのも、このプロセスが標準となっている開発チームもあるからです。スカッシュを行うと、他の人があなたのプロジェクトの履歴を理解しやすくなります。機能がマージされるときによく起こるのは、フィーチャーブランチがメインブランチに加えたすべての変更について、視覚的に複雑なログができあがってしまうことです。これらのコミットは、機能が開発中である間は重要ですが、メインブランチの履歴全体を見返すときには、実際にはそれほど必要ではありません。

リストの2番目のコミットを、1番目のコミットであるCreate first fileにsquashしたいとしましょう。まず、git rebase -i --rootと入力して、ルートコミットまで遡ってリベースしましょう。次に行うのは、2番目のコミットがsquashされる先となる1番目のコミットをpickすることです:

pick e30ff48 Create first file
squash 92aa6f3 Create second file
pick 05e5413 Create third file and create fourth file

エディタが開くと、スカッシュされるコミットのコミットメッセージが表示されます。コミットメッセージがCreate first and second fileだけを含むように編集し、それからエディタを保存して閉じ、スカッシュとリベースを完了させてください。これで完了です!git logを実行して、最初の2つのコミットがどのようにスカッシュされて1つになったかを確認してみましょう。

コミットを分割する

リモートについて深く掘り下げる前に、git resetという便利なGitコマンドを見ていきましょう。Create third file and create fourth fileというコミットを見てみましょう。今のところ、便宜上空のファイルを使っていますが、これらのファイルに何らかの機能が含まれていて、このコミットが一度に説明しようとしている内容が多すぎたとしましょう。その場合、再びインタラクティブなrebaseツールを使うことで、このコミットを2つの小さなコミットに分割することができます。

前回と同じようにツールを開き、分割しようとしているコミットのpickをeditに変更します。ただし今回は、代わりにgit reset HEAD~を実行します。これは、コミットをHEADの直前のものにリセットします。これにより、ファイルを個別に追加し、個別にコミットできるようになります。全体としては、次のようになります:

git reset HEAD~
git add test3.md && git commit -m 'Create third file'
git add test4.md && git commit -m 'Create fourth file'

ここで何が起こったのかを、もう少し詳しく見ていきましょう。git resetを実行すると、HEADをその直前のコミットに向けることで、現在のブランチをリセットします。同時に、git resetは、HEADが今指し示している場所の内容で、インデックス(ステージングエリア)も更新します。つまり、私たちのステージングエリアも、直前のコミットの時点の状態にリセットされたということです。これは好都合です。なぜなら、これにより両方のファイルを個別に追加し、個別にコミットできるようになったからです。

では、HEADが指し示す場所を移動させたいけれど、ステージングエリアには触れたくないとしましょう。インデックスをそのままにしておきたい場合は、git reset --softを使うことができます。これは、HEADが別の場所を指すように移動する、git resetの最初の部分だけを行います。

git reset --softは、より強力なamendのようなものだと考えることができます。直近のコミットを変更する代わりに、複数のコミット分さかのぼって、それらに含まれるすべての変更を1つのコミットにまとめることができます。

resetについて最後に触れておきたいのは、git reset --hardです。これが行うのは、HEADの移動とインデックスの更新というgit resetのすべてのステップに加えて、作業ディレクトリも更新するというものです。これは、データを破壊してしまう可能性があり危険なので、覚えておくべき重要な点です。ハードリセットは、HEADが最終的に指し示す場所のステージングエリアとまったく同じになるように、作業ディレクトリ内のファイルを上書きします。git commit --amendと同様、ハードリセットは履歴を上書きする破壊的なコマンドです。だからといって、他の開発者とチームで共有リポジトリを使って作業する際に、これを完全に避けるべきというわけではありません。しかし、自分がなぜそれを使っているのかを正確に把握し、同僚もあなたがどのように、そしてなぜそれを使っているのかを把握していることを、必ず確認してください。

ブランチはポインタである

このレッスンの焦点はGitの履歴を変更するためのより高度なツールでしたが、ここではさらに、人によっては理解しづらいかもしれないもう一つの高度なトピック、ポインタについて見ていきます。あなたはすでにRevisiting Rock Paper Scissorsのレッスンでブランチについて学んでおり、ブランチがファイルの複数のもう一つの現実バージョンをどのように保持しているかを学びました。今度は、それが内部では実際に何を意味しているのか、そしてブランチがポインタであるとはどういうことなのかについて説明していきます。

ブランチについて深く掘り下げる前に、コミットについて話しましょう。FoundationsのGit basicsのレッスンを思い出せば、コミットはスナップショットとして説明されていました。役に立つなら、これを非常に文字通りの意味で考えてみてください。git commitと入力するたびに、あなたのコンピュータはgit addでステージングされたすべてのファイルの内容の写真を撮っているのです。言い換えると、追跡されているワークスペース全体がコピーされるということです。

では、ブランチとは何なのでしょうか?これまで触れてきた内容から、ブランチをコミットの集まりとしてイメージしているかもしれません。しかし実際には、そうではないのです!ブランチとは、実際には単一のコミットを指すポインタなのです!これを聞くと、最初に「ブランチが単一のコミットを指す指にすぎないなら、そのコミットは、それより前にあったすべてのコミットについてどうやって知っているのか?」と思うかもしれません。この問いへの答えはとてもシンプルです: 各コミットもまた、その一つ前にあったコミットを指すポインタなのです!なんと。これは受け止めるのに少し時間がかかるかもしれないので、少し立ち止まって、この事実をじっくり考えてみましょう。

考えを整理し、この概念を理解しようとする時間が少し取れたところで、このレッスンで使ったポインタの具体例に立ち返ってみると理解の助けになるかもしれません。git rebase -i HEAD~2の使用を思い出してみましょう。覚えているかもしれませんが、このコマンドは直近の2つのコミットを編集できるようにしてくれます。Gitがどうやって編集すべき2つのコミットを知ったのか、見当がつきますか?そう、ポインタを使っているのです!私たちはHEADから始めます。HEADは、あなたが現在いるブランチを把握しておくための特別なポインタです。HEADは、現在のブランチの中で最も新しいコミットを指しています。そのコミットは、その直前に作られたコミット(これをコミット2と呼ぶことにします)を指しています。これが、git rebase -i HEAD~2がHEADポインタから始まり、それに続くポインタをたどることで、編集すべき2つのコミットを見つける仕組みです。

この時点で圧倒されているように感じているかもしれないので、これまで学んだことを振り返っておきましょう。ブランチとは、単一のコミットを指すポインタです。コミットとはスナップショットであり、履歴の中で直前にあるコミットを指すポインタでもあります。以上です!
