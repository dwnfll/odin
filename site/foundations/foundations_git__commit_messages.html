How and when to commit

イントロダクション

このレッスンでは、良いコミットメッセージの重要性、それらの書き方、いつコミットすべきか、そしてなぜ良いコミットの履歴を持つことがそれほど重要なのかを説明します!これを今学ぶのは、あなたがワークフローの一部としてGitを使う最初のプロジェクトを始めようとしているからです。

レッスン概要

このセクションでは、このレッスンで学ぶトピックの概要を説明します。

  • 意味のあるコミットメッセージの書き方。
  • なぜ意味のあるコミットメッセージが重要なのか。
  • いつコミットすべきか。

コミットメッセージは、それ専用のレッスンに値するほど重要なのか?

はい!その理由を簡単にリストアップしましょう:

  • 仕事に応募するとき、雇用主はあなたのGitHub上のプロジェクトに目を通し、コミット履歴を確認します。新人開発者として良いコミットを持っていることは、あなたを際立たせる助けになります。

  • 良いコミットメッセージの履歴があれば、あなた(やあなたのコードに取り組む他の開発者)は、どのような変更が、なぜ行われたのかをすぐに把握できます。これは、修正が必要なバグがコード内に見つかった場合に役立ちます!

  • 良いコミットメッセージの履歴は、しばらく離れていたプロジェクトに戻ってきたときにも役立ちます。最初にコードを書いたときの思考のプロセスや行った変更は、おそらく覚えていないでしょう。

悪いコミットと良いコミット

コミットを書くにあたっては、それらを効果的に書く方法を知ることが極めて重要です。悪いコミットメッセージの例を挙げてみましょう:

fix a bug

何をしたかは説明されていますが、このメッセージはあまりにも曖昧であり、チームの他の開発者を混乱させてしまいます。良いコミットメッセージは、あなたの変更の背後にある理由を説明します。言い換えると、コミットメッセージは、あなたの変更がどのような問題を、どのように解決するのかを説明するものです。

効果的なコミットは、サブジェクト(件名)とボディ(本文)という2つの別々の部分で構成されます:

サブジェクト(件名)

プロジェクトに加えた変更の簡潔な要約です。

This is the change I made to the codebase

コミットのサブジェクトの文字数制限

GitHubには72文字の制限があるため、コミットのサブジェクトはこの文字数以内に収めることをお勧めします。

ボディ(本文)

自分が行ったことについての、簡潔かつ明確な説明です。

Describe the problem your commit solves and how.

良いコミットメッセージを作る秘訣を学んだところで、先ほどのコミットメッセージを直してみましょう:

Add missing link and alt text to the company's logo

Screen readers won't read the images to users with disabilities without this information.

ああ、これでよくなりました!:) これで、開発者はこのコミットメッセージをより深く理解できるようになります。なぜなら、これは以下のことを行っているからです:

  • コードのアクションを明示するサブジェクト(件名)を提供している(例:「Add missing link and alt text to the company's logo」)。
  • なぜそのコミットが必要だったのかについて、簡潔かつ明確な説明を提供するボディ(本文)を含んでいる(例:「Screen readers won't read the images to users with disabilities without this information.」)。
  • サブジェクトとボディを、新しい行/空白行で区切っている。これは私たちが従うことを強くお勧めするベストプラクティスです。これにより、他の開発者にとってコミットメッセージが読みやすくなります。

開発者チームによっては、特定の形式でコミットメッセージの独自の慣習を持っていることもあります。しかし、それらも依然として、このレッスンで説明した原則に従っています。

サブジェクトとボディを含むメッセージでコミットする方法

これまでは、git commit -m <message>でコミットするよう指示されてきました。サブジェクトとボディを含むメッセージでコミットする最も簡単な方法は、-mフラグとメッセージ引数を付けずにgit commitと入力することです。

こうすることで、Visual Studio CodeをGitのエディタとして設定していれば、新しいVisual Studio Codeのタブが開きます。コメントを削除し、複数行のメッセージを入力できます。タブを保存して閉じると、コミットが作成されます。

いつコミットすべきか

コミットを捉える良い方法は、それが作られた瞬間のあなたのコードの「スナップショット」だと考えることです。その時点までのコードのバージョンが保存され、後で元に戻したり振り返ったりできるようになります。

コードを書くとき、コードに意味のある変更があるたびにコミットすることがベストプラクティスとされています。これにより、あなたの進捗のタイムラインが作られ、完成したコードが何もないところから突然現れたわけではないことが示されます。

言い換えると、取り組んでいるコードの一部を望み通りに機能させられたとき、タイプミスを直したとき、あるいはバグを直したときにコミットしてください。経験を積むにつれて、何をコミットすべきかについての感覚がより身についていきます!

プロジェクトに取り組んでいて、何かをようやく正しく動かせるようになる(これはコミットするのに良いタイミングです)ものの、その30秒後から数日後に、それが壊れてしまうという瞬間がやってきます。何を変更したのか見当もつかず、すべてが同じに見えるし、その行を編集した覚えもないのに、悲しいことに、もう望み通りには動かなくなっています。そんなとき、コミット履歴を遡って、その部分が最初に動くようになったときの最後のコミットにコードを戻すか、その時点でコードがどうなっていたかを確認できます。

覚えておくべきコツと注意点

  • テキストエディタとしてVSCodeを使用すること(Git Basicsのセクションですでに設定しているはずです)で、複数行のコミットメッセージを簡単に作成でき、各行の文字数を簡単に確認でき、またVSCodeのスペルチェック拡張機能を使ってスペルが正しいことを確認できるようになります。
  • 能動態を使いましょう: 「Fix card generator」。
  • 「saved」や「updated」のような曖昧なコミットメッセージは避けましょう。
  • 早めに、こまめにコミットしましょう!
