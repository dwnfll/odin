イントロダクション

DOMを操作できるようになったところで、Rock Paper Scissorsを再び訪れ、UIを追加する時が来ました。

Rock Paper Scissorsプロジェクトに変更を加え始める前に、現在あるものを壊してしまう心配をせずに変更を加えられるように、Gitのブランチという概念について学ぶ必要があります。

Gitのブランチを使うと、リポジトリはあなたのファイルの複数の別世界バージョンを同時に保持できます。実は、最初のコミットをした時からあなたは(ある意味)すでにブランチを使っていたのです。ただ知らなかっただけかもしれませんでgit config --global init.defaultBranch mainを実行したとき、あなたはリポジトリのデフォルトブランチと呼ばれるものの名前を設定していました。デフォルトブランチとは、プロジェクトで最初のコミットを行ったときに作成されるブランチを指す呼び方であり、あのコマンドでは、現在の標準であるmainという名前を設定していました。

木の枝のように(それがこの名前の由来です)、プロジェクトのすべてのブランチは「幹」(mainブランチ)から、あるいは他のブランチから枝分かれしています。

特定のブランチでコミットを行うと、その変更はそのブランチにのみ存在し、他のすべてのブランチは、そこから分岐した時点のままの状態で残ります。

つまり、mainブランチを、正しく動作すると分かっている完成した機能だけを置く場所として保っておき、フィーチャーブランチと呼ぶ専用のブランチを使って、それぞれの機能をプロジェクトに追加できるということです。

レッスン概要

このセクションでは、このレッスンで学ぶトピックの概要を説明します。

  • 新しいブランチを作成する方法。
  • ブランチをマージする方法。
  • ブランチのベストプラクティスとユースケース。

ブランチを使う

git branch <branch_name>というコマンドを使って新しいブランチを作成できます。それからgit checkout <branch_name>を使って新しいブランチに切り替えることができます。また、checkoutに-bフラグを付けて、git checkout -b <branch_name>という形式で、新しいブランチを作成して切り替えることを1つのコマンドで行うこともできます。

他の引数なしでgit branchを使うと、現在のすべてのブランチを確認できます。現在いるブランチにはアスタリスクが付いて示されます。他のブランチからmainに戻りたい場合は、git checkout mainを使って他のブランチに切り替えるのとまったく同じように行えます。

フィーチャーブランチでの作業が終わり、そこで行ったコミットをmainブランチに持っていく準備ができたら、merge(マージ)として知られる操作を行う必要があります。

マージはgit merge <branch_name>というコマンドを使って行われ、これはbranch_nameでコミットした変更を取り、現在いるブランチに追加します。以下の図で、developブランチが作成され、コミットされ、それからmainにマージされる例を見ることができます。


---

---
gitGraph
   commit id: "commit1"
   commit id: "commit2"
   branch develop
   checkout develop
   commit id: "commit1a"
   commit id: "commit2a"
   checkout main
   merge develop id: "merge to main"

時には、ファイル内の同じ行が2つの異なるブランチによって変更されていることがあります。これが起きると、それらのブランチを一緒にマージしようとしたときにマージコンフリクト(競合)が発生します。ブランチのマージを完了するには、まずそのコンフリクトを解決する必要があり、これは今後のレッスンで扱います。

ブランチがもう不要になったら、そのブランチがすでにmainにマージされている場合はgit branch -d <branch_name>を使って、まだマージされていない場合はgit branch -D <branch_name>を使って削除できます。通常、ブランチが不要になったら削除したくなるでしょう。そうしないと、ブランチが積み重なってしまい、必要なときに探しているブランチを見つけるのが難しくなってしまいます。

コードを共有する

ブランチのもう一つの素晴らしいユースケースは、mainブランチ(やフィーチャーブランチ)にはまったくコミットしたくないかもしれないコードを、他の人と共有することです。

例えば、取り組んでいる新しい機能に、原因が分からないバグがあり、それによってコードが壊れてしまう場合、その壊れたコードをコミットしてプロジェクトの「永続的な記録」に残したくはないでしょう。代わりに、新しい一時的なブランチを作成し、そこに切り替えて、そのコードを新しいブランチにコミットできます。それから、この新しい一時的なブランチをGitHubにプッシュすれば、問題の解決を手伝ってくれるかもしれない他の人と共有できます。以下の課題では、新しいブランチを作る実践的な練習ができます。

課題

ウォームアップ

  1. まずは少しブランチの練習をしましょう。Peter CottleによるこのインタラクティブなGitブランチ可視化ツールは見事なものです。「Introduction Sequence」のレベル1〜3だけを完了してください。

Rock Paper ScissorsにUIを追加する

  1. 以前のRock Paper Scissorsリポジトリに新しいブランチをセットアップしてください。

    1. Rock Paper ScissorsゲームのUIを作ることになるので、git checkout -b rps-uiというコマンドで新しいブランチを作成し、それに切り替えてください。

    2. これで、あなたはローカルでrps-uiブランチで作業しています。しかし、このブランチはまだリモートリポジトリには存在していません。GitHubのリポジトリページに行くと、ブランチが1つ、つまりmainしかないことが分かるでしょう。git push origin rps-uiというコマンドで、この新しいブランチをリモートリポジトリにプッシュしましょう。これで、あなたのGitHubリポジトリに2つのブランチが表示されるようになります!以下のスクリーンショットに示されているドロップダウンのブランチセレクタを使って、GitHub上で新しいブランチを選択できます。

    3. rps-uiブランチにいることを確認してください。これはgit branchコマンドで確認できます。現在いるブランチには、隣に(*)アスタリスクが付きます。何らかの理由で別のブランチにいる場合は、git checkout rps-uiというコマンドでrps-uiに切り替えてください。これで新しい機能に取り組む準備が整いました!注:mainブランチと同じように、このブランチにファイルを追加したり、コミットしたり、リポジトリに変更をプッシュしたりできます。変更をプッシュする際に、新しいブランチにプッシュしているためgit push origin mainの代わりにgit push origin rps-uiを使う点を除いて、すべて同じです。

    4. 私たちのUIでは、プレイヤーはプロンプトに答えを入力するのではなく、ボタンをクリックしてゲームをプレイできるようにするべきです。
    5. 今のところ、ちょうど5ラウンドをプレイするロジックは削除してください。
    6. それぞれの選択肢用に、3つのボタンを作成してください。ボタンがクリックされるたびに、正しいplayerSelectionでplayRound関数を呼び出すイベントリスナーをボタンに追加してください。(このステップではconsole.logを残しておいて構いません)
    7. 結果を表示するためのdivを追加し、すべてのconsole.logをDOMメソッドに変更してください。
    8. 現在のスコアを表示し、どちらかのプレイヤーが5ポイントに達したらゲームの勝者を発表してください。
    9. これを機能させるために、おそらく元のコードをリファクタリング(作り直し/書き直し)する必要があるでしょう。それで構いません!古いコードを作り直すことは、プログラマーの人生の重要な一部です。
    10. UIがすべて完成し、すべてが満足のいくものであることを確認したら、先に進む前にgit statusですべての変更がrps-uiブランチにコミットされていることを確認してください。
    11. さて、rps-uiブランチの変更をmainブランチにマージする方法を見てみましょう。
    12. git checkout mainというコマンドで、マージ「先」のブランチ、つまりmainにチェックアウトしてください。
    13. では、git merge rps-uiで、現在のブランチであるmainにrps-uiブランチをマージしましょう。
    14. すべてがうまくいけば、rps-uiブランチはこれでmainに正常にマージされました!git logを使うと、mainブランチに行ったコミットの上に、フィーチャーブランチに行ったすべてのコミットが表示されるでしょう。さあ最後のステップです!
    15. git push origin mainを実行して、mainブランチをリモートリポジトリにプッシュしましょう。GitHubのリポジトリに行くと、あなたのmainブランチにrps-uiブランチで行ったすべての変更とコミットが反映されていることが分かるでしょう。おめでとうございます!最初の機能をプロダクションブランチに正常にプッシュできました!
    16. これで私たちのコードはすべてmainブランチにあるので、rps-uiブランチはもう本当に必要ありません。ローカルとリモートリポジトリの両方で、少し片付けをしましょう。git branch -d rps-uiでローカルリポジトリからブランチを削除し、git push origin --delete rps-uiでGitHub上のリモートリポジトリからも削除してください。おめでとうございます、片付けはこれですべて終わりです!
    17. プロジェクトをGitHub Pagesで必ず公開し、プロジェクトのレッスンにライブプレビューのリンクを追加してください。
