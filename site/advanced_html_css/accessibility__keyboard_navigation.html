Keyboard Navigation

Learn how to ensure all users are able to access your site using only a keyboard.

イントロダクション

一部のユーザーは、コンピューター、ひいては訪問するウェブサイトをナビゲート・操作するためにマウスを使うことができません。これらのユーザーは代わりに、キーボードや、音声認識ソフトウェアのようなキーボード入力をシミュレートできる別の支援技術に頼ることがあります。他のユーザーは、マウスよりもキーボードを使う方を単に好むかもしれませんし、両方を組み合わせて使うかもしれません。これらのユーザーには適切なキーボードナビゲーションが必要であり、これはウェブサイトを開発する際に見落とされがちなことの一つです。

レッスン概要

このセクションでは、このレッスンで学ぶトピックの概要を説明します。

  • キーボードユーザーのために、インタラクティブな要素が持っていなければならない2つのことを知ります。
  • フォーカススタイルとは何か、そしてなぜそれを完全に取り除くべきではないかを理解します。
  • タブオーダーとは何かを理解します。
  • 隠されたコンテンツを支援技術から適切に隠す方法を知ります。

フォーカス

セマンティックHTMLのレッスンで出てきた、セマンティックHTMLを使わなかったRock, Paper, Scissorsの例を覚えていますか?<div>や<span>要素を使うことのもう一つの問題は、デフォルトではフォーカス可能ではなく、デフォルトでは何のイベントハンドリングも持たないということです。私たちの非セマンティックなRock, Paper, Scissorsの例をキーボードユーザーのために修正するには、以下のコードの断片のような、いくつかの追加のステップを踏む必要があります:

<!-- The `tabindex` attribute makes the `<div>` elements focusable. -->
<div class='button-container'>
  <div class='rock button' tabindex='0'>Rock</div>
  <div class='paper button' tabindex='0'>Paper</div>
  <div class='scissors button' tabindex='0'>Scissors</div>
</div>
// We also need to manually add in event handling for both mouse and keyboard events.
const buttons = document.querySelectorAll('.button');

function nameAlerter(e) {
  if (e.type === 'click' || e.key === ' ' || e.key === 'Enter') {
    alert(e.target.textContent);
  }
}

buttons.forEach(button => {
  button.addEventListener('click', nameAlerter)
  button.addEventListener('keydown', nameAlerter)
})

もちろん、この例はスクリーンリーダーのユーザーにとってより理解しづらいものにしてしまいます(覚えていますか、これらの「ボタン」はコンテキストを何も提供してくれません)。<button>要素を使うことは、スクリーンリーダーのユーザーが必要とするコンテキストを提供するだけでなく、デフォルトでフォーカス可能でキーボードのイベントハンドリングも持っています: <button>がフォーカスを持っているときにキーボードでSpaceキーやEnterキーを押すと、「click」イベントがトリガーされます。

ポイントは、あらゆるインタラクティブな要素がキーボードによってフォーカス可能であり、キーボードのイベントハンドリングを持っていることを確実にする必要がある、ということです。正しいセマンティックHTMLを使うことで、この目標を達成するのがずっと簡単になりますが、もしデフォルトではフォーカス可能でない、あるいは何のイベントハンドリングも持たない要素を使う必要がある場合は、その両方の機能を手動で追加する必要があります。

フォーカススタイル

フォーカス可能な要素のもう一つの側面は、そのフォーカススタイルです。これは通常、要素がフォーカスを受け取ったときにそれを囲むアウトラインや枠線です。あなたがやったことがあるかもしれない、あるいは今もやっているかもしれないことの一つは、以下の例のようなCSSルールを使って、これらのフォーカススタイルを完全に取り除くことです:

/* These are so ugh-ly! Let's get rid of them. */
*:focus {
  outline: none;
  border: none;
}

おそらくあなたは、これをしないようにと言われることを予想しているでしょう。ええ…フォーカススタイルを完全に取り除くべきでは決してありません。これらのデフォルトのフォーカススタイルをそのままにしておくか、自分自身のフォーカススタイルに置き換えるべきです。ボタンにtransform: scale()というCSSプロパティを追加するにしても、リンクにアウトラインを追加するにしても、inputの枠線の幅と不透明度を増やすにしても、自分自身のフォーカススタイルを追加することが、デフォルトのフォーカススタイルに対して検討すべき唯一の代替策です。

なぜでしょうか?フォーカススタイルを完全に取り除いてしまうと、キーボードユーザーは実際にどの要素がフォーカスを持っているかについて視覚的な手がかりを一切得られなくなるため、ページをナビゲート・操作することが不可能になってしまう可能性があります。これは、彼らに、Tabキーを何回押したかを手動で追跡し続けながら、どの要素が実際にフォーカス可能なのかを推測させることを強いてしまいます。見えないカーソルで、しかもリンクやボタンのようなインタラクティブな要素の上にカーソルがホバーしているときの視覚的な手がかりが一切ない状態で、ウェブサイトを閲覧しようとすることを想像してみてください。あまり楽しそうには聞こえませんよね?

タブオーダー

タブオーダーとは、Tabキーを押したときにページ上の要素がフォーカスを受け取る順序のことで、デフォルトではHTMLファイル内にリストされている要素の順序と同じです:

<!-- This element is first in the tab order. -->
<div tabindex='0'>This is the first element listed in the HTML.</div>

<!-- This element is second in the tab order. -->
<div tabindex='0'>This is the second element listed in the HTML.</div>

時には、CSS(例えばfloatやorderプロパティ)を使ってページ上の要素の視覚的な順序を変える必要があると感じたり、tabindex属性を使って要素自体のタブオーダーを変える必要があると感じたりするかもしれません。どちらの方法を使うにしても、タブオーダーが要素の視覚的な順序と一致していることを確認すべきです。もしタブオーダーが視覚的な順序と異なると、ユーザーはキーボードでページをナビゲートしようとする際に、視覚的なレイアウトに基づいてある要素がフォーカスを受け取ることを期待しているのに、代わりに別の要素がフォーカスを受け取ってしまい、混乱したり苛立ったりしてしまう可能性があります。

この問題を避ける最良の方法は、HTMLファイル内で、実際にフォーカスを受け取ってほしい順序で要素を配置することです。

隠されたコンテンツ

時には、ユーザーがメニューやモーダルボックスを開くためにボタンをクリックするといった特定のイベントが発生するまで、一部のコンテンツを隠しておきたい場合があります。このような目的でコンテンツを隠したい場合は、そのコンテンツが視覚的に隠されているだけでなく、そのコンテンツが表示されるべきときまで、支援技術からも隠されていることを確実にする必要があります。

そのようなコンテンツを適切に隠さないと、キーボードユーザーは、本来意図されたタイミングより前にそのコンテンツにタブで入り込めてしまいますが、そうすることでページ上の視覚的なフォーカスを見失ってしまいます。これらのユーザーは、ページをタブで移動しようとしているだけなのに、フォーカスインジケーターがその隠されたコンテンツの中に消えてしまい、混乱したり、苛立ったりすることさえあるでしょう。

このイライラする振る舞いを防ぐ一つの方法は、その隠されたコンテンツ内の個々のアイテムそれぞれにtabindexの値として-1を与えることです。これにより、要素がキーボードを通してフォーカスを受け取ることを防げます(ただし、JavaScriptのfocus()メソッドを使ってフォーカスを与えることは依然としてできます)。これはキーボードユーザーにとっての問題を修正しますが、他の支援技術は依然としてこの隠されたコンテンツにアクセスでき、それをアナウンスできてしまいます。

より良い解決策は、隠されたコンテンツのコンテナ自体に、隠されているときはdisplay: noneまたはvisibility: hiddenというCSSプロパティを与え、表示されるべきときにそのプロパティを削除するか上書きすることです。これにより、メニューアイテムをタブオーダーから取り除くだけでなく、支援技術がそれらをアナウンスするのを防ぐこともできます。

課題

  1. What is Focus?を見て、タブオーダーを変えようとするときに発生するいくつかの問題を確認し、それからtabindexを使ってフォーカスをコントロールするを見て、tabindex属性を使うことがタブオーダーにどう影響し得るか見てみてください。
  2. キーボードユーザーのためのもう一つの形式のアクセシビリティであるスキップリンクについて読んでください。これは、ページのコンテンツをタブで移動するのにより多くの労力を必要とするユーザーにとって、特に役立ちます。
