WAI-ARIAとは何か?

WAI-ARIAは-一息ついてください-Web Accessibility InitiativeのAccessible Rich Internet Applications仕様の略です。WAI-ARIA(しばしば単にARIAと呼ばれます)の目的は、ネイティブのHTMLではできない場合に、ウェブコンテンツをよりアクセシブルにする方法を定義することです。ARIAを、ネイティブHTMLが残したアクセシビリティの隙間を埋めてくれるものだと考えてください。

ARIAは要素のセマンティクスやコンテキストしか変更できないということに注意することが重要です。ARIAには次のことができません:

  • 要素の見た目を変更すること
  • 要素の振る舞いを変更すること
  • フォーカス可能性を追加すること
  • キーボードのイベントハンドリングを追加すること

ARIAを使うときは、通常、不足しているセマンティクスや機能を追加するために、追加のステップを踏む必要があります。Keyboard Navigationのレッスンで、<div>の「ボタン」に機能を追加しなければならなかったことを覚えていますか?

ARIAの5つのルール

ARIAは正しく使われれば非常に強力になり得ますが、間違って使われれば同じくらい危険にもなり得ます。このため、たとえ最善の意図を持っていたとしても、悪いARIAよりはARIAがない方がましであるということを心に留めておくべきです。WCAGには「ARIAの5つのルール」と呼ばれるものがあり、これはご想像の通り、ARIAを使う際に従うべきルールです。以下で言及されているすべての用語を扱うわけではありませんが、それでもルール自体を理解しておくことは重要です。特に、自分自身でさらにARIAを深く掘り下げていくことに決めた場合はなおさらです。

  1. 可能な場合は、ARIAよりも常にネイティブのHTML要素や属性を使ってください。
  2. 他に選択肢がない場合を除いて、ネイティブのセマンティクスを決して変更しないでください。
  3. すべてのインタラクティブなARIAコントロールは、キーボードで使用可能でなければなりません。
  4. フォーカス可能な要素にrole="presentation"やaria-hidden="true"を決して使わないでください。
  5. すべてのインタラクティブな要素は、アクセシブルな名前を持たなければなりません。

アクセシビリティツリー

私たちが利用できるARIA属性のいくつかに入っていく前に、アクセシビリティツリーとは何かの基本を知っておくことが重要です。それが、これらの属性が実際に何をしているのかを理解するのに役立つからです。

アクセシビリティツリーはDOMに基づいており、これは今のあなたにとってかなり馴染みがあるはずのものです。DOMがウェブページを構成するノードやオブジェクトを表しているのに対し、アクセシビリティツリーには、支援技術によって使われるアクセシビリティ関連の情報だけが含まれています。ARIAの機能の仕方は、このアクセシビリティツリーを構成するオブジェクトのプロパティを変更することによるものです。このレッスンでは、これらのプロパティのうち2つだけに焦点を当てていきます:

  • Name: 「アクセシブルな名前」としても知られ、これは支援技術がユーザーにアナウンスするものであり、同じタイプの要素を互いに区別するものです。名前は、要素のテキストコンテンツ、<label>要素、alt属性など、一つ以上のネイティブなラベルによって設定される場合があります。
  • Description: これは、支援技術がアクセシブルな名前に加えてアナウンスするものです。

ARIAラベル

ARIAラベルは、ネイティブなラベルを上書きしたり、追加の説明的なテキストを提供したりすることで、支援技術のユーザーがウェブページ上のコンテンツをよりよく理解する助けとなります。<label>要素とは異なり、ARIAラベルは限られた一部の要素だけに使用が制限されているわけではありませんが、それでも独自の制限があります。

カリキュラムの前の方で、id属性を使うことについて注意されたのを覚えているかもしれません。簡単に振り返ると、通常はid属性を使いすぎたり、必要でないときにさえ使ったりすることは避けたいところです(そして実際、必要でないことの方が多く、クラスを使い続けるべきです)。しかし、実は別の要素にidを持たせることを要求するARIA属性がいくつかあります。

そのようなARIA属性を使うときは、ある要素にidを与え、それからそのidの値を別の要素のARIA属性の値として渡します。これにより、<label>要素のfor属性がinputのidへのリンクを作るのと似たような形で、要素間にリンクが作られます。以下で言及する3種類のARIAラベルのうち、aria-labelledbyとaria-describedbyは、別の要素にidを持たせることを要求するARIA属性です。

aria-label

aria-label属性は、要素のネイティブなラベルを上書きし、アクセシビリティツリー内のそのnameプロパティを変更します。これは、要素がすでにネイティブなラベルを持っていない場合に最もよく使われます。追加されると、aria-label属性の文字列値がその要素のアクセシブルな名前になります。しかし、aria-labelは一部のHTML要素には何の効果も持ちません。<div>や<span>などです。

aria-labelの一般的な使用例は、メニューやモーダルの「閉じる」ボタンに見られます:

<button type="button" aria-label="Close menu">X</button>

スクリーンリーダーがユーザーにとってほとんど意味をなさない「X, button」とアナウンスする代わりに、「Close menu, button」とアナウンスすることになります。aria-labelを使えるもう一つの方法は、ランドマーク要素に対してです(Semantic HTMLのレッスンがまた出てきましたね…また!):

<nav aria-label="main navigation">...</nav>

スクリーンリーダーが上記のHTMLに到達すると、「Main navigation, navigation landmark」とアナウンスします。もしページに複数のnavigation要素があれば、それぞれに異なるaria-labelの値を与えることで、互いを区別し、スクリーンリーダーのユーザーにとってより理解しやすくすることができます。かなり素敵ですよね?

ある単語がどう発音されてアナウンスされるかを変えるためにaria-labelを使うのはやめてください。特定の単語は、スクリーンリーダーによって正しくアナウンスされないことがあり、これを修正しようとしたくなるかもしれません。ある単語がスクリーンリーダーによってどうアナウンスされるかを修正できたとしても、その「修正」が、点字リーダーのような他の支援技術によってアナウンスされたときには意味をなさなくなってしまう可能性があります。

aria-labelledby

aria-labelledby属性は、ネイティブなラベルとaria-label属性の両方を上書きします。aria-labelledbyを使うと、対象の要素のアクセシブルな名前は、idが参照されている要素のテキストコンテンツやalt属性を連結することで作られます。

aria-labelledbyの素晴らしいところは、いくつでもidの参照を渡せるだけでなく、要素自身を参照させることもできるということです。同じ参照を複数回渡すことはできないことに注意してください。なぜなら、最初の後に続く参照はすべて無視されるからです。

<!-- Here's the labeling element -->
<h2 id="label">Shirts</h2>

<!-- And here's the labeled element. Note the order of the ID references passed in -->
<button type="button" id="shop-btn" aria-labelledby="label shop-btn">Shop Now</button>

上記のHTMLは、スクリーンリーダーによって「Shirts, shop now, button」とアナウンスされます。これにより、ページ上の複数の「shop now」ボタンを互いに区別できるようになり、追加のコンテキストを提供して、ページをより理解しやすくすることができます。

aria-labelledbyのもう一つの素晴らしいところは、ラベル付けする要素がhidden HTML属性やCSSによって視覚的に隠されていたとしても、ラベル付けされる要素のアクセシブルな名前を変更し続けるということです。これは、支援技術のユーザーのために要素にラベルを付けたいが、そのラベル(または複数のラベル)を目の見えるユーザーには見えないようにしたい場合に役立ちます。

ネイティブの<label>要素と多少似たような働き方をするかもしれませんが、aria-labelledbyはデフォルトでは同じイベントハンドリングを持っていません。これは、あなた自身がJavaScriptで追加する必要のある機能です。

<!-- Clicking the <label> element gives focus to the input element -->
<label for="name">Name:</label>
<input id="name" type="text">

<!-- Clicking the <div> element won't give focus to the input element -->
<div id="label">Name:</div>
<input type="text" aria-labelledby="label">

aria-describedby

aria-describedby属性は、アクセシビリティツリー内のdescriptionプロパティを変更します。aria-labelledby属性と同様に、この属性を使うときは、他の要素のidの値をaria-describedbyの値として渡し、そのidの値が渡された要素も視覚的に隠すことができます。

<label>
  Password:
  <input type="password" aria-describedby="password-requirements">
</label>

<!-- Meaningful text + ARIA! -->
<span id="password-requirements">Password must be at least 10 characters long.</span>

<input>要素がフォーカスを受け取ると、スクリーンリーダーは「Password, edit protected, password must be at least ten characters long.」とアナウンスします。これにより、inputがフォーカスを受け取るたびに、選びたいパスワードに関する要件を、スクリーンリーダーのユーザーにすぐに知らせることができます。

アクセシビリティツリーからコンテンツを隠す

hidden HTML属性やdisplay・visibility CSSプロパティを使って要素を視覚的に隠せるのと同様に、aria-hidden属性を使って、装飾的な画像やアイコンなどの特定の要素をアクセシビリティツリーから隠すことができます。しかし、aria-hiddenとの違いは、その要素が目の見えるユーザーには見えたままになるということです。これは、ある要素の中にアイコンを追加したい場合に特に役立ちます。例えば、ボタンの中でMaterial Iconsを使うとしたら:

<!-- Example 1 -->
<button type="button">
  <span class="material-icons">add</span>
  Add Book
</button>

<!-- Example 2 -->
<button type="button">
  <span class="material-icons" aria-hidden="true">add</span>
  Add Book
</button>

上記の両方の例は視覚的には同じに見えますが、例1のボタンはスクリーンリーダーによって「Add add book, button」とアナウンスされます。<span>のテキストコンテンツとボタン自体のテキストコンテンツが連結されて、ボタンのアクセシブルな名前になります。しかし、例2のボタンは<span>をアクセシビリティツリーから隠しているため、そのテキストコンテンツはボタンのアクセシブルな名前に追加されず、つまりスクリーンリーダーは正しく「Add book, button」とアナウンスすることになります。

しかし、この属性を使う際には注意してください。ある要素にaria-hidden="true"を与えると、その要素のすべての子要素もアクセシビリティツリーから隠されることになります。親のいずれかがまだaria-hidden="true"を持っている場合、子要素にaria-hidden="false"を追加しても何の効果もありません。

また、フォーカス可能な要素にaria-hidden="true"を与えないよう注意すべきです。そうしてしまうと、その要素がフォーカスを受け取ったときに何もアナウンスされなくなり、スクリーンリーダーを使いキーボードでページをナビゲートするユーザーを混乱させてしまいます。

課題

  1. W3の「ARIA in HTML」のセクション1から5を読んでください。これは非常に徹底したドキュメントですが、いつも通り、何かを暗記することは期待されていません。内容の要点をつかむだけで十分です。後のレッスン、特にフロントエンドのテストに取り組む頃には、多くのツールがARIAのroleを使って、最初からアクセシビリティを念頭に置いた構築を促していることに気づくでしょう。おそらく、このドキュメントに戻ってきたり、似たようなリソースを調べたりすることになるでしょう。
  2. ARIAのライブリージョンは、ページに加えられた動的な更新を支援技術にアナウンスさせるのに非常に便利な、もう一つの種類のARIA属性です。
