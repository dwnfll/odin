Meaningful Text

日本語訳

← advanced_html_css

Learn the importance of being clear when labeling items on your website.

イントロダクション

意味のあるテキストというのはかなりシンプルです: ユーザーがテキストを読んだり、それがアナウンスされたりしたとき、周囲のコンテキストがなくても、それが何を意味するのかをすぐに理解できるべきだということです。意味のあるテキストが不足していると、すべてのユーザーに影響を与える可能性がありますが、特に支援技術に頼っているユーザーに影響します。このレッスンでは、ユーザーに意味のあるテキストを提供することを意識し始めるべきいくつかの場面を扱っていきます。

レッスン概要

このセクションでは、このレッスンで学ぶトピックの概要を説明します。

  • 意味のあるリンクを提供する方法を知ります。
  • フォームで意味のあるテキストを提供する方法を知ります。
  • 画像に意味のあるalt属性を提供する方法を知ります。

リンク

リンクの2つの異なる例を見てみましょう:

<!-- Example 1: Where's "here"? -->
<a href='...'>Click here</a> to start your career in web development!

<!-- Example 2: I love that place! -->
Visit <a href='...'>The Odin Project</a> to start your career in web development!

目の見えるユーザーにとって、例1のリンクは完全に理にかなっています。しかし、(セマンティックHTMLのレッスンで述べたように)ランドマークや見出しを通してページをナビゲートできることに加えて、スクリーンリーダーは、リンクのような特定のタイプの要素間をナビゲートできることがあります。もしユーザーがページ上のすべてのリンク間をナビゲートしたとしたら、例1でアナウンスされる唯一のものは「Click here, link」です。正確に「here」とはどこなのでしょうか?周囲のコンテキストがなければ、そのリンクは無意味です。それだけでなく、もしページ内に同じテキストコンテンツを持つ複数のリンクがあれば、ユーザーは何度も「click here」と言われることになります。

しかし、例2のリンクは、すべてのユーザーにとって文脈の中で理にかなっているだけでなく、アナウンスされたときにスクリーンリーダーのユーザーにとってコンテキストの外でも理にかなっています: 「The Odin Project, link」というようにです。

ページにリンクを追加する際、従うべきいくつかのルールがあります:

  1. <a>要素のテキストコンテンツが、リンクがどこにリダイレクトするかを何らかの形で示していること、そしてそれが簡潔である(約100文字程度)ことを確認してください。ですので、「click here」や「this page」のようなフレーズを使うのは避けてください。
  2. リンクがファイルを開いたりダウンロードしたりする場合は、それがどんな種類のファイルであるかとそのファイルサイズをユーザーに伝えるテキストを含めてください。
  3. リンクがtarget="_blank"属性で自動的に新しいタブやウィンドウで開く場合は、何らかの方法でこれをユーザーに示すべきです。
<!-- Example 1: Now the user is aware that this link will open or download a PDF file. -->
<a href='...'>2021 Sign Up Statistics (PDF, 1MB)</a>

<!-- Example 2: And now the user knows this link opens in a new tab! -->
<a href='...'>GitHub (opens in new tab)</a>

次にリンクを使う必要があるときは、その要素の内容を自分自身で声に出して言ってみてください。それは、ページ、記事、動画のタイトルのように、そのリンクがあなたをどこに連れて行くのかを合理的に示していますか?それが自動的に新しいタブで開くかどうか、あるいはダウンロードダイアログを開くかどうかを認識できていますか?もしここまでスクリーンリーダーを使ってテストしてきたなら、リンクが意味のあるテキストを持っているかどうかをテストするさらに良い方法は、スクリーンリーダー自体を使うことです!

フォーム

ユーザーがフォームに記入したり送信したりする際に、意味のあるエラーを提供することは、その体験をイライラするものから…まあ、楽しいとまでは言えないかもしれませんが、少なくとも少しはイライラしないものに変えることができます。まったく役に立たないものから非常に役立つものまで、いくつかのエラーの例を見てみましょう:

<!-- Example 1: Huh? -->
<div class='input-error'>Error: Invalid input.</div>

<!-- Example 2: That makes more sense. -->
<div class='input-error'>Error: Email is invalid.</div>

<!-- Example 3: Even better! -->
<div class='input-error'>Error: 'JohnSmith@@test.com' is not valid. Example of a valid email: example@yourdomain.com.</div>

たとえ例1でどのinputがエラーを引き起こしたか分かったとしても(それが常に当てはまるとは限りませんが)、そのエラーは意味のあるテキストを何も提供していません。どのinputが無効なのでしょうか?なぜ無効なのでしょうか?どうすれば修正できるのでしょうか?これらの質問はどれも答えられていません。では、このエラーが、ページ上のどこにエラーが描画されているかを見ることができず、「invalid input」とだけアナウンスされるかもしれない、支援技術のユーザーにとってどれほど無意味であるに違いないか想像してみてください。

例2のエラーは、どのinputが無効かを明確に伝えているので、どこに行けばよいか正確に分かります。これがユーザーが知る必要のあるすべてかもしれませんが、それでもまだかなり漠然としたエラーであるということは心に留めておく価値があります。私たちのメールがなぜ無効なのかは分かりません。

例3のエラーはさらに意味があります。どのinputが無効かを伝えるだけでなく、そのエラーをどう修正すればよいかも伝えてくれます。一般的に、ユーザーにフォームのエラーを伝える際は、どのinputがそのエラーを引き起こしたか、そして可能であれば、そのエラーをどう修正すればよいか、あるいはなぜそのエラーが発生したのかを何らかの形で伝えるべきです。

フォームで意味のあるテキストを提供するもう一つの方法は、パスワードのinputがパスワードに含まれていなければならない文字をリストする(「大文字を少なくとも1文字、数字を少なくとも1つ含める必要があります…」)ときのような指示です。あるinputに固有の指示は、そのinput自体のそばに配置すべきです。どのinputが必須かを示すような、フォーム全体にわたるより一般的な指示は、フォームの先頭に配置する(「* は必須項目を示します」)か、input自体かそのラベルのそばに配置する(「Name (required)」)べきです。

代替テキスト

この時点で、あなたはimg要素のalt属性にかなり馴染んでいるはずです。そうであってもなくても、以下の例のどちらが有効か分かるか試してみましょう:

<!-- Example 1 -->
<img src='...' alt='' />

<!-- Example 2 -->
<img src='...' alt='Odin' />

信じられないかもしれませんが、上記の例はどちらも有効です!例1は実際には意味のあるテキストを何も持っていません(おそらく意味のあるテキストの不在と言えるでしょう)が、それでもその重要性を理解しておくべきです。画像を純粋に装飾のためだけに使っている場合、あるいはその画像がユーザーにとって本当に重要ではない場合、一般的には支援技術のユーザーにそれを認識させたくないはずです。そのような場合は、例1に見られるように、alt属性の値として空の文字列を常に使うべきです(これはnull値としても知られていますが、JavaScriptのデータ型と混同しないでください)。もしalt属性を省略していたら、画像の存在が依然としてアナウンスされてしまう可能性があり、これはユーザーを混乱させるかもしれません(特にファイル名が文字と数字のランダムな文字列だった場合)。

例2では、スクリーンリーダーは「Odin, graphic」とアナウンスし、画像があることとそれが何の画像であるかをユーザーに知らせます。しかし、画像の代替テキストが何であるべきかは、最終的にはさまざまな要因によります。

課題

  1. Alternative Text - WebAIMを読んで、画像の機能とその周囲のコンテキストに基づいて、いつ、どのように画像に代替テキストを追加すべきかを学んでください。
  2. Usable and Accessible Form Validation and Error Recoveryを読んで、ユーザーにエラーを提供するさまざまな方法と、それぞれの長所と短所について学んでください。
