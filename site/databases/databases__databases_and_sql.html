Databases and SQL

日本語訳

← databases

Data is the core of every major web app and here you'll learn how to speak SQL. Being able to properly query a database will go a long way to minimising any problems your website's users might encounter with slow response times.

イントロダクション

データは、あらゆる優れたウェブアプリの中核であり、SQLについての実用的な知識があれば、大いに役立ちます。その知識があれば、Object-Relational Mapper(ORM。例えばRailsのActive RecordやNode.jsのPrisma)を使うときに舞台裏で何が起こっているかを理解できるだけでなく、データに対してより複雑な質問を投げかけることにも抵抗がなくなります。そしてそれこそが、SQLの本質です。つまり、データベースに質問を投げかけ、時にはその中の何かを追加したり変更したりすること。クエリを使うことは、あなたにとって信じられないほど役立つものになります。

よりシンプルなケースでは、プロモーションコード「FREESTUFF」を使って12月にサインアップしたすべてのユーザーを表示したいと思うかもしれません。現在のユーザーが作成したすべてのコメントを、トピックと作成日でソートして表示したいと思うかもしれません。より複雑なケースでは、1,000人を超えるユーザーがいる州に発送されたすべての注文を、数量と合計注文金額でリスト表示したいと思うかもしれません。あるいは、社内的な理由から、平日1週間に5本の記事を読むという指定したエンゲージメント基準を満たすユーザーを生み出しているのはどのプロモーションチャネルか、といったマーケティング分析の質問をするかもしれません。

これらの例はすべて、あなたがデータベースとやり取りすることを伴います。幸いなことに、(焦点を当てる)多くのデータベースはSQLを話しますし、幸運なことに、SQLには全体で数十個の単語しかない中で、実際に一貫して使うのはせいぜい十数個ほどです。つまり、それほど大きな言語ではなく、むしろその背後にある概念のほうがずっと重要なのです。

あなたは、上記のような質問から始め、それから、おそらくさまざまな種類のテーブルがたくさん入っているであろうデータベースに、それらを正しく問いかける方法を見つけ出す必要があります。おそらく誰もが少しずつ違ったイメージの仕方をしていますが、SQLクエリを実行するときに何が起こっているのかをイメージする方法を見つけることは、かなり重要です。私たち自身は、Excelのテーブルが頭の中で動き回り、互いに結合し、必要に応じて並び替えられていく様子を思い浮かべています。人それぞれです。

単なるSELECT users.* FROM users LIMIT 1のようなクエリを超えて、テーブル同士を結合したり、結果に対して計算を行ったり、新しい方法で結果をグループ化したりといった、より動的なトピックに進んでいきます。

リソースについての注記

SQLは、埃をかぶった古い技術マニュアルや90年代スタイルのウェブサイトにしまい込まれてきたトピックの一つです。世に出ている最高の書籍でさえ、実際に細かい詳細をすべて知っておく必要のあるデータベースエンジニア向けに書かれる傾向があるため、SQLを妙に複雑に見せてしまうことがあります。

近年ウェブアプリケーションが普及したことで、新しいユーザーの間でSQLの概念を理解することに焦点を当てたいという需要が高まっていますが、学習ツールはそれに本当には追いついていません。利用可能なツールを使って、それらの概念をできる限り伝えていきます。

世界最速の、そこそこ網羅的なSQLの説明

これは、SQLについての、最初から最後までの非常に簡単な説明です。特定の新しい戦術を教えるのにはあまり適していませんが、課題として読む文章に取り組む前の、全体的な概要を示してくれるはずです。それでは始めましょう……

SQLは、多くのリレーショナルデータベースとやり取りするために使われる言語です。これらのデータベースは、異なる種類のデータ(例えばusersテーブルやpostsテーブル)を保存するために、多くのテーブルを使います。テーブルはスプレッドシートのような長いリストであり、各行はそれぞれ異なるレコード(あるいはオブジェクト。例えば1人のユーザー)で、各列はそのレコードの属性の一つ(名前、メールアドレスなど)です。すべてのテーブルに含まれる一つの列がID列であり、これは一意な行番号を与えるもので、そのレコードの「主キー(primary key)」と呼ばれます。

一つのテーブルのある列が、別のテーブルのIDを指すようにすることで、テーブル同士を「リンク」させることができます。例えば、postsテーブルのある行には、user_idという列の下に、著者のIDが含まれているかもしれません。postsテーブルの中に別のテーブルのIDがあるため、その列は「外部キー(foreign key)」と呼ばれます。

いろいろセットアップする

SQLでは、あらゆることができます。最初のカテゴリのコマンドは、データベースをセットアップする(CREATE DATABASE)ためのもの、個別のテーブルをセットアップする(CREATE TABLE)ためのもの、そしてそれらを変更したり削除したりするための同様のコマンドです。データベースのセットアップ情報は、「スキーマ(Schema)」と呼ばれる特別なファイルに保存されており、これはデータベースの構造に変更を加えるたびに更新されます。スキーマは、「これが私たちのデータベースで、いくつかのテーブルがあります。最初のテーブルは'users'で、'ID'(整数)、'name'(文字の並び)、'email'(文字の並び)……という列があります」と語っているものだと考えてください。

テーブルをセットアップすることに加えて、特定の列(例えばユーザー名)には一意な値しか許可しないようデータベースに指示したり、CREATE INDEXを使って後で高速に検索できるように列にインデックスを付けたりすることもできます。基本的に、テーブルをあらかじめソートしておくという大変な作業を代わりに行ってくれるインデックスを、後で検索に使うことになりそうな列(ユーザー名など)に対して作成してください……そうすることで、あなたのデータベースははるかに高速になります。

SQLは、行末にセミコロンを付けることや、二重引用符(")の代わりに単一引用符(')を使うことを好みます。

データをいじり回す

データベースがセットアップされ、扱うための空のテーブルができたら、SQLの文を使ってそれにデータを入れ始めます。あなたが行いたい主な操作は、(以前見たことのある)CRUD、つまりCreate(作成)、Read(読み取り)、Update(更新)、Destroy(削除)です。あなたが実行するコマンドのほとんどは「Read」のカテゴリに分類されるでしょう。というのも、データに質問を投げかけ、それを表示しようとすることに、多くの時間を費やすことになるからです。

SQLにおけるCRUD関連のコマンドはすべて、いくつかの部分から構成されています。操作(「文」)、それが実行されるテーブル、そして条件(「句」)です。条件を指定せずにテーブルに対して操作を行うと、それはテーブル全体に適用されてしまい、おそらく何かを壊してしまうでしょう。

「Destroy」クエリにおける典型的な間違いは、WHERE句なしでDELETE FROM usersと入力してしまうことで、これはテーブルからすべてのユーザーを削除してしまいます。あなたはおそらく1人のユーザーだけを削除したかったはずで、その場合はnameやidのような(できれば一意な)属性に基づいて、条件句の一部としてそれを指定します。例えばDELETE FROM users WHERE users.id = 1のようにです。比較演算子(>、<、<=など)を使ってコマンドを実行する行のグループを指定したり、論理演算子(AND、OR、NOTなど)を使って複数の句を連結したりといった、あらゆる常識的なことができます。例えばDELETE FROM users WHERE id > 12 AND name = 'foo'のようにです。

「Create」クエリではINSERT INTOを使い、値を挿入する列を指定し、それに続けて値自体を指定する必要があります:

INSERT INTO users (name, email) VALUES ('foobar', 'foo@bar.com');

注: 技術的には列名を省略することも可能ですが、これは悪いプラクティスと見なされており、一般的には推奨されません。

これは、実際にはテーブルに新しい行を追加しているだけなので、どの行を選択したかについて注意する必要がない、数少ないクエリの一つです。

「Update」クエリではUPDATEを使い、(key="value"のペアを使って)SETで何のデータを設定するかと、どの行に対してその更新を行うかを伝える必要があります。WHERE句が複数の行を見つけてしまうと(例えば、よくある名前で検索した場合)、それらすべてが更新されてしまうので注意してください。ユーザーのメールアドレスを更新するための標準的なクエリは、以下のようになるかもしれません(ただし、実際にはIDは常に一意なので、IDで検索することになるでしょう):

  UPDATE users
  SET name='barfoo', email='bar@foo.com'
  WHERE email='foo@bar.com';

SELECTを使う「Read」クエリが最も一般的です。例えばSELECT * FROM users WHERE created_at < '2013-12-11 15:35:59 -0800'のようにです。ここで見える*は、単に「すべての列」を意味します。列を指定するには、テーブル名と列名の両方を使います。テーブルが一つだけのクエリであれば列名だけでも許されますが、複数のテーブルが関わってくるとすぐにSQLに怒られてしまうので、常にテーブル名を指定するようにしましょう: SELECT users.id, users.name FROM users。

SELECTの近い親戚で、列の一意な値だけが欲しいときに使うのがSELECT DISTINCTです。重複なしに、すべての異なるユーザー名のリストが欲しいとしましょう……SELECT DISTINCT users.name FROM usersを試してみてください。

テーブル同士をマッシュアップする

特定のユーザーが作成したすべての投稿を取得したい場合、ON句を使って、テーブル同士を結合する際にどの列を使うべきかをSQLに伝える必要があります。この「結合」は、JOINコマンドで行います。しかし、データが完全には一致しない2つのテーブルをマッシュアップした場合(例えば、1人のユーザーに対して複数の投稿がある場合)、実際にはどの行が残るのでしょうか?4つの異なる可能性があります:

JOINにおける「LEFT」が何を指すかを明確にする

「left(左側)」のテーブルとは、元となるテーブル(FROM句が対象としているテーブル)のことです。例えば、以下の例ではusersがそれにあたります。

  1. INNER JOIN、別名JOIN -- あなたの一番の親友であり、あなたが使うものの95%を占めます。両方のテーブルのうち、一致する行だけを残します。もしすべてのユーザーのすべての投稿を求めたなら(SELECT * FROM users JOIN posts ON users.id = posts.user_id)、実際に投稿を書いたことのあるユーザーと、user_id列に著者が指定されている投稿だけが返されます。ある著者が複数の投稿を書いている場合、複数の行が返されます(ただし、ユーザーのデータを含む列は、単純に繰り返されるだけです)。
  2. LEFT OUTER JOIN -- 左側のテーブルのすべての行を残し、左側のテーブルと一致する右側のテーブルの行を追加します。これによって生じる空のセルは、すべてNULLに設定されます。例えば、投稿を書いたかどうかにかかわらず、すべてのユーザーを返します。投稿がある場合は、上記と同じようにそれらの投稿を並べます。ない場合は、postsテーブルから求めた列をNULLに設定します。
  3. RIGHT OUTER JOIN -- その逆です……右側のテーブルのすべての行を残します。
  4. FULL OUTER JOIN -- 両方のテーブルの間に不一致があっても、すべてのテーブルのすべての行を残します。一致しないセルはすべてNULLに設定されます。

JOINでは当然、特定のユーザーの投稿だけが欲しい場合のように、条件を指定することもできます: SELECT * FROM users JOIN posts ON users.id = posts.user_id WHERE users.id = 42。

優れた図解については、Jeff Atwoodによる「A Visual Explanation of SQL Joins」を参照してください。

より良い説明については、W3SchoolsのJoinsのレッスンを読んでください。

関数を使ってデータを集計する

通常のSQLクエリを実行すると、たいてい大量の行が返ってきます。時には、ユーザーが書いた投稿のCOUNTのように、ある列を集計した単一の関連値だけを返したいこともあります。この場合、SQLが提供している便利な「集計」関数の一つを使うだけです(そのほとんどは、あなたが予想する通りのものでしょう。SUMやMIN、MAXなどの関数です)。この関数は、SELECT MAX(users.age) FROM usersのように、SELECT文の一部として含めます。この関数は、*を指定しない限り単一の列に対してのみ動作します。*が機能するのは、COUNTのような一部の関数だけです(COUNT(*)はすべての行を数えますが、MAX(*)のようなものは意味をなしません。というのも、すべてのものの最大値を取るとはどういうことなのか、ということになるからです)。

後でそのエイリアスを使って呼び出せるように、列や集計関数の名前を変更するためにエイリアス(AS)が使われているのをよく見かけます。例えば、SELECT MAX(users.age) AS highest_age FROM usersは、最大年齢を含むhighest_ageという列を返します。

さて、ここからが面白いところです。データセット全体に対して単一の値だけを返すCOUNTのような集計関数は便利ですが、データの非常に特定の塊に対してそれらを使い、それからグループ化したいときに、本当に役立つようになります。例えば、(すべてのユーザーによるすべての投稿の数とは対照的に)ユーザーごとの投稿のCOUNTを表示する場合です。それは次のようになります:

  SELECT users.id, users.name, COUNT(posts.id) AS posts_written
  FROM users
  JOIN posts ON users.id = posts.user_id
  GROUP BY users.id, users.name;

users.idに加えてusers.nameでもグループ化していることに注目してください。これは、GROUP BY句に選択したすべての非集計列を明示的に含めるというベストプラクティスに沿ったもので、明確さを高めてくれます。ほとんどのデータベースでは厳密には必要ないかもしれませんが。 インタラクティブな図解については、W3Schoolsのブラウザベースのplaygroundを参照してください。

最後の便利なテクニックは、データの一部だけを表示したい場合です。通常の状況であれば、WHERE句を使って絞り込むでしょう。しかし、(上の例のようにユーザーごとの投稿数を取得するために)COUNTのような集計関数を使っている場合、WHEREはもう機能しません。そのため、集計関数に基づいて条件付きでレコードを取得するには、HAVING句を使います。これは本質的に、集計のためのWHEREです。例えば、10件を超える投稿を書いたユーザーだけを表示したいとしましょう:

  SELECT users.id, users.name, COUNT(posts.id) AS posts_written
  FROM users
  JOIN posts ON users.id = posts.user_id
  GROUP BY users.id, users.name
  HAVING COUNT(posts.id) >= 10;

W3Schoolsのブラウザベースのplaygroundにもう一度戻り、CustomersテーブルとOrdersテーブルを結合して各国の注文数を取得し、GROUP BYの後にHAVING COUNT(*) > 10;という行を追加してみてください(そして、前の行の余分なセミコロンを削除してください)。

上の説明のどこかで迷子になってしまったかもしれませんが、それでまったく問題ありません……これは、誰であっても10分で身につけられる以上のことをカバーしています。課題として指定されている読み物のほうが、物事をうまく説明してくれるはずですが、それよりも重要なのは、プロジェクトの中で実際に応用することで、理解を確かなものにする機会がたくさんあるということです。恐れずに、粘り強く続けてください!

SQLはあなたのコードより速い!

これを学ぶことが特に重要なのは、データベースから大量のデータをただ取り出して、それからプログラミング言語(RubyやJavaScriptなど)を使って処理するよりも、SQLを賢く使ったクエリを組み立てるほうが、はるかに速いからです。例えば、すべてのユーザーの一意な名前が欲しい場合、SELECT users.name FROM usersのようなSQLでデータベースからリスト全体を取得し、それからJavaScript/Rubyのメソッドを使って重複を取り除くこともできます……しかし、それにはそのデータをすべてデータベースから取り出し、メモリに置いてから、コードの中でそれを反復処理する必要があります。代わりにSELECT DISTINCT users.name FROM usersを使えば、SQLにそれをすべて一つのステップで行わせることができます。

SQLは、速くなるように作られています。特別なクエリオプティマイザを持っており、これがこれから実行しようとしているクエリ全体を確認し、どのテーブルを結合する必要があるか、そしてどうすればそのクエリを最も速く実行できるかを正確に把握します。SELECTを使う場合とSELECT DISTINCTを使う場合の違いは、自分でそれを行うことにかかる時間のコストと比べれば、無視できるほどです。SQLを学ぶことは、より多くのことができる、より良いクエリを書く助けとなり、それがあなたのアプリをはるかに高速にしてくれます。

まとめ

SQLは、特に複数のJOINの結果を条件付きで表示したりグループ化したりすることに関しては、理解するのが難しい概念の集まりになり得ます。基本的なJOINと基本的な集計関数までの内容は、しっかりと身につける努力をすべき、中核となる知識です。

本当に高度な概念に十分慣れる段階までなかなか到達できなかったとしても、幸いなことに、将来のごくわずかな状況を除いては、それらを使う必要はないでしょう。すべてを最初に学んでおくのは良いことですが、いずれにせよ、いざその時が来たら、特定の高度なクエリの実行方法をGoogleで調べることになるでしょう。

次のステップは、プロジェクトの中でこれをすべて実践する機会を得たら、今後のコースであなたのコードベースにそれを応用することです。ORMツールを使うことで、生活がはるかに、はるかに、はるかに楽になることにすぐ気づくでしょう。でも、そういったより良く輝かしいものに移っていっても、あの昔なじみのSQLのことを忘れないでくださいね?
