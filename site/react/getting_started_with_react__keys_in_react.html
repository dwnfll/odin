Keys In React

イントロダクション

このレッスンでは、Reactにおけるkeyについて扱います。keyはコンポーネントのための特別なpropsであり、なぜそれが使われるのかを学んでいきます。

レッスン概要

このセクションでは、このレッスンで学ぶトピックの概要を説明します。

  • keyとは何か、そしてReactがそれをどう使うか。
  • Reactアプリケーションにおけるkeyの良い使い方と悪い使い方。

なぜReactにはkeyが必要なのですか?

Reactは内部で「仮想DOM」を使って、実際のDOMの中で何を更新すべきかを判断し、不要な処理を最小限に抑えていることを思い出すかもしれません。再レンダーが発生すると、Reactはまずこの仮想DOMを再作成し、新しい仮想DOMと以前の仮想DOMの差分を取り(変更点を比較し)、それから実際に変更があったものについてのみ、実際のDOMを更新します。

Reactは、これらの各コンポーネントの違いを見分けられる必要があります。それぞれが独自のpropsとstateを持つことになるからです。そのため、すべてのコンポーネントには内部でIDが与えられます。それがkeyです。例えば、stateを更新しても、それは依然として同じインスタンスのコンポーネントであり、コンポーネントのkeyが変わっていないため、Reactはそれを認識でき、不要な処理を避けることができます。しかし、もしkeyが変われば、Reactはこれがそのコンポーネントの新しいインスタンスであることを認識し、新しいstateを持つ新しいインスタンスを構築できます。

通常、Reactがこれを自動的に処理してくれるため、コンポーネントに手動でkeyを与える必要はありません。しかし、それらを活用できるいくつかのケースがあります。

リストをレンダーするときのkey

前のレッスンでは、.map()メソッドを使ってデータの配列を反復処理し、コンポーネントを返すことで、コンポーネントのリストをレンダーしました。では、もしそのリストの中のいずれかの項目が変わったとしたら、Reactは内部でどの項目を更新すればよいのか、どうやって知るのでしょうか?

リストが変化した場合、次の2つのうちどちらかが起こることを望むかもしれません:

  1. リスト全体を完全に再レンダーする
  2. 変更された特定の項目だけを見つけ出し、それらだけを再レンダーする

Reactに変更された項目だけを見つけ出してほしいのであって、(不要な作業を避けるために)リスト全体を再レンダーしてほしくはありません。そのため、そのリストの各項目にはkeyが必要です。

もしJSXの中でコンポーネントをハードコードするなら、Reactにkeyを自動的に処理させておくことができます。指示が明示的かつ静的であるため、再レンダーをまたいでも、あるコンポーネントと別のコンポーネントの間で曖昧さが生じることはありません。

しかし、配列に対してmapすることでリストをレンダーする場合、状況は動的になります。.map()メソッドに対して書くのはたった一つの戻り値だけですが、最終的な結果は、その戻り値のコンポーネントの2個、3個、あるいは100個のインスタンスになることもあり、それらの数も順序も、レンダーごとに変化する可能性があります。Reactは、再レンダーをまたいで特定のインスタンスを確実に一致させられるような形で、これらの各コンポーネントに自動的にkeyを提供することはできません。もし項目の数や順序が変わったらどうでしょうか?どのコンポーネントを新しいstateでゼロから作り直す必要があり、どれがstateを保持・更新する既存のインスタンスなのかを、どうやって確実に知ることができるでしょうか?

だからこそ、リストを動的にレンダーする際は、自分自身でkeyを提供しなければなりません。そうすることで、(サーバーからであれ、ユーザーの操作からであれ)何らかの理由でリストが更新されたときに、Reactは以前のリストの各項目のkeyを、更新後のリストと照合できます。もし何か変更があれば、Reactは変更があった項目だけを更新します。

keyが一貫していて一意である限り、ReactはDOMを効果的かつ効率的に処理できます。

keyを使う

keyは、propとしてコンポーネントやDOM要素に渡されます。この構文にはすでに馴染みがあるはずです。

<Component key={keyValue} />
<div key={keyValue}></div>

注目すべき重要な違いは、keypropはプライベートであり、React内部の処理のためだけに使われる、という点です。これはpropsパラメータオブジェクトを介してコンポーネント自体に渡されることはありません。

構文がわかったところで、次の疑問は、keyとして何を使うべきか、ということです。理想的には、リストの各項目に一意な識別子があるべきです。ほとんどのデータベースは各エントリに一意なidを割り当てるため、自分でidを割り当てる心配をする必要はないはずです。もし自分でデータを定義している場合は、各項目に一意なidを割り当てるのが良いプラクティスです。例えば、一意なidを生成するためにcrypto.randomUUID()関数を使うことができます。例を見てみましょう:

// a list of todos, each todo object has a task and an id
const todos = [
  { task: "mow the yard", id: crypto.randomUUID() },
  { task: "Work on Odin Projects", id: crypto.randomUUID() },
  { task: "feed the cat", id: crypto.randomUUID() },
];

function TodoList() {
  return (
    <ul>
      {todos.map((todo) => (
        // here we are using the already generated id as the key.
        <li key={todo.id}>{todo.task}</li>
      ))}
    </ul>
  );
}

さらに、リストがアプリケーションの存続期間を通じて変化しないと確信できる場合は、配列のインデックスをkeyとして使うこともできます。しかし、項目が削除・挿入・並べ替えられることでリストが変化する場合、わかりにくいバグにつながる可能性があるため、これは推奨されません。これについては、課題セクションでリンクされている記事でさらに詳しく学びます。

const months = ['January', 'February', 'March', 'April', 'May', 'June', 'July', 'August', 'September', 'October', 'November', 'December'];

function MonthList() {
  return (
    <ul>
      {/* here we are using the index as key */}
      {months.map((month, index) => (<li key={index}>{month}</li>))}
    </ul>
  );
}

keyの使い方自体はシンプルですが、知っておくべきアンチパターンが一つあります。keyは決してその場で生成すべきではありません。リストをレンダーしている最中にkey={Math.random()}やkey={crypto.randomUUID()}を使うと、keyの目的が損なわれてしまいます。というのも、リストがレンダーされるたびに新しいkeyが作られてしまうからです。上の例で示したように、keyはデータ自体から導き出されるべきです。

const todos = [
  { task: "mow the yard", id: crypto.randomUUID() },
  { task: "Work on Odin Projects", id: crypto.randomUUID() },
  { task: "feed the cat", id: crypto.randomUUID() },
];

function TodoList() {
  return (
    <ul>
      {todos.map((todo) => (
        // DON'T do the following i.e. generating keys during render
        <li key={crypto.randomUUID()}>{todo.task}</li>
      ))}
    </ul>
  );
}

keyとstate

リストを動的にレンダーすることは、間違いなく、手動でkeyを提供する必要がある最も一般的な状況ですが、それが唯一のケースというわけでは決してありません。keyは単に、Reactがコンポーネントのインスタンスを区別するための内部的なIDにすぎないため、特定のコンポーネントがそのstateの更新に伴って同じインスタンスであるべきか、それとも新しいstateを持つまったく新しいインスタンスであるべきかを、意図的に自分でコントロールしたい場合にも、自分自身でkeyを提供できます。

あなたがゲームを持っていて、それが終わったときに、元のstateにリセットできるようにしたいとします。ページをリフレッシュするのはおそらく賢明ではありません。特に、手を触れずにおきたい独自のstateを持つ他のコンポーネントがある場合はなおさらです。関連するそれぞれのstateを初期値に設定する関数を書くこともできますが、その場合、stateを見落としたり、間違った値を設定したりしないよう気をつけなければならず、またstateを追加・削除するたびにこれを最新の状態に保つ必要が出てきます。

「このコンポーネントを新しいstateでゼロからレンダーしてほしい」とReactに伝える、もっとずっとシンプルな方法があったらどうでしょうか?実は、keyを更新するだけでよいのです。例えば:

function GamePage() {
  const [key, setKey] = useState(0);

  return <Game key={key} resetGame={() => setKey(key + 1)} />;
}

Gameは独自のstateを持ち、独自のコンポーネントをレンダーします。再レンダーされても、keyが変わっていない限り、それは依然として同じインスタンスのGameであるため、そのstateは保持/更新されます。もしGameの内部のどこかに、クリックされるとresetGame()を呼び出すボタンがあれば、それをクリックすることでkeyのstateが変化します。するとGamePageが再レンダーされ、Gameが新しいkeyを持つようになったため、ReactはそれをGameのまったく新しいインスタンスと見なし、新しいstateを持つ新しいインスタンスを作成します。
