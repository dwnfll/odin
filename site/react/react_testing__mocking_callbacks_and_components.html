Mocking Callbacks And Components

イントロダクション

すでにReactテストの基本のいくつかを扱いました。今度はさらに深く掘り下げていくときです。

このレッスンでは、モックについて学びます。さらに、この(theodinproject.com)ウェブサイトのReactコンポーネントについて取り上げ、実際のアプリケーションでReactのテストがどのように書かれているかを理解します。

レッスン概要

このセクションでは、このレッスンで学ぶトピックの概要を説明します。

  • Reactテストの文脈でモックを実行する。

モックとは何ですか?

ここまでのレッスンについてきたなら、モックの概念はすでに以前のセクションで紹介されており、あなたのBattleshipプロジェクトにモックを取り入れたこともあるかもしれません。モックがReactコンポーネントのテストにどう役立つかを見ていきましょう。

コールバックハンドラをテストする

コールバックはどこにでも存在します。ユーザーとのあらゆるやり取りの手段には、コールバックが関わっています。時には、親コンポーネントのstateを変更するために、propsとして渡されることもあります。以下のボタンコンポーネントを考えてみましょう:

// CustomButton.jsx

const CustomButton = ({ onClick }) => {
  return (
    <button onClick={onClick}>Click me</button> 
  );
};

export default CustomButton;

特に凝ったものではありません。CustomButtonはpropが渡されているコンポーネントです。私たちが注目しているのはonClickpropです。その関数が何をするのかはわかりません。その関数がアプリケーションにどう影響するのかもわかりません。私たちにわかっているのは、ユーザーがボタンをクリックしたときに、それが呼び出される必要があるということだけです。テストしてみましょう。

onClick関数をどのようにモックしテストするかに注目してください:

// CustomButton.test.jsx

import { vi, describe, it, expect } from 'vitest'
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import CustomButton from "./CustomButton";

describe("CustomButton", () => {
  it("should render a button with the text 'Click me'", () => {
    render(<CustomButton onClick={() => {}} />);

    const button = screen.getByRole("button", { name: "Click me" });

    expect(button).toBeInTheDocument();
  });

  it("should call the onClick function when clicked", async () => {
    const onClick = vi.fn();
    const user = userEvent.setup()
    render(<CustomButton onClick={onClick} />);

    const button = screen.getByRole("button", { name: "Click me" });

    await user.click(button);

    expect(onClick).toHaveBeenCalled();
  });

  it("should not call the onClick function when it isn't clicked", () => {
    const onClick = vi.fn();
    render(<CustomButton onClick={onClick} />);

    expect(onClick).not.toHaveBeenCalled();
  });
});

3つのテストで、このコンポーネントは完了です。最初のテストがどのように機能するかについては、すでに馴染みがあるはずです。どの関数がどのパッケージから来ているのか、少し時間をかけて把握してみてください。

2つ目と3つ目のテストでは、Vitestの関数の一つであるvi.fn()を使ってonClickハンドラをモックします。それから、ボタンがクリックされたとき/されなかったときに、それが呼び出された/呼び出されなかったことをアサートします。

モックは、各テストブロックの中ではなく、beforeEachブロックの中でセットアップすることもできます。これは、状況によっては適している場合もあります。しかし、可読性を高めるためには、すべてのセットアップを同じテストブロックの中で行うことが推奨されます。そうすることで、コンテキストを把握するためにファイル全体を検索する必要がなくなり、将来の変更をレビューしやすくなります。これはまた、リーク(漏れ)がテストスイート全体で問題を引き起こす可能性も減らしてくれます。テストファイルが特に長く、テストの準備が数十行にもなる場合を除いて、モックは各テストブロックの中でセットアップすることが推奨されます。そうでない場合は、beforeEachを使ってもかまいません。

userEvent.setup()は、コンポーネントをレンダーする前に呼び出すことが推奨されます。レンダーやuserEvent関数を(例えばbeforeEachブロックの中のような)テスト自体の外で呼び出すことは推奨されません。複数のテストで同じコードを繰り返していることに気づいたら、各テストを短くするための推奨されるアプローチは、setup関数を書くことです。

子コンポーネントをモックする

モジュールをモックするという概念に出会ったことがあるかもしれません。Reactでは、コンポーネントツリーが大きくなると、テストが複雑になることがあります。特に、ツリーの上位にあるコンポーネントについてはなおさらです。だからこそ、私たちは子コンポーネントをモックします。これは頻繁に出会うものではありませんが、それでも、自分自身のテストで必要になるかもしれない場合に備えて、この概念を理解しておくことは有益です。

注記 - Vitestのモック

ここでのテストではjest.mock()を使っています。ここまでついてきて、Vitestを使ってテストをセットアップしている場合は、代わりにvi.mock()を使ってもかまいません。vi.mock() APIを参照してください。

最初のアサーションに進みましょう。ProjectSubmissionContext.Providerについてはあまり気にしなくて大丈夫です。このテストの文脈では、その目的は、allSubmissionsPathpropを渡すための経路として機能することです。私たちはすでに、テストしたい3つの注目ポイントを特定しています。可読性のために、describeを使ってそれらを3つのテストスイートに分けます。

最初のスイートでは、ユーザーが提出物を持っている場合のアサーションと、持っていない場合のアサーションを行います。他のスイートも同様のパターンに従います。

さらに探ってみる

他のコンポーネントとそのテストにも、遠慮なく目を通してみてください。モックされた関数を目にするでしょう。actのような、まだ見たことのない関数も目にするでしょう。カスタムのrender関数も目にするでしょう。すべてを理解できなくても大丈夫です。目標は、慣れ親しむことです。

もう一つ注意しておくべき重要な点は、ほとんどすべてのテストが、書き方の点である一定のパターンに従っている、ということです。それらはArrange-Act-Assertパターンに従っています。テストをより読みやすく、最終的により良いものにするために、遅かれ早かれこのパターンを取り入れるのは良い考えです。
