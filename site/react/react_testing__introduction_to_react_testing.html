Introduction To React Testing

イントロダクション

前のセクションで、素のJavaScriptアプリケーションをテストする方法を学びました。テストは、保守しやすく柔軟なコードを書くことを可能にしてくれる、強力なツールです。これまでのレッスンについてきたなら、ここまではJestフレームワークを使ってきました。しかし、私たちはViteを使っているので、Viteとうまく統合されるVitestに、テストランナーを切り替えます。React Testing Library(RTL)を使って、テストにさらなる機能を追加していきます。

レッスン概要

このセクションでは、このレッスンで学ぶトピックの概要を説明します。

  • なぜUIテストが価値あるものなのか。
  • Reactのテスト環境をセットアップする方法。
  • UI要素をテストする方法。
  • スナップショットテストを理解する。

UIテスト

ここまでで、あなたはすでにTDDや、テスト全般についての考え方をある程度経験しているはずです。Battleshipプロジェクトを思い出すかもしれません。そこでは、DOMをまったく関与させることなく、根底にあるBattleshipのゲームロジックに限定したテストを書いたはずです。UIに関係のない変更を加え、テストを失敗させ、それから必要なことを解決して、関連性がありパスするテストにした、という経験があるかもしれません。

それにもかかわらず、あなたのテストが根底にあるロジックにしか関わっていなかったため、UIのバグに遭遇したことがあるかもしれません。動作するBattleshipゲームを持っているとしても、それは、UIが実際にあなたの意図した通りに表示され、ユーザーが意図した通りにゲームと対話できることを意味するわけではありません。正直に言えば、コードのどこかの部分(UIに関係あるかないかにかかわらず)を変更するたびに、関連するすべてのUIの側面を再チェックして、すべてが期待通りに動作することを確認しよう、とはなかなか思わないものです。つまり、これは以前と何ら変わりません。今はただUIも関与しているというだけです。

UIテストは、私たちのウェブサイトが意図した内容を含み、望んだ通りに動作しているという自信をより高めてくれ、何かが要件を満たさなくなったときにそれを知らせてくれます。もしかしたら、単純なオブジェクトから配列に変更するといった、stateの正確な構造を変更することにしたものの、今度はリストが意図したテキストを含まなくなってしまうかもしれません。あるいは、コンポーネントのどこかに条件を追加したところ、突然、ドラッグアンドドロップのカードの最後の3つのドロップターゲットだけが、有効なターゲットでなくなってしまうかもしれません。ウェブサイトが複雑になるにつれて、(UIも非UIも含めた)優れたテストの価値は増していく一方です。

Reactのテスト環境をセットアップする

Robin WieruchによるVitestとRTLのセットアップガイドに沿って進めてください。セットアップが完了したら、ここに戻ってきましょう。

Vitestのグローバル変数とESLint

セットアップのチュートリアルのようにvite.config.jsでglobals: trueを設定していたとしても、eslint.config.jsファイルに追加の設定をしない限り、ESLintはこれらのグローバル変数を認識できないため、それでも警告を出してきます。最もシンプルな解決策は、代わりに必要なグローバル変数を明示的にインポートすることです。この場合、vite.config.jsからglobals: trueを省略することができます。

ふう、たくさんのセットアップでしたね。しかし、始める前にもう一つ、小さなパッケージをインストールする必要があります:

npm install @testing-library/user-event --save-dev

これで必要なものがすべて揃ったので、それらのパッケージのいくつかが何をするのか、簡単に見ていきましょう。主に@testing-libraryのパッケージに焦点を当てます。

  • @testing-library/reactは、後で実演するrenderのような便利な関数へのアクセスを提供してくれます。

  • @testing-library/jest-domには、toBeInTheDocumentなどの、便利なカスタムマッチャー(アサーション関数)がいくつか含まれています(完全なリストはjest-domのgithubにあります)。Jestにはすでに多くのマッチャーがあるため、このパッケージの使用は必須ではありません。

  • @testing-library/user-eventは、ウェブページとのユーザーの操作をシミュレートするuserEventAPIを提供します。

最初のクエリ

まず、renderを使ってコンポーネントをレンダーします(この関数が何をできるかについては、renderについてのReact Testing Library APIドキュメントですべて読むことができます)。「レンダー」と言っていますが、実際に画面が表示されるわけではありません。先ほどのRTLセットアップの記事に戻ると、インストールされたパッケージの一つにjsdomがあります。これは、ブラウザのように実際に見た目としてレイアウトすることなく、(イベントを含めた)DOMをメモリ内でシミュレートするもので、これにより、テストのためにその内容をパースできるようになります。これは、より複雑なエンドツーエンドテストのために実際のブラウザ環境を動かす他のライブラリとは異なり、はるかに複雑さが少ないものです。それはここでは扱う範囲外です。

// App.jsx

const App = () => <h1>Our First Test</h1>;

export default App;
// App.test.jsx

import { describe, it, expect } from "vitest";
import { render, screen } from "@testing-library/react";
import App from "./App";

describe("App component", () => {
  it("renders correct heading", () => {
    render(<App />);
    // using regex with the i flag allows simpler case-insensitive comparison
    expect(screen.getByRole("heading").textContent).toMatch(/our first test/i);
  });
});

ターミナルでnpm test App.test.jsxを実行し、テストがパスするのを確認してください。getByRoleは、私たちが使えたであろう十数個のクエリメソッドのうちの一つにすぎません。基本的に、クエリはgetBy、queryBy、findByという3つのタイプに分類されます。クエリについてのReact Testing Libraryドキュメントのページに目を通してください。特に「Types of Queries」と「Priority」のセクションに注目してください。

React Testing Libraryのドキュメントで述べられているように、ByRoleメソッドは、特にnameオプションと組み合わせた場合に、クエリのために好まれるメソッドです。例えば、上のクエリの特異性を次のように改善できます: getByRole("heading", { name: "Our First Test" })。ByRoleを通して行われるクエリは、ユーザーがウェブページをどのような方法(マウスや支援技術など)でナビゲートしていても、私たちのUIが誰にとってもアクセシブルであることを保証してくれます。

ユーザーイベントをシミュレートする

ユーザーがウェブページと対話する方法は数多くあります。実際のユーザーからのフィードバックや操作にはかけがえのない価値がありますが、それでもテストを通して、私たちのコンポーネントにある程度の自信を築くことができます。以下は、Appの見出しを変更するボタンです:

// App.jsx

import { useState } from "react";

const App = () => {
  const [heading, setHeading] = useState("Magnificent Monkeys");

  const clickHandler = () => {
    setHeading("Radical Rhinos");
  };

  return (
    <>
      <button type="button" onClick={clickHandler}>
        Click Me
      </button>
      <h1>{heading}</h1>
    </>
  );
};

export default App;

このボタンが意図通りに機能するかテストしてみましょう。このテストスイートでは、UI要素をクエリするために別のユーティリティを使います。React Testing Libraryは、クエリのためのすべてのメソッドを持つscreenオブジェクトを提供しています。screenを使えば、renderの分割代入を最新の状態に保つ心配をする必要がありません。そのため、renderを分割代入するよりも、screenを使ってクエリにアクセスするほうが良いでしょう。

// App.test.jsx

import { describe, it, expect } from "vitest";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import App from "./App";

describe("App component", () => {
  it("renders magnificent monkeys", () => {
    // since screen does not have the container property, we'll destructure render to obtain a container for this test
    const { container } = render(<App />);
    expect(container).toMatchSnapshot();
  });

  it("renders radical rhinos after button click", async () => {
    const user = userEvent.setup();

    render(<App />);
    const button = screen.getByRole("button", { name: "Click Me" });

    await user.click(button);

    expect(screen.getByRole("heading").textContent).toMatch(/radical rhinos/i);
  });
});

これらのテストは、それ自体で説明になっています。最初のテストでは、スナップショットを活用して、すべてのノードが期待通りにレンダーされるかを確認しています。2つ目のテストでは、クリックイベントをシミュレートしています。それから、見出しが変わったかを確認しています。toMatchは、私たちが行えたであろうさまざまなアサーションの一つです。2つ目のテストのコールバック関数がasyncになっていることに注目してください。これは、await user.click()を行うために必要だからです。

また、React Testing Libraryは、すべてのテストの後にレンダーされたコンポーネントをアンマウントする、という点にも注意しておくことが重要です。だからこそ、私たちは各テストごとにレンダーを行っています。1つのコンポーネントに対してテストがたくさんある場合は、カスタムのsetup関数が役立つことがあります。

スナップショットとは何ですか?

スナップショットテストとは、単に、私たちがレンダーしたコンポーネントを、関連するスナップショットファイルと比較することです。例えば、"renders magnificent monkeys"テストを実行した後に自動生成されたスナップショットファイルは、以下のようなものでした:

// Vitest Snapshot v1, https://vitest.dev/guide/snapshot.html

exports[`App component > renders magnificent monkeys 1`] = `
<div>
  <button
    type="button"
  >
    Click Me
  </button>
  <h1>
    Magnificent Monkeys
  </h1>
</div>
`;

これは、AppコンポーネントのHTMLによる表現です。そして、これは今後のスナップショットのアサーションで、Appと比較されることになります。Appが少しでも変化すると、テストは失敗します。

スナップショットテストは、書くのが速く、簡単です。一つのアサーションで、複数行のコードを書く手間を省けます。例えば、toMatchSnapshotを使えば、ボタンや見出しの存在をアサートする必要がなくなります。 また、予期しない変更がコードに忍び込むことも防いでくれます。スナップショットで何が実現できるかについては、Vitestのスナップショットドキュメントですべて読むことができます。

スナップショットは、これまでのテストの中で私たちに起こった最高の出来事のように思えるかもしれません。しかし、私たちは疑問を抱かざるを得ません。私たちは正確に何をテストしているのでしょうか?何が検証されているのでしょうか?もしスナップショットがパスしたら、それはコンポーネントの正しさについて何を伝えているのでしょうか?

スナップショットテストは、偽陽性(false positive)を引き起こすことがあります。スナップショットテストからはコンポーネントの妥当性を確認できないため、バグが検出されないまま残ってしまうことがあります。スナップショットに過度に依存すると、開発者が自分のコードについて、実際よりも自信を持ちすぎてしまうことがあります。

スナップショットのもう一つの問題は、偽陰性(false negative)です。どんなにささいな変更でも、テストを失敗させてしまいます。句読点を直しただけ?スナップショットは失敗します。HTMLタグをよりセマンティックなものに置き換えただけ?スナップショットは失敗します。これにより、テストスイート全体への信頼を完全に失ってしまうかもしれません。スナップショットが本質的に悪いわけではなく、それなりの目的を果たしてくれます。しかし、いつスナップショットを取るべきで、いつ取るべきでないかを理解しておくことは有益です。

課題

概念に焦点を当てる

一部の記事ではJestやEnzymeテストライブラリが使われていますが、概念自体は他の環境にも適用できるはずです。

  1. Kent C. Dodds氏によるTesting Implementation Detailsは、実装の詳細をテストすることを避けることで、誤ったテスト結果や柔軟性のないテストをどう減らせるかを示してくれます。
  2. React Testing Libraryのチートシートのページで、利用可能なすべてのクエリメソッドにざっと目を通してください。すべてを使う必要はありませんが、特定のクエリには特定のメソッドを使うのが最適です。どのクエリメソッドも十分でない場合は、test idを使うという選択肢もあります。test idについては、React Testing Libraryのtest idのドキュメントで学んでください。
  3. ユーザーのシミュレーションをどう実現するかの感覚をつかむために、userEvent APIのドキュメントを読んでください。
  4. スナップショットテストの長所と短所についてのこの記事は、スナップショットテストの利点と欠点について詳しく掘り下げています。そして、Snapshot Testing: Benefits and Drawbacksのこちらの記事も、プログラミング全般においてスナップショットテストが何であるかを見事に説明してくれています。
