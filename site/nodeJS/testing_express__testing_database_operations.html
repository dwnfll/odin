Testing Database Operations

日本語訳

← nodeJS

we learn how to use mongodb-memory-server to write tests for routes that manipulate a database

イントロダクション

テストしているコードがデータベースに触れる必要がある場合、行わなければならないセットアップの量はかなり複雑になります。当然のことながら、ユーザーのデータを危険にさらすリスクがあるため、本番データベースに対してテストコードを実行したくはありません。このレッスンでは、ユニットテストおよび統合テストの環境で、データベースをどう扱うかについて触れていきます。

レッスン概要

このセクションでは、このレッスンで学ぶトピックの概要を説明します。

  • Expressサーバーの文脈における、ユニットテストと統合テストを扱う。
  • 統合テストのために、別々のデータベースを作成し使用する。

ユニットテスト――そもそも必要なのか?

飛び込む前に、そもそもテストしようとしているデータベース操作を、本当にテストする必要があるのかどうか、考えてみたいと思うかもしれません。pgや他のdbモジュールを使ってデータベースから直接読み書きしているだけなら、そのコードを本当にテストする必要はないかもしれません。pg(そしておそらく他の人気のあるdbモジュールもすべて)は、すでにそのすべてのアクションについて十分なテストを備えているため、あなたがただJSON APIを提供していて、行っていることが別のモジュールの関数を活用しているだけなら、それらの操作はすでにカバーされています。

もしあなたのクエリが複雑であれば、それらを正しく使えていること、そして書いたコードが意図した通りに動作することを確認するために、ユニットテストを追加することを正当化できるかもしれません。また、独自のコードを使ってデータのフィルタリング、ソート、その他の操作を行っている場合は、それもテストしたいと思うでしょう。ただし、自分のコードの場合は、それらをデータベース操作から切り離して独自のモジュールに取り出せれば、データベースをいじることなくそれらをテストできるので、より良いでしょう。

統合テスト

しかし、データベースに触れるものをテストしたい場合もあります。例えば、Testing Routes and Controllersレッスンでは、supertestを使ってサーバーに対する統合テストを行いました。

テスト用に別々のデータベースを作成し、簡単に識別できるようにtest_という接頭辞を付けてください。テスト用データベースのURLに入れ替えて、prisma migrateを実行したいと思うかもしれません。その後、このデータベースインスタンスにseedスクリプトを使うか、テストスイートのbeforeAll関数の中で手動でデータを挿入することもできます。

どのデータベースを使うかをコードベースで識別するために、環境変数を活用します。まず、テスト用データベースを.envファイルに追加してください:

NODE_ENV=development
DATABASE_URL=postgresql://<user>:<password>@localhost:5432/inventory_application
TEST_DATABASE_URL=postgresql://<user>:<password>@localhost:5432/test_inventory_application

次に、package.jsonファイルに適切なnpmスクリプトをセットアップしてください:

{
  // other stuff
  "scripts": {
    "dev": "node app.js",
    "test": "jest"
  },
  // even more stuff
}

環境変数を読み込むには、app.js用に好みの方法を使うことができますが、Jestでnodeを直接呼び出すわけではないため、Jestとともに--env-fileや--env-file-if-existsを使うことはできません。この場合、環境変数をテスト環境にプログラム的に読み込むために、process.loadEnvFile()のようなものを使う必要があります。例えば、これはJestのグローバルセットアップファイルの中で行うことができます。さらに、JestはデフォルトでNODE_ENVを'test'に設定するため、これが.envファイルのNODE_ENV=developmentを上書きします。そのため、そこでは特別なことをする必要はありません。

NODE_ENVに基づいて、データベースのURLをプログラム的に切り替えることができます:

const connectionString = process.env.NODE_ENV === 'test'
  ? process.env.TEST_DATABASE_URL
  : process.env.DATABASE_URL;

const adapter = new PrismaPg({ connectionString });
const prisma = new PrismaClient({ adapter });

テスト間でデータベースをリセットする

データベース操作をテストする際、常にテストを互いに分離し、どのテストも他のテストに依存しないようにする必要があります。例えば、テストされている主な振る舞いが実際にはうまく機能していたとしても、別のテストでテーブルの行を追加または削除しなかったせいで、あるテストが失敗するようなことは望ましくありません。つまり、テストの中でデータベースとやり取りする(レコードの読み取り、作成、更新、削除を行う)ときは、理想的には、次のテストの前にデータベースを初期状態にリセットすることでクリーンアップするべきです。

これは、beforeEachのようなものの中で便利に処理できます。例えば、usersとprojectsを持つデータベースがある場合、以下のようなものを用意できます:

beforeEach(async () => {
  await prisma.$transaction([
    prisma.user.deleteMany(),
    prisma.project.deleteMany(),
  ]);
});

これにより、他のどのテストを実行する前にも、usersテーブルとprojectsテーブルがリセットされることが保証されます。

さらに、テストを別々のファイルに分割している場合は、並列ではなく順番に(一つのファイルの後に次のファイルというように)実行するように、テストランナーをセットアップする必要があります。これにより、異なるテスト用データベースの操作が混同されるのを防げます。Jestはデフォルトでファイルを並列実行するため、package.jsonのtestスクリプトに--runInBandフラグを追加することで、順次実行を保証できます。

これで、セットアップは完了です。さあ……テストをしに行きましょう。

課題

  1. 深く掘り下げる必要はありませんが、人気のあるライブラリのほとんどがどれほどしっかりテストされているかを見るために、pgのGitHubリポジトリのtestsディレクトリを覗いてみてください。
