API Basics

日本語訳

← nodeJS

You already know most of what you need to create robust APIs. This lesson fills in the blanks for you.

イントロダクション

近年、ウェブサイトを開発するための新しいパターンが人気を集めています。データベースとビューテンプレートの両方をホストするアプリを作成する代わりに、多くの開発者は、これらの関心事を別々のプロジェクトに分離し、バックエンドとデータベースをサーバー上に(例えばHerokuのようなものか、Digital OceanのようなVPS上に)ホストし、それからGitHub PagesやNetlifyのようなサービスを使ってフロントエンドをホストしています。この技法は、Jamstackと呼ばれることもあります。

このようにプロジェクトを整理することは、ビジネスロジックとビューロジックを組み合わせるのではなく、プロジェクトをよりモジュール化できるため、有益な場合があります。これにより、ウェブサイト、デスクトップアプリ、モバイルアプリといった、複数のフロントエンドアプリケーションのために、単一のバックエンドソースを使うこともできるようになります。他の開発者たちは、ReactやVueのようなフロントエンドフレームワークを使って、洗練されたフロントエンドのみのシングルページアプリケーションを作るのが好きだという理由で、このパターンを好んでいます。

フロントエンドとバックエンドのアプリケーションは、通常JSONを使って互いに通信します。これは、私たちのフロントエンドJavaScriptコースを通してすでに出会っているはずです。そのため、今の時点で本当に学ぶ必要があるのは、あなたのExpressアプリケーションに、HTMLの代わりにJSONを話させる方法だけです。このレッスンの最後の課題では、チュートリアルを通してこれを扱いますが、基本的にあなたがしなければならないのは、res.send()やres.render()の代わりに、res.json()に情報を渡すことだけです。とても簡単ですよね?

Routesレッスンでのルートの整理の仕方を思い出してみると、関連するルートをまとめてグループ化し、それぞれのグループを個別のファイルに抽出しました。このアプローチにより、他のルートに影響を与えることなく、特定のルートをより簡単に修正できるようになりました。

REST

APIの構造にはさまざまな形があり得ます。例えば、/api/getAllPostComments/:postidや/api/posts/:postid/commentsという名前のルートを持つことができます。 しかし、CRUDアクションに対応する、あなたのAPIのための人気があり一般的な整理方法である、REST(Representational State Transferの頭字語)に従うのが慣習です。RESTのような確立されたパターンに従うことで、あなたのAPIはより保守しやすくなり、他の開発者があなたのAPIと統合しやすくなります。ソフトウェア開発は、しばしば明確なコミュニケーションが重要であり、それは期待に従うことによって助けられます。

RESTの実際の技術的な定義は少し複雑ですが、私たちの目的のためには、その要素のほとんど(ステートレス性、キャッシュ可能性など)は、単にExpressを使ってJSONを出力するだけで、デフォルトでカバーされます。特に考えたい部分は、エンドポイントのURI(Uniform Resource Identifier)をどう整理するかです。

REST APIはリソースベースです。これは基本的に、/getPostCommentsや/savePostInDatabaseのような名前を持つ代わりに、リソースを直接指す(この場合はブログ投稿)ということを意味し、アクションを決定するためにGET、POST、PUT、DELETEといったHTTP動詞を使います。 通常、これはリソースごとに2つのURIという形を取ります。一つはコレクション全体のためのもので、もう一つはそのコレクション内の単一のオブジェクトのためのものです。例えば、/postsからブログ投稿のリストを取得し、それから/posts/:postidから特定の投稿を取得するかもしれません。このようにコレクションをネストすることもできます。ある投稿へのコメントのリストを取得するには/posts/:postid/commentsにアクセスし、それから単一のコメントを取得するには/posts/:postid/comments/:commentidにアクセスします。以下は、あなたが持つことになるかもしれない、エンドポイントの他の基本的な例です。

HTTP動詞の表

動詞 アクション 例
POST Create POST /posts 新しいブログ投稿を作成する
GET Read GET /posts/:postid 単一の投稿を取得する
PUT Update PUT /posts/:postid 単一の投稿を更新する
DELETE Delete DELETE /posts/:postid 単一の投稿を削除する

APIのURIのそれぞれの部分は、リソースを指定します。例えば、GET /postsはブログ投稿のリスト全体を返しますが、GET /posts/:postidは求める正確なブログ投稿を指定します。GET /posts/:postid/commentsでさらにネストして、そのブログ投稿へのコメントのリストを返すこともできますし、GET /posts/:postid/comments/:commentidで非常に特定のブログ投稿のコメントを返すこともできます。

CORS

同一オリジンポリシーは、ブラウザにとって重要なセキュリティ対策であり、ウェブページが、そのページを提供したオリジンとは異なるオリジンにリクエストを送ることを制限します(何が「同一オリジン」とみなされるかについてのいくつかの例は、上記のリンクを参照してください)。

次のプロジェクトでは、私たちのREST APIとフロントエンドを別々に(異なるドメインに)デプロイすることになります。つまり、私たちの別々のフロントエンドがそのリソースにアクセスできるように、サーバー上でクロスオリジンリソース共有(CORS)を有効にする必要があります。Expressには、すべてをセットアップできるCORSミドルウェアパッケージがあります。

今のところ、どのオリジンからでもアクセスを許可するだけで問題ありません。これによって開発はかなり楽になりますが、実際のプロジェクトでは、本番環境にデプロイしたら、おそらくあなたのフロントエンドのウェブサイト以外のあらゆるオリジンからのアクセスを、特別にブロックしたいと思うでしょう。上記のドキュメントでは、これを行う方法が説明されています。

課題

  1. RESTful API設計について読んでください。もし最初の記事と一緒にコードを書きたい場合は、これにはリクエストボディのJSONデータを解析するためのbody-parserミドルウェアが含まれていますが、Express 4.16.0以降、この解析機能はExpressパッケージ自体に直接組み込まれていることに注意してください。
  2. Expressで REST APIをセットアップするについてのこのチュートリアルを読み、一緒にコードを書いてください。これはこれまで出会った中で最良のExpressチュートリアルの一つであり、モジュール化されたコードの整理やミドルウェアの書き方についても触れており、最後には素晴らしい追加情報へのリンクもあります。
