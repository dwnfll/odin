Controllers in Express

イントロダクション

コントローラーの仕事は、本当のところ、究極の仲介役として振る舞うことです。モデルに尋ねたい質問が何であるかは知っていますが、それらの質問を実際に解決するための重労働はすべてモデルにやらせます。どのビューをレンダリングしてブラウザに送り返したいかは知っていますが、そのHTMLをすべて組み立てる作業自体はビュー自身に任せます。だからこそ「コントローラー」と呼ばれるのです――何をすべきかを把握するだけの賢さを持ちながら、大変な作業はすべて委任するのです。

結局のところ、コントローラーはこの一連の作業の頭脳であり、それぞれのコンポーネントが最終的な結果を届けるために自分の役割を果たすことを保証します。そして実際のところ、MVCパターンの一部として、明確に定義された責任を持つ単なる関数にすぎません。

レッスン概要

このセクションでは、このレッスンで学ぶトピックの概要を説明します。

  • さまざまなレスポンスメソッドを探る。
  • エラーを適切に捕捉し処理するためのエラーハンドリングミドルウェアを実装する。
  • バリデーションや認証といった、ミドルウェアのよくあるユースケースを説明する。

レスポンスを処理する

コントローラーからレスポンスを送信する際には、いくつかのメソッドを自由に使うことができます。よく使われるメソッドとそのユースケースをいくつか見ていきましょう。

  • res.send - レスポンスを送信するための汎用的なメソッドで、渡されたデータに基づいてContent-Typeヘッダーを自動的に設定してくれるため、送信できるデータについて柔軟性があります。例えば、オブジェクトを渡すと、それをJSONとして文字列化し、Content-Typeヘッダーをapplication/jsonに設定します。
  • res.json - これは、JSONでリクエストに応答するためのより明示的な方法です。これは常にContent-Typeヘッダーをapplication/jsonに設定し、データをJSONとして送信します。
  • res.redirect - クライアントを別のURLにリダイレクトしたい場合、このメソッドがその機能を提供してくれます。
  • res.render - res.renderを使うと、ビューテンプレートをレンダリングし、その結果のHTMLをレスポンスとして送信できます。これについては後のレッスンで扱います。

ステータスコードを手動で設定するために使える便利なメソッドもあります。

  • res.status - これはレスポンスのステータスコードを設定しますが、それ自体ではリクエスト-レスポンスサイクルを終了しません。これを介して他のメソッドをチェーンできます(例えばres.status(404).send(...)は可能ですが、res.send(...).status(404)はできないことに注意してください)。デフォルトのステータスコードである200を使いたい場合は、これを省略しても構いません。

res.sendとres.json

res.sendが渡されたデータに基づいてContent-Typeを自動的に設定してくれるのなら、なぜres.jsonをわざわざ使うのでしょうか?res.jsonはJSONを強制し、オブジェクトでない値も自動的にJSONに変換しますが、res.sendはそうしません。res.jsonは、内部的にはres.sendも呼び出す、単なる便利なメソッドです。res.sendは、真偽値とオブジェクト(配列を含む)を扱う場合にのみ、JSONとして処理します。

そのため、便宜上、res.sendの代わりにres.jsonを使う方が適切であり、JSONを送信するのであれば、文字通り「json」という名前のメソッドを使うのも理にかなっています。まさに完璧な組み合わせですね!

また、これらのレスポンスメソッドは、リクエスト-レスポンスサイクルを終了させるだけだということにも注意する必要があります。関数の実行を終了させるわけではありません。例えば、以下のようにした場合:

app.use((req, res) => {
  // This works and this ends the request-response cycle
  res.send("Hello");

  // However, it does not exit the function so this will still run
  console.log('will still run!!');

  // This will then throw an error that we cannot send again after sending to the client already
  res.send("Bye");
});

ミドルウェア

ミドルウェア関数はExpressにおける中核的な概念であり、リクエストとレスポンスを処理する上で極めて重要な役割を果たします。それらは、受信したリクエストと、最終的に意図されたルートハンドラの間で動作します。

ミドルウェア関数は通常、3つの引数を取ります(ただし、後ほど扱う4つの引数を取るものが一つあります):

  • req - 受信したHTTPリクエストを表す、リクエストオブジェクト。
  • res - クライアントに送り返されるHTTPレスポンスを表す、レスポンスオブジェクト。
  • next - チェーン内の次のミドルウェア関数に制御を渡す関数(これについては後ほど触れます)。これは省略可能です。

命名規則

名前は単なる慣習にすぎず、req → request、res → responseのように、好きなように名付けることができます。

ミドルウェア関数は、以下のようなさまざまなタスクを実行できます:

  • リクエストオブジェクトやレスポンスオブジェクトを変更する(例えば、一部のパッケージは、リクエストオブジェクトに新しいプロパティを追加したり、res.renderでレンダリングされるテンプレートで使われるres.localsを設定したりします)。
  • 追加のコードを実行する(メインのロジックに進む前にリクエストを検証するバリデーションミドルウェア関数、認証ミドルウェア関数など)。
  • チェーン内の次のミドルウェア関数を呼び出す。
  • リクエスト-レスポンスサイクルを終了する(つまり、チェーンの中にさらに関数があったとしても、それ以上のミドルウェア関数は呼び出されなくなります)。

Expressには豊富なエコシステムがあるので、あなたが直面している問題を解決してくれるパッケージが、おそらく見つかるでしょう。例えば、認証、CORS、レート制限、セッション、ロギング、バリデーションなどを扱うためのミドルウェア関数を提供するパッケージがあります!このレッスン(そしてこのコース)を通して、このコースでプロジェクトを構築するのに必要なミドルウェアを紹介していきますが、自分自身で探索してみるのも歓迎です。

アプリケーションレベルのミドルウェア

アプリケーションレベルのミドルウェアは、app.useまたはapp.METHOD(例えばapp.get、app.post)関数を使って、Expressのインスタンスにバインドされます。Expressは、指定されたパスに一致するすべての受信リクエストに対して、これらのミドルウェア関数を実行します。パスを指定しない場合、Expressはデフォルトでパスを/とし、あらゆる受信リクエストに一致させます。他のどんなミドルウェア関数とも同じく、それらに到達する前にリクエスト-レスポンスサイクルが終了していれば、それらは実行されません。通常、これらのミドルウェア関数は、常に最初に実行されることを保証するために、アプリケーションコードの一番上に配置されます。

Expressは、アプリケーションの中で頻繁に使うことになる、いくつかの重要な組み込みミドルウェア関数を提供しています。それらには以下が含まれます:

  • ボディパーサー(例えばexpress.json、express.urlencoded) - これらにより、受信したリクエストのボディを正しく解析できるようになり、req.bodyを通してそれを使えるようになります。
  • 静的ファイルの提供(例えばapp.use(express.static('public'))) - このミドルウェア関数は、HTML、CSS、JavaScript、画像といった静的ファイルを提供します。引数を渡して、どのディレクトリから静的ファイルを提供するかを指定できます。

ルーターレベルのミドルウェア

ルーターレベルのミドルウェアは、アプリケーションレベルのミドルウェアと同じように動作しますが、router.useまたはrouter.METHOD(例えばrouter.get)関数を使って、Expressルーターのインスタンスにバインドされます。このため、Expressは、リクエストがそのルーターに一致し通過する場合にのみ、これらのミドルウェアを実行します。

以下は、基本的なミドルウェア関数の例です:

function myMiddleware(req, res, next) {
  // Perform some operations
  console.log("Middleware function called");

  // Modify the request object
  req.customProperty = "Hello from myMiddleware";

  // Call the next middleware/route handler
  next();
}

app.use(myMiddleware);

この例では、ミドルウェア関数がメッセージをログに出力し、リクエストオブジェクトにカスタムプロパティを追加し、それからnext()関数を呼び出して、次のミドルウェア関数またはルートハンドラに制御を渡しています。また、app.useの使用を通じてこのミドルウェア関数を登録しているため、これはアプリケーションレベルのミドルウェアになります。このチェーンの中でmyMiddlewareに続くミドルウェア関数は、これで値"Hello from myMiddleware"を含むreq.customPropertyにアクセスできるようになります。

一つ注意すべき点は、Expressはアプリケーションの中で定義または登録した順番通りにミドルウェア関数を実行するということです。つまり、ミドルウェア関数を定義する順番が重要であり、それがリクエスト-レスポンスサイクルの中でそれらが呼び出される順番を決定します。そのため、ミドルウェア関数が正しい順番で配置されていることを確認し、意識しておく必要があります。例として、一部のパッケージにはRequestオブジェクトを変更するミドルウェア関数があり、その結果、それらのミドルウェア関数の変更を、それより下にあるすべてのミドルウェア関数で見られるようにするためには、アプリケーションの一番上に配置される必要があります。

エラーを処理する、特殊なタイプのミドルウェア関数もあり、これについてはこの後すぐに説明します。

コントローラー

先ほど述べたように、コントローラーは単なる関数です。それらは(少なくともExpressの世界では)、ルートハンドラによって使われるミドルウェアにも分類されます。しかし、コントローラーとミドルウェアが別個の概念であることに注意することが重要です。コントローラーは、ソフトウェアを整理するための設計アプローチである、MVC(Model-View-Controller)パターンの重要な構成要素です。一方でミドルウェアは、コードを実行したり、リクエストを変更したり、リクエスト-レスポンスサイクルの特定の時点でサイクルを終了させたりすることを可能にする、Expressの中核機能です。つまり、私たちはExpressの中でミドルウェアを使うことで、MVCパターンの「コントローラー」の部分を実装しているのです。

コントローラーは、リクエストがサーバーに到達し、あるルートがリクエストされたHTTP動詞とパスに一致したときに、その役割を発揮します。ルートは、定義されたミドルウェアチェーンに基づいて、どのコントローラーがそのリクエストを処理すべきかを決定します。それから、適切なコントローラーが引き継ぎ、リクエストを満たすために必要なアクションを実行します。これには、モデルからデータを取得したり、そのデータを処理したり、ビジネスロジックに基づいて判断を下したり、新しいデータでモデルを更新したりすることが含まれる場合があります。

コントローラーがそのタスクを完了すると、処理済みのデータをビューに渡します。それからビューは、このデータをクライアントに送り返すのに適した形式にレンダリングします。通常、これはHTMLになります。後ほどAPIの構築について扱う際には、以前使ったことのあるAPI(例えばGiphy API)のように、JSONレスポンスを送信することもできます。

これらのコントローラーの命名規則は、通常、それらがアタッチされるルートに基づきます。例えばGETルート → getSomething、POSTルート → createSomething、DELETEルート → deleteSomething、といった具合です。とはいえ、Expressは自分の主張を持たない(unopinionated)ため、固定のルールがあるわけではありません。それは常に、あなたや他の誰かの慣習、そしてその関数の要件に基づくことになります。

前のレッスンから、すでにアプリケーションのセットアップが済んでいるはずです。以前、/authors/:authorId用のルートを定義しましたが、今回はそのルート用のコントローラーを定義し、サンプルデータと連携させます。しかし、例が何か成果を生み出すようにするために、まずはIDで著者を取得するために使える関数を持った、モックのデータベースを作成しましょう。

プロジェクトのルートに以下のファイルdb.jsを作成し、次のコードを追加してください:

// db.js

const authors = [
  { id: 1, name: "Bryan" },
  { id: 2, name: "Christian" },
  { id: 3, name: "Jason" },
];

async function getAuthorById(authorId) {
  return authors.find(author => author.id === authorId);
};

module.exports = { getAuthorById };

このファイルの名前、内容、場所は、ここでは重要ではありません。これは単に、コントローラーの中で呼び出せるようにするための、簡単なモック「データベース」とクエリ関数です。

次に、コントローラーのために、controllersフォルダの中に以下のファイルauthorController.jsを作成してください:

// controllers/authorController.js

const db = require("../db");

async function getAuthorById(req, res) {
  const { authorId } = req.params;

  const author = await db.getAuthorById(Number(authorId));

  if (!author) {
    res.status(404).send("Author not found");
    return;
  }

  res.send(`Author Name: ${author.name}`);
};

module.exports = { getAuthorById };

この例では、getAuthorById関数は、IDによって著者を取得することに関連する特定のアクションを処理する、コントローラーです。ルートを定義しているファイルにこれをインポートして、以下のようにこのコントローラーを使うことになります:

// routes/authorRouter.js

const { Router } = require("express");
const { getAuthorById } = require('../controllers/authorController');

const authorRouter = Router();

// ... other route handlers
authorRouter.get("/:authorId", getAuthorById);

このコントローラーの中で何が起きているかを分解してみましょう:

  1. ルートパスにはルートパラメータ(/authors/:authorId)が含まれています。コントローラーはreq.paramsからauthorIdを抽出します。
  2. それから、authorIdに基づいて著者データを取得するために、データベースのクエリ関数getAuthorByIdを呼び出します。
  3. コントローラーが著者を見つけられなかった場合、res.status(404).send(...)を使って、404ステータスコードとメッセージ"Author not found"を含むレスポンスを送信します。それから、レスポンスを送信しても関数の実行が自動的に停止するわけではないため、コントローラー内の他のロジックが呼び出されるのを避けるために、コントローラー関数からreturnします。
  4. コントローラーが著者を見つけた場合、res.send(...)を使って、著者名を示すテキストとともに200ステータスコードのレスポンスを送信します。

とてもシンプルですよね?

エラーを処理する

堅牢なアプリケーションを構築する際には、アプリケーション内でエラーを適切に処理することが極めて重要です。適切なエラーハンドリングを実装することで、クライアントに意味のあるエラーレスポンスを提供でき、アプリケーションが予期せずクラッシュするのを防ぐことができます。そして、私たちが知っているように、エラーは非同期処理の最中に発生することがあり、これまでのコードスニペットでは、それをきちんと処理できていませんでした。これらの可能性を処理するために何ができるか、見ていきましょう。

try/catch

先ほどと同じコードを使って、コントローラーのロジックをtry/catchブロックで包むことで、素早くエラーを処理できます。

async function getAuthorById(req, res) {
  const { authorId } = req.params;

  try {
    const author = await db.getAuthorById(Number(authorId));

    if (!author) {
      res.status(404).send("Author not found");
      return;
    }

    res.send(`Author Name: ${author.name}`);
  } catch (error) {
    console.error("Error retrieving author:", error);
    res.status(500).send("Internal Server Error");

    // or we can call next(error) instead of sending a response here
    // Using `next(error)` however will only render an error page in the express' default view and respond with the whole html to the client.
    // So we will need to create a special type of middleware function if we want a different response and we will get to that... next.
  }
};

もし、非同期のミドルウェア関数がたくさんあり、そのうちの多くが、ステータスコードやレスポンスメッセージが違うだけで、同じように応答する場合はどうでしょうか?それぞれのミドルウェアでtry/catchを使う代わりに、Expressはスローされたエラーを自動的に捕捉してnext(error)を呼び出し、それが特別な「エラーミドルウェア関数」に制御を渡してくれるため、元のコントローラー自体の中で捕捉して処理する必要はなくなります。

エラーハンドラミドルウェア

エラーハンドラミドルウェア関数は、アプリケーション内の他のミドルウェア関数から降りてくる、すべてのエラーを処理します。このエラーミドルウェア関数は、最後に実行されるミドルウェア関数であることを保証し、それ以前のミドルウェア関数からバブリングしてくるエラーだけを処理するようにするために、アプリケーションコードの一番最後に配置したいところです。

アプリケーション内のすべてのミドルウェア関数の最後に、app.jsに以下のコードを追加してください:

// Every thrown error in the application or the previous middleware function calling `next` with an error as an argument will eventually go to this middleware function
app.use((err, req, res, next) => {
  console.error(err);
  res.status(500).send(err);
});

しかし、これは4つのパラメータを必要とするミドルウェア関数であり、それらが使われていなくても提供する必要があることに注意してください。例えば、パラメータのうち一つでも除いてしまうと、エラーミドルウェア関数として認識されなくなります。自分で試してみることもできますよ ;)

これは少し変わった点で、コールバックの中でエラーオブジェクトが必ず最初のパラメータでなければなりません。

このミドルウェア関数は、他のミドルウェア関数でスローされたエラー、または前のミドルウェア関数がnext関数(例えばnext(err))を使って送ったものを処理します。

そのため、Expressがこのミドルウェア関数を区別する方法は、やはり4つのパラメータを追加することであり、一つでも欠けてはいけません。4つ未満のパラメータを持つルートミドルウェア関数、またはミドルウェア関数は、たとえそれを最後に配置したとしても、常にこのエラーミドルウェア関数ではなく、リクエストミドルウェア関数と見なされます。

app.use((req, res, next) => {
  throw new Error("OH NO!");
  // or next(new Error("OH NO!"));
});

app.use((err, req, res, next) => {
  console.error(err);
  // You will see an OH NO! in the page, with a status code of 500 that can be seen in the network tab of the dev tools
  res.status(500).send(err.message);
});

カスタムエラーを作成する

上記の解決策では、エラーミドルウェア関数は、どんなエラーであっても実質的に500ステータスコードでしか応答できません。しかし、もし本当に404を送りたい場合はどうでしょうか?これを行う一般的な方法は、Errorオブジェクトを拡張して独自のカスタムエラーを作成することです。

errorsフォルダの中に、以下のファイルCustomNotFoundError.jsを作成してください:

// errors/CustomNotFoundError.js

class CustomNotFoundError extends Error {
  constructor(message) {
    super(message);
    this.statusCode = 404;
    // So the error is neat when stringified. NotFoundError: message instead of Error: message
    this.name = "NotFoundError";
  }
}

module.exports = CustomNotFoundError;

これで、このカスタムエラークラスを使って、先ほどのgetAuthorByIdのバージョンを次のようにリファクタリングできます:

const CustomNotFoundError = require("../errors/CustomNotFoundError");

const getAuthorById = async (req, res) => {
  const { authorId } = req.params;

  const author = await db.getAuthorById(Number(authorId));

  if (!author) {
    throw new CustomNotFoundError("Author not found");
  }

  res.send(`Author Name: ${author.name}`);
};

Expressは非同期のミドルウェア関数でスローされたエラーを自動的に捕捉してくれるため、この関数の中でエラーレスポンスを送信する必要はなく、代わりにただエラーをスローするだけで済みます。Expressはnext()を呼び出し、捕捉したエラーを引数として渡すことで、私たちのカスタムエラーハンドラに制御を渡してくれます!

これは最終的にエラーミドルウェア関数に行き着き、そこでも次のように変更を加えることができます:

app.use((err, req, res, next) => {
  console.error(err);
  // We can now specify the `err.statusCode` that exists in our custom error class and if it does not exist it's probably an internal server error
  res.status(err.statusCode || 500).send(err.message);
});

これは便利なパターンであり、必要に応じてさまざまなユースケースのために、さらにカスタムエラークラスを作成することができます。

next関数とは何か

これまでにnext関数を何度か使ってきました。しかし、それは正確には何なのでしょうか?簡単に言うと、それはアプリケーションのリクエスト-レスポンスサイクルの中で、次のミドルウェア関数に制御を渡すために使われます。例を挙げてみましょう:

function middleware1(req, res, next) {
  console.log("Middleware 1");
  next(); // Pass control to the next middleware
};

function middleware2(req, res, next) {
  console.log("Middleware 2");
  res.send("Response from Middleware 2");
  // request-response cycle ends here
};

function middleware3(req, res, next) {
  console.log("Middleware 3");
  res.send("Response from Middleware 3");
};

app.use(middleware1);
app.use(middleware2);
app.use(middleware3);
// will log `Middleware 1` -> `Middleware 2` and send a response with the text "Response from Middleware 2"

ここではmiddleware1、middleware2、middleware3があります。middleware1はnext関数を呼び出し、まだレスポンスを送信していないため、制御を次のミドルウェア関数――middleware2(app.use呼び出しの順番によって示される通り)――に渡します。middleware2の中では、レスポンスを送信し、それによってリクエスト-レスポンスサイクルが終了します。それが終了したため、3番目のミドルウェア関数(middleware3)は実行されません。しかし、もし何らかの理由でmiddleware1の中でnext関数を呼び出さなかったら、どうなるかわかりますか?ぜひTOP Discordサーバーに立ち寄って、あなたの考えを教えてください!

また、先ほどnext関数の呼び出しについて説明したように、それに渡すことができる引数には以下のものがあります:

  1. 引数なしのnext() - 次のミドルウェア関数に制御を渡します。とてもシンプルでわかりやすいですね。
  2. エラー引数を伴うnext(new Error(...)) - 制御を直接エラーミドルウェア関数に渡します。
  3. 文字列next('route') - (もしあれば)同じ一致するパスを持つ、次のルートハンドラに制御を渡します。これはapp.METHODまたはrouter.METHODでのみ機能します。場合によっては、これは単に引数なしでnextを呼び出すのと同じ結果になることもあります。
  4. 文字列next('router') - 特定のルーターインスタンスにアタッチされたすべてのミドルウェア関数をスキップし、そのルーターインスタンスの外側に制御を戻します。基本的には、そのルーターを抜けて、親のルーター、例えばappに戻ります(そう、Expressアプリ自体も、内部的には単なるルーターにすぎません)。

この4つのうち、他の2つが必要になるような非常に特殊なニーズがない限り、私たちはおそらく最初の2つしか使わないでしょう。

学んだことをまとめる

もしここまでコードを書きながら進めてきたなら、以下のようなフォルダ構造になっているはずです:

express-app/
├─ errors/
│  ├─ CustomNotFoundError.js
├─ controllers/
│  ├─ authorController.js
├─ routes/
│  ├─ authorRouter.js
│  ├─ ... other routers
├─ app.js
├─ db.js

練習として、db.jsファイルにもっとサンプルデータを作成したり、これまでに作成した他のルート用のコントローラーを作成したりしてみてください。

    非同期ハンドラ

    上記の記事を読んでいると、次のような段落に気づくかもしれません:

    — Express was not built to await on handlers or handle returned promises. Hence, when a handler function is an async function, it will return a promise. When we throw an error, we are simply rejecting that promise. So, the only way to pass an error is via 'next(err)' function

    Expressの現在のバージョン(v5)では、非同期のルートハンドラがネイティブでサポートされるようになりました。この点に関しては、この記事は古くなっていることに注意してください。
